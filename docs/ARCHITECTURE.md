# Arcform Architecture

Reference doc for Arcform's source layout, key types, execution model, and runtime dependencies. Loaded on demand via the trigger pointer in `CLAUDE.md`.

## Source layout

```
src/
  main.rs         # Entry point
  cli.rs          # Clap CLI definition
  manifest.rs     # YAML manifest parsing (arcform.yaml)
  runner.rs       # Step execution engine (~1150 lines, largest module)
  engine.rs       # SQL engine invocation (DuckDB CLI delegation), the engine range, the extension refusals
  asset.rs        # Assets, SQL auto-discovery, dependency validation, case-collision gate
  duckdb_tokens.rs # A SQL file's tokens, asked of the DuckDB that runs it (`sql_tokenize`); the refusals and the asset graph read these
  duckdb_lineage.rs # What each statement reads and produces, from DuckDB 2.0's tokens and parse trees
  introspect.rs   # SQL introspection: chooses the reader, falls back to sqlparser-rs per statement
  precondition.rs # Typed step preconditions (modified_after, fresh, command, tool)
  state.rs        # Run state tracking (step config hash, artifact hash, staleness)
  inspect.rs      # Read-only look inside a Protocol's database: `arc table describe`, `arc sql query`
  record.rs       # Recording a step: the operation catalogue, its argument gates, `arc operation record`, `arc sql record`
  protocol_files.rs # Writes a Protocol's schemas/, panels/ and README.md, each recorded in its own history: `arc protocol write-file`
  panel_check.rs  # Finds panels that name a table or column the Protocol does not make: `arc panel check`
  report.rs       # Writes report.md from an agent's prose and a run's contract: `arc report write`
  skills.rs       # `arc skills`: lists the agent skills `build.rs` embeds from `skills/`, and installs them into agents' skills folders
  finetype_cli.rs # Runs the `finetype` command and holds its version floor, `MIN_VERSION`; shared by the CLI verbs and the MCP tools
  error.rs        # Error types
  mcp/            # `arc mcp`: a Model Context Protocol server over stdio (feature `mcp`)
    mod.rs        #   JSON-RPC transport, protocol-version negotiation, the tool registry, each tool's read-only, open-world and destructive annotations
    finetype.rs   #   The five FineType tools, each running the `finetype` command
    hero.rs       #   arc's own tools: protocol_run, protocol_create, the record, edit, history, describe, query, check and report tools
```

### `arc mcp` and `protocol_run`

The MCP stdio transport gives standard output to JSON-RPC alone: one message per line, and any other byte there breaks the client's reading of the stream. A run prints a great deal (step progress, the asset graph, the rows a SQL step's `SELECT` prints on the DuckDB command line, whatever a `command:` step writes), so `protocol_run` does not run the Protocol inside the server. It starts `arc run` as a child process from the server's own executable, in the Protocol's directory, with standard input closed and standard output and standard error piped into a buffer that keeps the last 4,000 bytes. When the child exits, the tool returns the run record it wrote under the Protocol's runs directory; when it wrote none, the tool's error carries the exit status and that tail of output.

`tests/finetype_mcp.rs` (feature `mcp`) calls the five FineType tools through `arc mcp` against the real `finetype`, with every property and enum value their `tools/list` schemas advertise; a property with no call, or a call setting one no schema advertises, fails the test. The unit tests in `src/mcp/finetype.rs` use a stand-in that accepts any arguments, so this is the test that catches a flag finetype drops. CI's build job installs the finetype release pinned by `FINETYPE_VERSION` and `FINETYPE_SHA256` in `.github/workflows/ci.yml` and sets `ARCFORM_REQUIRE_FINETYPE_CLI`, under which this test fails rather than skips when the CLI is missing; `tests/common` resolves the binary as arc does, from `FINETYPE_BIN` or `PATH`, against the floor in `src/mcp/finetype.rs`.

### DuckDB 2.0: the engine, the shared database and agent mode

arc links the DuckDB 2.0 library, the `duckdb` crate at `=1.20000.0` (DuckDB 2.0.0), and runs each SQL step and SQL hook on a DuckDB command line, `ARC_DUCKDB_BIN` or `duckdb` on `PATH`, as `duckdb <db> -f <file.sql>`. It accepts a command line in `>=2.0, <3` (`SUPPORTED_ENGINE_RANGE` and `OLDEST_ENGINE` in `src/engine.rs`). The two must share a major version because they share a file: the command line writes the Protocol's database, and arc opens the same file through the linked library for run state, `arc table describe` and `arc sql query`. A database DuckDB 2.0 creates cannot be opened by DuckDB 1.x, so a 1.x command line is refused as too old even with `ARC_ALLOW_UNTESTED_ENGINE`, and the refusal names arc 0.2.1 as the release for DuckDB 1.5. The variable lifts the range only upwards, to a 2.x pre-release or a 3.x, where a failure to open the file is the user's accepted risk; under it arc also reads the tokens and trees of a DuckDB whose major is above 2 (`duckdb_tokens::tokens_accepted_from`, reading the variable through `engine::untested_engine_allowed` as the engine check does), and below 2 is refused either way.

A development build whose printed source id is the commit of a release's tag counts as that release wherever arc compares versions (its range, a Protocol's `engine_version:`, the extension pin keys, the new-engine notice); the run record keeps the raw string. Homebrew's 2.0.0 prints `v2.0.0-dev88614 (Development Version) d54cbbe3df`, the v2.0.0 tag's commit. The release-tag-to-commit table is `RELEASE_COMMITS` in `src/engine.rs`, and each later 2.x patch needs a row there. Such a build looks community extensions up under its commit hash, which the registry does not serve, so a run of a Protocol that installs one warns before the first step, naming DuckDB's installer for the release build.

arc reads SQL tokens from `sql_tokenize`, which lives in DuckDB's autocomplete extension. DuckDB's release command line links it in; a build without it, such as Homebrew's 2.0.0 at the time of writing, fails to autoload it, so it gives no tokens for any file. `arc run` names that cause rather than refusing the first file: when the pre-run token check fails, or asked DuckDB nothing (no file held SQL yet), it probes `SELECT count(*) FROM sql_tokenize('SELECT 1')` (`duckdb_tokens::tokenizer_failure`, through `Engine::tokenizer_failure`), and a DuckDB that exits with an error there refuses the run with exit 2 before any step (`Error::NoTokenizer`), naming the DuckDB, its printed version and DuckDB's installer pinned to `DUCKDB_RECOMMENDED` in `src/engine.rs`. The message says the build lacks the autocomplete extension only when DuckDB's error names `autocomplete` or `sql_tokenize`; any other error is quoted, with the same fix. A run whose files read starts no extra DuckDB process: the probe adds one only on those two paths. arc probes the capability and never recognises a build by name or path, so a build that adds the extension just works. Outside a run, the one sqlparser-rs warning names the same cause and fix when the same probe fails. `scripts/install.sh` runs that probe on the `duckdb` on `PATH` after installing arc, and installs DuckDB's release build with DuckDB's installer when there is none or it fails (naming a 1.x by its version, since 1.x has no `sql_tokenize` at all), unless `ARC_SKIP_DUCKDB` is set.

Every DuckDB process arc starts goes through `DuckDbProgram::command()`, which sets `DUCKDB_AGENT_MODE=0`. DuckDB 2.0's shell otherwise switches to markdown output, a row cap and a stderr banner when it finds a variable an agent's harness sets (`AI_AGENT`, `CLAUDECODE` and others), and arc would misread its answers and report the banner as a step's error. The environment arc adds for a step holds only `ARC_*` names, so a Protocol cannot turn agent mode back on or change which DuckDB runs it.

`arc run` prints one notice on stderr before the first step when the newest readable run record that names `duckdb_cli` names a different major.minor from the engine about to run; for 1.x to 2.x it also names the four results DuckDB 2.0 changes without an error. It changes no setting.

The bundled build (`bundled-duckdb`) compiles in the DuckDB source `libduckdb-sys` vendors, which names itself a development version; until duckdb-rs fixes that (duckdb/duckdb-rs#917), CI's `bundled` job and the release workflow define `DUCKDB_VERSION` for the C++ compile through `CXXFLAGS`, and `the_linked_duckdb_reports_the_release_version` in `src/engine.rs` asserts the result for every build, bundled or linked. The documented from-source command (README, `scripts/install.sh`) sets the same `CXXFLAGS`; a bare `cargo install --features bundled-duckdb` does not, and reports the development version until then.

One DuckDB version runs throughout: the crate pin in `Cargo.toml`, `DUCKDB_VERSION` in the CI workflows, `DUCKDB_RECOMMENDED` in `scripts/install.sh` and in `src/engine.rs` (the version arc's messages pin DuckDB's installer to) and each entry's `duckdb_versions` in `src/vetted_extensions.json`. `scripts/check_duckdb_version.py`, run in CI's `release-guard` job with its self-test, fails when a pin disagrees with the version Cargo.lock's `libduckdb-sys` decodes to; a vetted entry must include the linked version and may list others. CI's build job also runs the tests that need a real DuckDB, with `--include-ignored`, against the v2.0.0 command line it installs, named by `ARC_DUCKDB_RECORD_BIN`.

### Reading a step's SQL

arc reads each SQL file twice over for two purposes, from one answer: the refusals (which extensions a step installs, which settings it names) and the asset graph (what each statement reads and produces). Both start from the same two layers.

- **The command-line layer is arc's own.** What the DuckDB command line does to a `-f` file before its parser sees it is not something DuckDB will report, so `cli_lines`, `sql_is_complete` and `cli_batches` in `src/engine.rs` copy it from DuckDB v2.0.0's `tools/shell/shell.cpp` and `src/parser/parser.cpp`, each rule citing its source: dot commands and `#` lines, the `0x03` byte, NUL bytes, how lines batch into statements (a backtick counts as a quote in statement completion on 2.0), and the unicode spaces the parser reads as a space.
- **The tokens are DuckDB's.** `src/duckdb_tokens.rs` asks the program the step runs on (never `PATH` when `ARC_DUCKDB_BIN` is set, and never the linked library) for each batch's `sql_tokenize`, one process per file. Each batch is sent hex-encoded, because the command line drops a `\r` before a `\n` in piped standard input, and every token's start is a byte offset into the file arc holds. Answers are cached by the SHA-256 of the file's bytes and shared between the pre-run check, the check just before each step, and the asset graph, so a file read again unchanged is not asked again. A step's whole reading, its trees included, is cached the same way by program and SHA-256 in `duckdb_lineage::read_step`, so the run contract written after the last step reuses the asset graph's reading and starts no DuckDB of its own: a run of three SQL steps starts seven DuckDB processes before its first step (the version, three token questions, three tree questions) and one after its last. A program that could not be started is remembered for `NOT_STARTED_LIFETIME` (30 seconds) in `src/duckdb_tokens.rs`, so a command reading many files with no DuckDB starts none after the first, and a long-lived `arc mcp` started before DuckDB was installed finds it once it is.

The refusals fail closed: a DuckDB that fails, answers in a form arc cannot read, or answers from a version other than 2.x (with `ARC_ALLOW_UNTESTED_ENGINE` set, one before 2) stops the run with exit 2, naming the step or hook. An empty token list (no SQL in the file) is a valid answer and asks nothing. `PARSER_SWITCHES` is `allow_parser_override_extension` and `current_dialect`; `enable_peg_parser` is gone in 2.0. `docs/VETTED_EXTENSIONS.md` is the user-facing statement of what is refused and what is not read.

The asset graph is read by `src/duckdb_lineage.rs` by default: statements split at DuckDB's `;` tokens, then `json_serialize_sql` gives the tree of each query, and what a non-query statement creates, inserts into or copies comes from its tokens. A keyword is matched by its text, never by the token type, which on 2.0 changes with context. sqlparser-rs (the vendored `arcform-sqlparser` fork) reads, per statement, any statement DuckDB gives no tree for; `ARC_SQL_READER=sqlparser` has it read every statement, and any value other than `duckdb` or `sqlparser` is refused. A statement neither reader can read draws a warning and reads nothing; the rest of the step is still read. A bare-name statement (`tbl;`, which the 2.0 shell runs as `SELECT * FROM tbl`) reads its table.

When no DuckDB 2 answers, `arc run` refuses before any step runs, and a DuckDB 2 whose answer for a file cannot be read refuses that step by name, also before any step runs and before the run's state is set up, so a refused Protocol leaves no run behind. Every question for a step's trees ends with the tree of `SELECT 1`, so a DuckDB that gives tokens and no trees refuses each step that holds a statement as unreadable, with no process of its own; a trees question that could not start or run the DuckDB that just gave the tokens is unreadable too. Outside a run (`arc sql record`, `arc operation record`, the MCP tools), no DuckDB 2 means sqlparser-rs reads the whole graph, with one warning for each cause (the failure and the program, or the version), said again when the same cause outlasts `NOT_STARTED_LIFETIME`, and an unreadable answer draws a per-file warning. A quoted DuckDB error is put on one line in the refusal and the warning that quote it.

The run contract records each statement's `byte_range`, computed from DuckDB's statement split and mapped from the command-line batches back to file bytes (a range that cannot be placed is `null`), and its `read_by`: `duckdb`, `sqlparser`, or `nothing`.

`tests/reader_parity.rs` is the parity gate. It reads every `.sql` file under `tests/fixtures` and `examples` with both readers and compares what each statement produces and reads; each known difference is pinned exactly with its reason, and the test also pins which statements take the sqlparser-rs fallback, so a change in DuckDB's reading or in the fallback shows up as a failure. Known sqlparser-rs gaps, which only the forced and fallback paths see: tables inside `EXISTS` and scalar subqueries; a select list of `COLUMNS(…) AS '…'`, which `join-tables` writes, so that under `ARC_SQL_READER=sqlparser` a recorded join step is not seen reading its tables (`tests/join_tables.rs`'s graph test fails there, and the generated SQL is not changed to suit this reader); and a URL read in SQL: only a bare `FROM '…'` URL comes out of that reader as `source` (a table) rather than `remote`, as sqlparser-rs already read a bare `FROM 'x'`, while reader functions and `COPY` targets come out `remote` (`the_fallback_reader_reads_a_url_as_remote_too`). A step that reads such a URL only by the fallback is therefore not forced stale on every run.

### The operation catalogue

`CATALOGUE` in `src/record.rs` holds the SQL operations arc can record as a step by name: `filter-rows`, `sort-rows`, `hide-column`, `rename-column`, `derive-column`, `cast-column`, `summarise-rows`, `dedupe-rows`, `limit-rows`, `fill-nulls`, `join-tables`, `append-rows` and `read-file`. Each entry is a description and a SQL writer, and nothing that runs: a long name, one sentence, what the step reads and writes by role, a closed JSON Schema of its arguments, and the function that writes the step's model from a recording the schema has admitted. `arc operation list|describe|record` and `arc mcp`'s `operation_list`, `operation_describe` and `operation_record` read the same entries, so an operation added there reaches both with no other edit. Only `filter-rows` has a recogniser, which reads typed SQL back as the operation.

Every table a step reads is a role in the description's `reads`: a name, a kind, one value or a list (with the fewest a list takes), and a sentence. The rule for the catalogue is that an operation's `reads` is empty or its first role is `table`, one value and required; `read-file` has none and starts a branch of the graph. A request names its reads by role in a `reads` map (`--read ROLE=TABLE` on the command line, repeated for a list role, which appends in order; `reads` in `arc mcp`'s `operation_record`), and `on` stays as shorthand for the `table` role, so every request of the first ten is unchanged. `Operation::record` runs three checks on the map before anything is written, after `admit` has checked the arguments. `Operation::admit_reads` refuses a required role with no value, a role the operation does not read, one value for a list or a list for one, a list shorter than its minimum, `on` together with `reads.table`, and any table role on an operation that reads none. The operation's `reads_checks` then runs on the admitted reads (`join-tables` refuses a table joined to itself there), and `made_by_a_step` refuses any table read that no step of the Protocol makes. The `column` role is supplied by where the operation is asked from and is not recorded, so `reads.column` is refused.

A recorded model opens with `-- generated: <operation> on <t1>, <t2>, …`, naming every table the step reads in role order (a list's members in their order, role names left out), and makes the table the step's name names. A single-table operation writes `-- generated: <operation> on <table>` as it always has, and an operation that reads no table writes `-- generated: <operation>` alone. The header is for people: names go in unquoted, so one holding `, ` reads ambiguously, and `sql_is_generated` reads only the marker. A program that needs a step's tables reads the SQL. Most are one `CREATE OR REPLACE TABLE … AS` statement. `rename-column` and `derive-column` are a copy and an `ALTER TABLE … RENAME COLUMN` in one transaction: DuckDB 2.0's `SELECT * RENAME` renames nothing when the column is misspelt, and a select whose new column clashes with an existing one suffixes it `_1`, both without an error, while `ALTER` fails the run and the transaction leaves no table. `derive-column` adds its column as `__arc_derived` before renaming it, so a table already holding that name is not one it can add to. `summarise-rows` groups by position (`GROUP BY 1, …, k`, or `GROUP BY ()` with no grouping) so that DuckDB fails the run on a plain column among the aggregates, which `GROUP BY ALL` would silently group by.

`join-tables` takes a `kind` (`left` by default, `inner`, `right`, `full`, `semi`, `anti` or `cross`) and exactly one of `using` (column names, quoted by arc) or `condition` (a SQL condition naming both tables, probed in its place, `… JOIN <other> ON <condition>`), neither for `cross`. Recording opens no database, so it cannot know which column names clash, and the column rule is fixed instead: `table`'s columns keep their names, every column of `other` comes through prefixed by `prefix` (`<other>_` by default, written into DuckDB's `COLUMNS(…) AS '<prefix>\0'` rename pattern, so its `'` is doubled and a prefix that is empty or holds `\` or a control character is refused; the default has its `\` escaped), and the `using` keys appear once, bare, first. The bare keys come first because `table.*` on a right or full join gives a null key for a row only `other` holds, where DuckDB's own coalesced key is correct. `semi` and `anti` return `table`'s columns alone and take no `prefix`. A prefixed column that clashes with one `table` already has, as when the same lookup is joined twice, is renamed with a `_1` suffix by DuckDB without an error; the way out is another `prefix`. `table` and `other` naming one table is refused, because a self-join needs aliases the condition would have to name, and a repeated `using` key is refused. On the command line `--arg using=a,b` splits on commas, as `typed_arguments` does for any list argument; a name holding a comma is given through `arc mcp`. `append-rows` writes `SELECT * FROM <table> UNION ALL BY NAME SELECT * FROM <other>` for each table in the list: columns match by name, a column one table lacks is null in its rows, duplicates are kept (`dedupe-rows` drops them) and a table repeated in the list stacks twice.

`read-file` takes a `path`, a relative or absolute path, a glob or a URL, written as `FROM '<path>'` so that DuckDB picks the reader from the ending. Recording returns notes with the model path: a list of sentences, `notes` in `arc mcp` and `note: …` lines on standard error from the command line. A path outside the Protocol's folder (absolute, starting with `~`, or leaving it by `..`; a `file://` URL counts here) draws a note that the step works on this machine only, and a remote path draws a note that the data is read live at each run and no copy is kept, and pointing to a snapshot by the fetch operators that reach the scheme: `http_fetch` for `http` and `https`, and `opendal_fetch` only in a build with the `opendal` feature and only for lowercase `http`, `https` and `s3`, each followed by a `read-file` of what it wrote. An `s3://` URL in a build without `opendal` is pointed at that feature, and any other scheme is told that no fetch arc holds reaches it. The other operations record no notes.

String arguments come in three kinds, set by each property's `x-kind`; an argument with no `x-kind`, such as `limit-rows`' integer `count`, is held only to its JSON type and bounds and written as a value. A column (`x-kind: column`) is a name, not SQL: `column_ident` writes it bare where DuckDB reads it bare as that column and quoted otherwise, so it cannot leave the clause it is written into, and only an empty or blank name is refused. A path (`x-kind: path`) is a value, written as a single-quoted literal with `'` doubled, so it cannot leave the literal; it is refused only when empty, blank or holding a control character, and need not exist, since a fetch step may write it later and DuckDB fails the run on a path that matches nothing. Everything else is a SQL fragment written verbatim, so `Operation::admit` checks it with DuckDB's parser before anything is written, in a probe that reproduces what follows the fragment in the step; each probe but a clause's ends in the alias `__arc_probe`:

| `x-kind` | Probe | Holds it to |
|---|---|---|
| `condition`, `order` | `SELECT 1 WHERE <v>` / `SELECT 1 ORDER BY <v>` | one statement |
| `expression` | `SELECT 1, <v> AS __arc_probe` | one item of a bare select, after the probe's own |
| `select-list`, `partition` | `SELECT 1, <v>, 1 AS __arc_probe` | a bare select ending in the sentinel |
| `type` | `SELECT CAST(NULL AS <v>) AS __arc_probe` | one `CAST` of the probe's own `NULL` |

A bare select has no `FROM`, `WHERE`, grouping, `HAVING`, `QUALIFY`, sample, modifier or CTE. A trailing `--` comment swallows the sentinel, a comma list displaces it and a clause that runs on makes the select not bare, so each is refused. The probe's own leading `1,` puts the value after a comma, as each step does, so a leading `ALL`, which DuckDB would read as the probe's `SELECT ALL`, is refused as it fails in the step. A star or `COLUMNS(…)` outside a subquery reads as one item and expands to several columns, and `unnest`, `unlist` and `generate_subscripts` change the number of rows, so the expression and select-list probes refuse them too; a value holding `__arc_probe` itself is refused. Where a fragment's position depends on another argument, an operation-level `checks` hook probes the step's own clause: `dedupe-rows` asks that its key and order read as one `row_number() OVER (PARTITION BY … ORDER BY …)` with the default frame and no constant in either, `limit-rows` that its order leaves the step's `LIMIT` the only limit and offset, and `summarise-rows` that no `group_by` item is a constant, which is the same value for every row and so groups nothing. `admit` also reads `dependentRequired`, `minimum` and `maximum`. The command line passes every `--arg` as a string, so `typed_arguments` turns one into a number where the schema types it `integer` and splits one on commas where it types it `array`; `arc mcp` passes JSON as given. `admit` also reads `enum`, `minItems` and array `items`.

### Asset kinds

`AssetKind` in `src/asset_kind.rs` classifies every name the graph holds: `file` (hashed by its bytes), `directory` (hashed as a manifest of its contents), `pattern` (a glob, never hashed itself), `table` (never hashed; staleness comes from the producing step) and `remote`. A `remote` asset is any `scheme://` URL a step reads or writes, named in the graph by the URL as written, from SQL (`FROM 'https://…'`, `read_csv('s3://…')`, `COPY … TO 's3://…'`) or from a manifest's `depends_on:`, `produces:` or `assets:`; a glob URL is remote, not a pattern. arc cannot read one from disk, so it is never hashed and never checked as missing, and a step that reads or produces one is forced stale on every run, by an explicit check that holds for every kind of step rather than by leaving the asset out of the hash. `file://` counts as remote, because arc does not strip the scheme and so cannot hash the file; forcing the step stale never reports a false "unchanged". The run contract names the kind `remote`, with no path, size or hash, and its version tag is unchanged. `http_fetch`'s `url` is a configuration value, not an asset, since `fetch_cache` already handles its freshness. A follow-up would replace the forced rerun with a conditional check, an ETag or Last-Modified comparison for `https://` and the object's ETag for `s3://`.

### Release and distribution

The package and library are `arcform` and the binary is `arc`. The vendored sqlparser fork is published as its own crate, `arcform-sqlparser`, pinned exactly, because Cargo drops `[patch.crates-io]` on publish. A release binary is built with `mcp,bundled-duckdb`, so it carries DuckDB and starts on a machine with no DuckDB library; SQL steps still run through the `duckdb` command. A pushed `vX.Y.Z` tag builds four targets, publishes the GitHub release with the tag's `CHANGELOG.md` section as its notes, publishes both crates and updates the install script, behind a guard that refuses a tag not matching `Cargo.toml` and the changelog. `docs/RELEASE.md` describes the machinery.

### Agent skills

`skills/` at the repository root holds six agent skills, one folder each, that teach an agent the analyst workflow through arc: `using-arcform` (the entry point: the safety model, where results land, the sizes of a task, the environment check and the full CLI-to-MCP verb map), then one per stage, `scoping-an-analysis`, `profiling-and-typing-data`, `building-and-checking-a-protocol` (Build and Check) and `presenting-findings`, and `dashboard-from-data`, which the entry skill routes to when the user wants to see what is in a dataset rather than ask a question of it. A skill is a `SKILL.md` with YAML frontmatter (`name`, `description`, `metadata.arc_version`) and, where it helps, a `references/` folder; each shows every step both as an `arc` command and as the matching `arc mcp` tool. The workflow outline in `INSTRUCTIONS` (`src/mcp/mod.rs`) names the same stages and skills, and its test fails when the outline names a skill that has no folder. The maintainer's `release` skill is separate, in `.claude/skills/`.

The skills exist so that an agent given a tabular dataset and a question reaches for arc, not a throwaway script, and leaves the analyst a Protocol they can re-run, inspect in Brightfield or share. Their design follows from that:

- **The method is in the skills; the tool stays thin.** A short entry skill routes to one skill per stage, each with a checkpoint where the analyst can redirect, and the work is sized up front (a quick look, an analysis or a project) so the checkpoints scale with it. The skills spend their words on arc's method, checks and traps, not on SQL agents already know. Routing is left to the skills' descriptions and the `arc mcp` instructions; there are no routing hooks.
- **An agent with only `arc mcp` must be able to follow every step.** That includes a desktop chat app with no file access of its own, so every file the workflow produces (a schema, a panel, the project's `README.md`, the report) is written by an arc verb with a matching tool, inside the Protocol folder and recorded in history. The CLI stays canonical: each MCP tool has its CLI verb.
- **arc draws no chart.** A chart is a Mosaic spec the agent writes to `panels/<name>.yaml`, which Brightfield opens and history versions. `arc panel check` checks only that a panel's tables and columns exist; whether Brightfield can draw it is left to the release eval, which opens every panel. A PDF of the report comes from Brightfield too, so arc gains no renderer and stays local-first.
- **The report is a verb, not a step.** It is a snapshot of one session's findings, cited to the run it describes and versioned by history, so a re-run does not rewrite it; the Protocol stays the reproducible record.
- **A skill never describes a different arc from the one running.** `arc skills install` writes the skills embedded in that binary. Channels that serve the repository instead (a plugin, GitHub, a skills directory) can drift from the user's arc, so each skill names the version it was written for and the entry skill's environment check compares it with `arc --version`.

Model training and per-operator recipe skills are outside the set: the modelling the skills teach is what the existing operators do, and the build skill points at the operators and `operator_describe`.

The skills ship inside the binary. `build.rs` embeds every file of each skill folder (a directory under `skills/` holding a `SKILL.md`; hidden files and the maintainer's `skills/README.md` stay out) as `SKILLS` in `$OUT_DIR/skills.rs`, and reruns when `skills/` changes. `arc skills install` (`src/skills.rs`) writes them into each agent whose folder exists under the home directory: Claude Code `~/.claude/skills`, and the shared `~/.agents/skills` for Codex, Cursor and Gemini CLI (when `~/.codex`, `~/.cursor`, `~/.gemini` or `~/.agents` exists), one target per distinct folder. Cursor and Gemini CLI each read their own folder as well as the shared one, so writing both would give them two copies of every skill, and refreshing only their own would leave a stale copy in the shared folder, which Gemini CLI reads first; `--agent` and `--target` name them instead. Each folder written gets a `.arc-skill` marker whose first line is `arc <version>`. Each target is all or nothing as far as refusal goes: every destination in it is checked before any is written; one with the marker is replaced, an absent one is written, and any other is refused, which writes nothing into that target while other targets still install, and the command exits 1. A target that passes has every skill staged in a hidden folder beside its destination before any is swapped in; a swap renames the old folder aside, renames the new one in, then deletes the old one, putting it back if the rename fails, so an error leaves each skill folder one version whole unless the put-back fails too. That case, and a process killed between the two renames, leave no folder and the old one set aside as `.<skill>.arc-old` (a failed put-back's error names it); the next run writes the skill afresh and clears that folder, as it clears any `.arc-old` once a new folder is in place. With no agent found and none named, it prints where each would go and exits 1. `tests/skills_install.rs` drives it with `HOME` set to a temporary folder.

The repository is also a plugin for Claude Code, Codex and Cursor and an extension for Gemini CLI, each bringing the skills and starting `arc mcp` from `PATH`. No agent's format is the source: `scripts/generate-plugins.py` (standard library Python) writes every manifest from `plugin/plugin.meta.json`, with the version from `Cargo.toml`, and `tests/plugin_manifests.rs` runs it into a temporary folder and fails, naming the source file to edit, when a committed manifest differs. The marketplace that Claude Code and Codex read names the plugin at the release tag `v<version>`, not the default branch, so those agents install the newest release's skills; Gemini CLI and Cursor install at the tag the user names. `skills/using-arcform/references/agents/` holds the notes for each agent and for a desktop chat app, which has no plugin route and uploads the skills `arc skills install --target` writes.

`tests/skills.rs` (feature `mcp`) holds the skills to the binary they teach. It checks every MCP tool and argument a skill names against a live `arc mcp` `tools/list`, and every `arc` verb, subcommand and flag against `arc … --help`; requires every row of a CLI and MCP table to fill both columns, an MCP cell naming a tool or saying `None:` and why (the test prints those gaps); checks the frontmatter loads and names this crate's version; and runs each `sh arc-example` block under `set -e` in a fresh copy of a fixture Protocol, matching the `text expect` block after it against the output. An example declares what it needs (`needs=finetype`, `needs=finetype-ext`) and is skipped without it, except that `ARCFORM_REQUIRE_FINETYPE_CLI` and `ARCFORM_REQUIRE_FINETYPE_EXT`, which CI sets, turn a missing CLI or extension into a failure. The notation the checker reads is specified in the module doc at the top of the file. Its fixtures: `tests/fixtures/skills/`, the default Protocol for examples (one step loading a 200-row `sales.csv`, beside an `orders.json`); `tests/fixtures/skills-empty-filter/`, whose filter step leaves an empty table to trace; `tests/fixtures/skills-many-series/`, a year of monthly revenue for twelve stores, for the chart past eight series; and `tests/fixtures/skills-docs/`, test-only skills that exercise the checker itself, `good/` passing every check and `bad/` and `bad_name/` failing each at the line the test asserts.

`tests/finetype_mcp.rs` (feature `mcp`) calls the five FineType tools through `arc mcp` against the real `finetype`, with every property and enum value their `tools/list` schemas advertise; a property with no call, or a call setting one no schema advertises, fails the test. The unit tests in `src/mcp/finetype.rs` use a stand-in that accepts any arguments, so this is the test that catches a flag finetype drops. CI's build job installs the finetype release pinned by `FINETYPE_VERSION` and `FINETYPE_SHA256` in `.github/workflows/ci.yml` and sets `ARCFORM_REQUIRE_FINETYPE_CLI`, under which this test, the CLI tests in `tests/table_profile.rs` and the `needs=finetype` skill examples fail rather than skip when the CLI is missing; `tests/common` resolves the binary as arc does, from `FINETYPE_BIN` or `PATH`, against the floor in `src/finetype_cli.rs`.

The structural test proves a skill names only what arc has, not that an agent picks arc up and follows the method. `eval/analyst-workflow/` is the release test for that: ten analyst tasks on public datasets, across the three sizes, run by hand before each release in Claude Code, Codex and a desktop chat client with only `arc mcp`. A task passes in an agent when the agent chose arc unprompted and ended with the seven outcomes the skills promise; failures are clustered by cause and fixed with the smallest skill edit, and the scored sheet goes in the release pull request. It is not a CI job, because it needs paid agent sessions. Its `README.md` is the runbook.

## Key types

- **`Manifest`** — top-level project config loaded from `arcform.yaml`. Contains `name`, `engine`, `engine_version`, `db`, `steps`, `assets`.
- **`Step`** — a pipeline step. Either `sql` (path to .sql file) or `command` (shell string). Has `produces`, `depends_on`, `preconditions`.
- **`Precondition`** — typed freshness check. Variants: `modified_after` (file age), `fresh` (a fetched artifact's recorded identity vs. the remote), `command` (shell exit code), `tool` (the identity of an external binary or artifact the step did not produce — a reported version or a content hash). AND semantics — all must pass to skip.
- **`AssetOverride`** — manual asset dependency declaration (for command steps; SQL steps auto-discover).

## Execution model

1. Load `arcform.yaml` manifest
2. Build asset dependency graph (SQL introspection + manual overrides); refuse the manifest if two produces:/depends_on: declarations collapse onto one asset by case alone
3. For each step in order:
   - Evaluate preconditions (if any) + SQL/op config hash staleness + produced/read artifact hash staleness
   - Skip if fresh; execute if stale
   - SQL steps: delegate to engine CLI (`duckdb <db> -f <file.sql>`)
   - Command steps: shell execution with real-time stdout streaming
4. Update run state after each step

## Runtime dependencies

- **clap** — CLI argument parsing
- **serde / serde_yaml** — manifest (de)serialization
- **sqlparser** — SQL introspection fallback (the vendored `arcform-sqlparser` fork), for statements DuckDB's reading cannot take or when `ARC_SQL_READER=sqlparser`
- **duckdb** — DuckDB 2.0 Rust bindings (state backend; reads the database the command line writes)
- **semver** — engine version constraint checking
- **sha2** — SQL/op config hashing AND produced/read artifact content hashing, both for staleness detection
- **humantime** — duration parsing for preconditions

## Conventions

- Manifest filename: `arcform.yaml`
- SQL files live alongside the manifest, referenced by relative path
- Engine delegation: SQL runs via `duckdb <db> -f <file.sql>`, with `DUCKDB_AGENT_MODE=0`
- State is persisted in the DuckDB database itself (run metadata tables)
