# Arcform Architecture

Reference doc for Arcform's source layout, key types, execution model, and runtime dependencies. Loaded on demand via the trigger pointer in `CLAUDE.md`.

## Source layout

```
src/
  main.rs         # Entry point
  cli.rs          # Clap CLI definition
  manifest.rs     # YAML manifest parsing (arcform.yaml)
  runner.rs       # Step execution engine (~1150 lines, largest module)
  engine.rs       # SQL engine invocation (DuckDB CLI delegation), the engine range, the extension refusals
  asset.rs        # Assets, SQL auto-discovery, dependency validation, case-collision gate
  duckdb_tokens.rs # A SQL file's tokens, asked of the DuckDB that runs it (`sql_tokenize`); the refusals and the asset graph read these
  duckdb_lineage.rs # What each statement reads and produces, from DuckDB 2.0's tokens and parse trees
  introspect.rs   # SQL introspection: chooses the reader, falls back to sqlparser-rs per statement
  precondition.rs # Typed step preconditions (modified_after, fresh, command, tool)
  state.rs        # Run state tracking (step config hash, artifact hash, staleness)
  inspect.rs      # Read-only look inside a Protocol's database: `arc table describe`, `arc sql query`
  record.rs       # Recording a step: the operation catalogue, its argument gates, `arc operation record`, `arc sql record`
  protocol_files.rs # Writes a Protocol's schemas/, panels/ and README.md, each recorded in its own history: `arc protocol write-file`
  panel_check.rs  # Finds panels that name a table or column the Protocol does not make: `arc panel check`
  report.rs       # Writes report.md from an agent's prose and a run's contract: `arc report write`
  skills.rs       # `arc skills`: lists the agent skills `build.rs` embeds from `skills/`, and installs them into agents' skills folders
  finetype_cli.rs # Runs the `finetype` command and holds its version floor, `MIN_VERSION`; shared by the CLI verbs and the MCP tools
  error.rs        # Error types
  lake/           # Publishing into a DuckLake on object storage (feature `http-fetch`); the `ducklake_write` step is `operator/ducklake_write.rs`
    store.rs      #   The object-store seam: local folder, signed S3, public https; conditional puts
    commit.rs     #   One upserted snapshot of a Protocol's tables, with their `meta` rows
    meta.rs       #   A Frictionless descriptor as `meta.descriptors` and `meta.fields` rows
    publish.rs    #   Fetch, commit, pin, conditional catalogue write and retry; readable copies after
    manifest.rs   #   The compatible `manifest.json`
    rebase.rs     #   `arc lake rebase`: a lake moved onto a new persisted data path
  mcp/            # `arc mcp`: a Model Context Protocol server over stdio (feature `mcp`)
    mod.rs        #   JSON-RPC transport, protocol-version negotiation, the tool registry, each tool's read-only, open-world and destructive annotations
    finetype.rs   #   The five FineType tools, each running the `finetype` command
    hero.rs       #   arc's own tools: protocol_run, protocol_create, the record, edit, history, describe, query, check and report tools
  protocol_test/  # `arc test`: a Protocol run against checked-in fixtures in place of its fetches (see "Protocol tests")
    mod.rs        #   runs each test in tests.yaml order and hands back the results
    spec.rs       #   reads and checks tests.yaml: `ProtocolTest`
    plan.rs       #   which steps a test's fixtures replace, which never run, and the network refusals: `TestPlan`
    fixture.rs    #   places fixtures and applies a break as SQL, writing the file back in its format
    run.rs        #   one test: the copy beside the Protocol, its rewritten manifest, the child `arc run`, the outcome, the control
    report.rs     #   the `ok`/`FAIL` lines and the JUnit XML

runner/           # The hosted runner image: one run of one pinned Protocol (see "The runner image")
  Dockerfile      #   linux/arm64: arc built from this tree, DuckDB's release library and command line, curl, jq, git
  entrypoint.sh   #   exchange the token, fetch the pinned commit, `arc run`, renew, upload the run log
  tests/run.sh    #   the image's acceptance tests, against the stub in tests/stub/
```

### `arc mcp` and `protocol_run`

The MCP stdio transport gives standard output to JSON-RPC alone: one message per line, and any other byte there breaks the client's reading of the stream. A run prints a great deal (step progress, the asset graph, the rows a SQL step's `SELECT` prints on the DuckDB command line, whatever a `command:` step writes), so `protocol_run` does not run the Protocol inside the server. It starts `arc run` as a child process from the server's own executable, in the Protocol's directory, with standard input closed and standard output and standard error piped into a buffer that keeps the last 4,000 bytes. When the child exits, the tool returns the run record it wrote under the Protocol's runs directory; when it wrote none, the tool's error carries the exit status and that tail of output.

`tests/finetype_mcp.rs` (feature `mcp`) calls the five FineType tools through `arc mcp` against the real `finetype`, with every property and enum value their `tools/list` schemas advertise; a property with no call, or a call setting one no schema advertises, fails the test. The unit tests in `src/mcp/finetype.rs` use a stand-in that accepts any arguments, so this is the test that catches a flag finetype drops. CI's build job installs the finetype release pinned by `FINETYPE_VERSION` and `FINETYPE_SHA256` in `.github/workflows/ci.yml` and sets `ARCFORM_REQUIRE_FINETYPE_CLI`, under which this test fails rather than skips when the CLI is missing; `tests/common` resolves the binary as arc does, from `FINETYPE_BIN` or `PATH`, against the floor in `src/mcp/finetype.rs`.

### DuckDB 2.0: the engine, the shared database and agent mode

arc links the DuckDB 2.0 library, the `duckdb` crate at `=1.20000.0` (DuckDB 2.0.0), and runs each SQL step and SQL hook on a DuckDB command line, `ARC_DUCKDB_BIN` or `duckdb` on `PATH`, as `duckdb <db> -f <file.sql>`. It accepts a command line in `>=2.0, <3` (`SUPPORTED_ENGINE_RANGE` and `OLDEST_ENGINE` in `src/engine.rs`). The two must share a major version because they share a file: the command line writes the Protocol's database, and arc opens the same file through the linked library for run state, `arc table describe` and `arc sql query`. A database DuckDB 2.0 creates cannot be opened by DuckDB 1.x, so a 1.x command line is refused as too old even with `ARC_ALLOW_UNTESTED_ENGINE`, and the refusal names arc 0.2.1 as the release for DuckDB 1.5. The variable lifts the range only upwards, to a 2.x pre-release or a 3.x, where a failure to open the file is the user's accepted risk; under it arc also reads the tokens and trees of a DuckDB whose major is above 2 (`duckdb_tokens::tokens_accepted_from`, reading the variable through `engine::untested_engine_allowed` as the engine check does), and below 2 is refused either way.

A development build whose printed source id is the commit of a release's tag counts as that release wherever arc compares versions (its range, a Protocol's `engine_version:`, the extension pin keys, the new-engine notice); the run record keeps the raw string. Homebrew's 2.0.0 prints `v2.0.0-dev88614 (Development Version) d54cbbe3df`, the v2.0.0 tag's commit. The release-tag-to-commit table is `RELEASE_COMMITS` in `src/engine.rs`, and each later 2.x patch needs a row there. Such a build looks community extensions up under its commit hash, which the registry does not serve, so a run of a Protocol that installs one warns before the first step, naming DuckDB's installer for the release build.

arc reads SQL tokens from `sql_tokenize`, which lives in DuckDB's autocomplete extension. DuckDB's release command line links it in; a build without it, such as Homebrew's 2.0.0 at the time of writing, fails to autoload it, so it gives no tokens for any file. `arc run` names that cause rather than refusing the first file: when the pre-run token check fails, or asked DuckDB nothing (no file held SQL yet), it probes `SELECT count(*) FROM sql_tokenize('SELECT 1')` (`duckdb_tokens::tokenizer_failure`, through `Engine::tokenizer_failure`), and a DuckDB that exits with an error there refuses the run with exit 2 before any step (`Error::NoTokenizer`), naming the DuckDB, its printed version and DuckDB's installer pinned to `DUCKDB_RECOMMENDED` in `src/engine.rs`. The message says the build lacks the autocomplete extension only when DuckDB's error names `autocomplete` or `sql_tokenize`; any other error is quoted, with the same fix. A run whose files read starts no extra DuckDB process: the probe adds one only on those two paths. arc probes the capability and never recognises a build by name or path, so a build that adds the extension just works. Outside a run, the one sqlparser-rs warning names the same cause and fix when the same probe fails. `scripts/install.sh` runs that probe on the `duckdb` on `PATH` after installing arc, and installs DuckDB's release build with DuckDB's installer when there is none or it fails (naming a 1.x by its version, since 1.x has no `sql_tokenize` at all), unless `ARC_SKIP_DUCKDB` is set.

Every DuckDB process arc starts goes through `DuckDbProgram::command()`, which sets `DUCKDB_AGENT_MODE=0`. DuckDB 2.0's shell otherwise switches to markdown output, a row cap and a stderr banner when it finds a variable an agent's harness sets (`AI_AGENT`, `CLAUDECODE` and others), and arc would misread its answers and report the banner as a step's error. The environment arc adds for a step holds only `ARC_*` names, so a Protocol cannot turn agent mode back on or change which DuckDB runs it.

`arc run` prints one notice on stderr before the first step when the newest readable run record that names `duckdb_cli` names a different major.minor from the engine about to run; for 1.x to 2.x it also names the four results DuckDB 2.0 changes without an error. It changes no setting.

The bundled build (`bundled-duckdb`) compiles in the DuckDB source `libduckdb-sys` vendors, which names itself a development version; until duckdb-rs fixes that (duckdb/duckdb-rs#917), CI's `bundled` job and the release workflow define `DUCKDB_VERSION` for the C++ compile through `CXXFLAGS`, and `the_linked_duckdb_reports_the_release_version` in `src/engine.rs` asserts the result for every build, bundled or linked. The documented from-source command (README, `scripts/install.sh`) sets the same `CXXFLAGS`; a bare `cargo install --features bundled-duckdb` does not, and reports the development version until then.

One DuckDB version runs throughout: the crate pin in `Cargo.toml`, `DUCKDB_VERSION` in the CI workflows, `DUCKDB_RECOMMENDED` in `scripts/install.sh` and in `src/engine.rs` (the version arc's messages pin DuckDB's installer to) and each entry's `duckdb_versions` in `src/vetted_extensions.json`. `scripts/check_duckdb_version.py`, run in CI's `release-guard` job with its self-test, fails when a pin disagrees with the version Cargo.lock's `libduckdb-sys` decodes to; a vetted entry must include the linked version and may list others. CI's build job also runs the tests that need a real DuckDB, with `--include-ignored`, against the v2.0.0 command line it installs, named by `ARC_DUCKDB_RECORD_BIN`.

### Reading a step's SQL

arc reads each SQL file twice over for two purposes, from one answer: the refusals (which extensions a step installs, which settings it names) and the asset graph (what each statement reads and produces). Both start from the same two layers.

- **The command-line layer is arc's own.** What the DuckDB command line does to a `-f` file before its parser sees it is not something DuckDB will report, so `cli_lines`, `sql_is_complete` and `cli_batches` in `src/engine.rs` copy it from DuckDB v2.0.0's `tools/shell/shell.cpp` and `src/parser/parser.cpp`, each rule citing its source: dot commands and `#` lines, the `0x03` byte, NUL bytes, how lines batch into statements (a backtick counts as a quote in statement completion on 2.0), and the unicode spaces the parser reads as a space.
- **The tokens are DuckDB's.** `src/duckdb_tokens.rs` asks the program the step runs on (never `PATH` when `ARC_DUCKDB_BIN` is set, and never the linked library) for each batch's `sql_tokenize`, one process per file. Each batch is sent hex-encoded, because the command line drops a `\r` before a `\n` in piped standard input, and every token's start is a byte offset into the file arc holds. Answers are cached by the SHA-256 of the file's bytes and shared between the pre-run check, the check just before each step, and the asset graph, so a file read again unchanged is not asked again. A step's whole reading, its trees included, is cached the same way by program and SHA-256 in `duckdb_lineage::read_step`, so the run contract written after the last step reuses the asset graph's reading and starts no DuckDB of its own: a run of three SQL steps starts seven DuckDB processes before its first step (the version, three token questions, three tree questions) and one after its last. A program that could not be started is remembered for `NOT_STARTED_LIFETIME` (30 seconds) in `src/duckdb_tokens.rs`, so a command reading many files with no DuckDB starts none after the first, and a long-lived `arc mcp` started before DuckDB was installed finds it once it is.

The refusals fail closed: a DuckDB that fails, answers in a form arc cannot read, or answers from a version other than 2.x (with `ARC_ALLOW_UNTESTED_ENGINE` set, one before 2) stops the run with exit 2, naming the step or hook. An empty token list (no SQL in the file) is a valid answer and asks nothing. `PARSER_SWITCHES` is `allow_parser_override_extension` and `current_dialect`; `enable_peg_parser` is gone in 2.0. `docs/VETTED_EXTENSIONS.md` is the user-facing statement of what is refused and what is not read.

The asset graph is read by `src/duckdb_lineage.rs` by default: statements split at DuckDB's `;` tokens, then `json_serialize_sql` gives the tree of each query, and what a non-query statement creates, inserts into or copies comes from its tokens. A keyword is matched by its text, never by the token type, which on 2.0 changes with context. sqlparser-rs (the vendored `arcform-sqlparser` fork) reads, per statement, any statement DuckDB gives no tree for; `ARC_SQL_READER=sqlparser` has it read every statement, and any value other than `duckdb` or `sqlparser` is refused. A statement neither reader can read draws a warning and reads nothing; the rest of the step is still read. A bare-name statement (`tbl;`, which the 2.0 shell runs as `SELECT * FROM tbl`) reads its table.

When no DuckDB 2 answers, `arc run` refuses before any step runs, and a DuckDB 2 whose answer for a file cannot be read refuses that step by name, also before any step runs and before the run's state is set up, so a refused Protocol leaves no run behind. Every question for a step's trees ends with the tree of `SELECT 1`, so a DuckDB that gives tokens and no trees refuses each step that holds a statement as unreadable, with no process of its own; a trees question that could not start or run the DuckDB that just gave the tokens is unreadable too. Outside a run (`arc sql record`, `arc operation record`, the MCP tools), no DuckDB 2 means sqlparser-rs reads the whole graph, with one warning for each cause (the failure and the program, or the version), said again when the same cause outlasts `NOT_STARTED_LIFETIME`, and an unreadable answer draws a per-file warning. A quoted DuckDB error is put on one line in the refusal and the warning that quote it.

The run contract records each statement's `byte_range`, computed from DuckDB's statement split and mapped from the command-line batches back to file bytes (a range that cannot be placed is `null`), and its `read_by`: `duckdb`, `sqlparser`, or `nothing`.

`tests/reader_parity.rs` is the parity gate. It reads every `.sql` file under `tests/fixtures` and `examples` with both readers and compares what each statement produces and reads; each known difference is pinned exactly with its reason, and the test also pins which statements take the sqlparser-rs fallback, so a change in DuckDB's reading or in the fallback shows up as a failure. Known sqlparser-rs gaps, which only the forced and fallback paths see: tables inside `EXISTS` and scalar subqueries; a select list of `COLUMNS(…) AS '…'`, which `join-tables` writes, so that under `ARC_SQL_READER=sqlparser` a recorded join step is not seen reading its tables (`tests/join_tables.rs`'s graph test fails there, and the generated SQL is not changed to suit this reader); and a URL read in SQL: only a bare `FROM '…'` URL comes out of that reader as `source` (a table) rather than `remote`, as sqlparser-rs already read a bare `FROM 'x'`, while reader functions and `COPY` targets come out `remote` (`the_fallback_reader_reads_a_url_as_remote_too`). A step that reads such a URL only by the fallback is therefore not forced stale on every run.

### The operation catalogue

`CATALOGUE` in `src/record.rs` holds the SQL operations arc can record as a step by name: `filter-rows`, `sort-rows`, `hide-column`, `rename-column`, `derive-column`, `cast-column`, `summarise-rows`, `dedupe-rows`, `limit-rows`, `fill-nulls`, `join-tables`, `append-rows` and `read-file`. Each entry is a description and a SQL writer, and nothing that runs: a long name, one sentence, what the step reads and writes by role, a closed JSON Schema of its arguments, and the function that writes the step's model from a recording the schema has admitted. `arc operation list|describe|record` and `arc mcp`'s `operation_list`, `operation_describe` and `operation_record` read the same entries, so an operation added there reaches both with no other edit. Only `filter-rows` has a recogniser, which reads typed SQL back as the operation.

Every table a step reads is a role in the description's `reads`: a name, a kind, one value or a list (with the fewest a list takes), and a sentence. The rule for the catalogue is that an operation's `reads` is empty or its first role is `table`, one value and required; `read-file` has none and starts a branch of the graph. A request names its reads by role in a `reads` map (`--read ROLE=TABLE` on the command line, repeated for a list role, which appends in order; `reads` in `arc mcp`'s `operation_record`), and `on` stays as shorthand for the `table` role, so every request of the first ten is unchanged. `Operation::record` runs three checks on the map before anything is written, after `admit` has checked the arguments. `Operation::admit_reads` refuses a required role with no value, a role the operation does not read, one value for a list or a list for one, a list shorter than its minimum, `on` together with `reads.table`, and any table role on an operation that reads none. The operation's `reads_checks` then runs on the admitted reads (`join-tables` refuses a table joined to itself there), and `made_by_a_step` refuses any table read that no step of the Protocol makes. The `column` role is supplied by where the operation is asked from and is not recorded, so `reads.column` is refused.

A recorded model opens with `-- generated: <operation> on <t1>, <t2>, …`, naming every table the step reads in role order (a list's members in their order, role names left out), and makes the table the step's name names. A single-table operation writes `-- generated: <operation> on <table>` as it always has, and an operation that reads no table writes `-- generated: <operation>` alone. The header is for people: names go in unquoted, so one holding `, ` reads ambiguously, and `sql_is_generated` reads only the marker. A program that needs a step's tables reads the SQL. Most are one `CREATE OR REPLACE TABLE … AS` statement. `rename-column` and `derive-column` are a copy and an `ALTER TABLE … RENAME COLUMN` in one transaction: DuckDB 2.0's `SELECT * RENAME` renames nothing when the column is misspelt, and a select whose new column clashes with an existing one suffixes it `_1`, both without an error, while `ALTER` fails the run and the transaction leaves no table. `derive-column` adds its column as `__arc_derived` before renaming it, so a table already holding that name is not one it can add to. `summarise-rows` groups by position (`GROUP BY 1, …, k`, or `GROUP BY ()` with no grouping) so that DuckDB fails the run on a plain column among the aggregates, which `GROUP BY ALL` would silently group by.

`join-tables` takes a `kind` (`left` by default, `inner`, `right`, `full`, `semi`, `anti` or `cross`) and exactly one of `using` (column names, quoted by arc) or `condition` (a SQL condition naming both tables, probed in its place, `… JOIN <other> ON <condition>`), neither for `cross`. Recording opens no database, so it cannot know which column names clash, and the column rule is fixed instead: `table`'s columns keep their names, every column of `other` comes through prefixed by `prefix` (`<other>_` by default, written into DuckDB's `COLUMNS(…) AS '<prefix>\0'` rename pattern, so its `'` is doubled and a prefix that is empty or holds `\` or a control character is refused; the default has its `\` escaped), and the `using` keys appear once, bare, first. The bare keys come first because `table.*` on a right or full join gives a null key for a row only `other` holds, where DuckDB's own coalesced key is correct. `semi` and `anti` return `table`'s columns alone and take no `prefix`. A prefixed column that clashes with one `table` already has, as when the same lookup is joined twice, is renamed with a `_1` suffix by DuckDB without an error; the way out is another `prefix`. `table` and `other` naming one table is refused, because a self-join needs aliases the condition would have to name, and a repeated `using` key is refused. On the command line `--arg using=a,b` splits on commas, as `typed_arguments` does for any list argument; a name holding a comma is given through `arc mcp`. `append-rows` writes `SELECT * FROM <table> UNION ALL BY NAME SELECT * FROM <other>` for each table in the list: columns match by name, a column one table lacks is null in its rows, duplicates are kept (`dedupe-rows` drops them) and a table repeated in the list stacks twice.

`read-file` takes a `path`, a relative or absolute path, a glob or a URL, written as `FROM '<path>'` so that DuckDB picks the reader from the ending. Recording returns notes with the model path: a list of sentences, `notes` in `arc mcp` and `note: …` lines on standard error from the command line. A path outside the Protocol's folder (absolute, starting with `~`, or leaving it by `..`; a `file://` URL counts here) draws a note that the step works on this machine only, and a remote path draws a note that the data is read live at each run and no copy is kept, and pointing to a snapshot by the fetch operators that reach the scheme: `http_fetch` for `http` and `https`, and `opendal_fetch` only in a build with the `opendal` feature and only for lowercase `http`, `https` and `s3`, each followed by a `read-file` of what it wrote. An `s3://` URL in a build without `opendal` is pointed at that feature, and any other scheme is told that no fetch arc holds reaches it. The other operations record no notes.

String arguments come in three kinds, set by each property's `x-kind`; an argument with no `x-kind`, such as `limit-rows`' integer `count`, is held only to its JSON type and bounds and written as a value. A column (`x-kind: column`) is a name, not SQL: `column_ident` writes it bare where DuckDB reads it bare as that column and quoted otherwise, so it cannot leave the clause it is written into, and only an empty or blank name is refused. A path (`x-kind: path`) is a value, written as a single-quoted literal with `'` doubled, so it cannot leave the literal; it is refused only when empty, blank or holding a control character, and need not exist, since a fetch step may write it later and DuckDB fails the run on a path that matches nothing. Everything else is a SQL fragment written verbatim, so `Operation::admit` checks it with DuckDB's parser before anything is written, in a probe that reproduces what follows the fragment in the step; each probe but a clause's ends in the alias `__arc_probe`:

| `x-kind` | Probe | Holds it to |
|---|---|---|
| `condition`, `order` | `SELECT 1 WHERE <v>` / `SELECT 1 ORDER BY <v>` | one statement |
| `expression` | `SELECT 1, <v> AS __arc_probe` | one item of a bare select, after the probe's own |
| `select-list`, `partition` | `SELECT 1, <v>, 1 AS __arc_probe` | a bare select ending in the sentinel |
| `type` | `SELECT CAST(NULL AS <v>) AS __arc_probe` | one `CAST` of the probe's own `NULL` |

A bare select has no `FROM`, `WHERE`, grouping, `HAVING`, `QUALIFY`, sample, modifier or CTE. A trailing `--` comment swallows the sentinel, a comma list displaces it and a clause that runs on makes the select not bare, so each is refused. The probe's own leading `1,` puts the value after a comma, as each step does, so a leading `ALL`, which DuckDB would read as the probe's `SELECT ALL`, is refused as it fails in the step. A star or `COLUMNS(…)` outside a subquery reads as one item and expands to several columns, and `unnest`, `unlist` and `generate_subscripts` change the number of rows, so the expression and select-list probes refuse them too; a value holding `__arc_probe` itself is refused. Where a fragment's position depends on another argument, an operation-level `checks` hook probes the step's own clause: `dedupe-rows` asks that its key and order read as one `row_number() OVER (PARTITION BY … ORDER BY …)` with the default frame and no constant in either, `limit-rows` that its order leaves the step's `LIMIT` the only limit and offset, and `summarise-rows` that no `group_by` item is a constant, which is the same value for every row and so groups nothing. `admit` also reads `dependentRequired`, `minimum` and `maximum`. The command line passes every `--arg` as a string, so `typed_arguments` turns one into a number where the schema types it `integer` and splits one on commas where it types it `array`; `arc mcp` passes JSON as given. `admit` also reads `enum`, `minItems` and array `items`.

### Operator descriptions and READMEs

`arc operation describe <operator>` prints an operator in the shape an operation is printed in, plus two keys of its own: `wraps`, the projects it stands on, and `example`, one step as manifest YAML. Each `wraps` entry has a stable kebab-case `id` (`splink`, `opendal`, `duckdb`, `umap-learn`), a display `name`, the project's `url` and one sentence on what the operator uses it for. Both live in `DESCRIBED` in `src/operator.rs`, beside the summary and roles, and `every_example_step_loads` runs each example through the schema check and the operator's own asset declaration.

Every operator in `DESCRIBED`, the Rust ones included, has `operators/<name>/README.md`, because meridian.online's operation pages link each built operator to its README; for an operator written in Rust the directory holds only the README. Its Reference section, between `<!-- arc:reference:start -->` and `<!-- arc:reference:end -->`, is rendered from the description by `src/operator/reference.rs`: summary, what it wraps, reads and writes, the parameters with their defaults, and the example step. `every_operator_readme_holds_its_generated_reference` fails when a section differs from what the catalogue renders, and `ARC_UPDATE_READMES=1 cargo test --lib operator::reference` rewrites them; prose outside the markers is written by hand and kept. A README names each vendor as a link and carries no logo. The `id` is what a page binds a vendor's mark to, shown beside the operation's shape icon and never in its place, so the marks live with the site and this repository ships none.

An operator is written for many Protocols, so it takes everything particular to one source from its step's `with:` and from the Protocol's SQL: the file and column names, an endpoint and its paging, a dataset's model. `dlt` and `splink` are the shape. `dlt` is given its source in `with:`, and `splink` is given its inputs, its model and its threshold there, with the cleaning before it and the choosing of a best match after it written as the Protocol's own `sql:` steps. An operator that names one source in its inputs, or whose script holds one dataset's columns, endpoints, paging or model, makes a fix to that source an arc release for a change only one Protocol needs. `REVIEW.md` makes this a finding at Medium or above.

### `splink@1`

`splink@1` scores record pairs with a Splink model the Protocol supplies. It reads one or more Parquet files, each given as a `role` and a `path`, and the model, which is Splink's own settings JSON, the file `linker.misc.save_model_to_json` writes. It writes one Parquet file: the table Splink's `predict()` returns, plus the columns the model names in `additional_columns_to_retain`. With two or more inputs the rows are sorted by `source_dataset_l`, `source_dataset_r`, `<uid>_l`, `<uid>_r`; with one, by `<uid>_l`, `<uid>_r`, where `<uid>` is the model's `unique_id_column_name`. The file is therefore the same bytes on a second run over the same inputs. `threshold_match_probability` (at least 0 and below 1) or `threshold_match_weight` sets the prediction threshold; with neither, every blocked pair is written. An input with no rows, or a threshold no pair reaches, writes a file with the full prediction columns and no rows. The README's generated reference lists the keys.

Each input is registered with Splink under a generated table name, never under its role, and the role is the name Splink gives that input's rows in `source_dataset`. Paths are bound as values and never written into SQL.

The script, `operators/splink/splink.py`, is frozen into the binary and run with `uv`, as the other embedded Python operators are. Unlike them, which pin version ranges, it pins `splink==5.0.0`, `duckdb==2.0.0` and `pyarrow==26.0.1` exactly, because its output is published and a parity check against an earlier build of the same crosswalk depends on every dependency staying where it was.

It refuses before Splink starts, exiting 2 with one line per reason. arc refuses some of these at manifest load, before `uv` runs: no inputs; a role that does not match `^[a-z][a-z0-9_]*$` or is given twice; both thresholds set; a match probability outside [0, 1). The script refuses the rest, and the first four again for a step it is run on directly:

- a level other than the null level that lacks `m_probability` or `u_probability`;
- a `link_type` that does not fit the input count (`dedupe_only` takes one input, `link_only` and `link_and_dedupe` at least two);
- inputs whose column names differ, or whose shared columns differ in type;
- an input missing the unique-id column, or a column a comparison level, blocking rule or `additional_columns_to_retain` names (found by reading the SQL text with regular expressions, so unusual SQL can go unseen);
- a custom `source_dataset_column_name` that the inputs do not hold;
- a NULL or duplicate unique id in an input;
- a model that does not parse or is the wrong shape.

Rulings behind it:

- **Generalise first, then fix.** The first crosswalk was built as an operator whose script held its two sources, its columns and its model, so a fix to that model, such as a leading "THE" that costs some companies their match, would have shipped as an arc release though only one Protocol cares. The operator is made general first and the fix follows as an ordinary change to that Protocol.
- **The model is the Protocol's, in Splink's own JSON.** A model trained or charted in a notebook is used unchanged and Splink's documentation describes every field. Cleaning, column mapping and blocking keys are `sql:` steps before the operator, and the choice of a best match, the tie-breaks and the statuses are a `sql:` step after it, so arc's SQL reader sees each of them and each can be tested with `arc test`.
- **Prediction only, in this version.** The operator never trains and never clusters. A run that estimated parameters would not be reproducible, so every non-null level carries both probabilities and the frozen model is checked into the Protocol. The crosswalk picks one best edge per row, which Splink's clustering does not express. Either can be added later as a minor version.
- **Splink 5, unless the crosswalk's parity check shows a changed value.** Splink's current documentation is for Splink 5. If it changes any published value on the same inputs, the operator pins 4.0.17 instead and the move to 5 becomes its own change.
- **The operator rule is enforced in review**, as above.
- **`splink_resolve` stays** in the catalogue until the crosswalk Protocol no longer uses it.

### Asset kinds

`AssetKind` in `src/asset_kind.rs` classifies every name the graph holds: `file` (hashed by its bytes), `directory` (hashed as a manifest of its contents), `pattern` (a glob, never hashed itself), `table` (never hashed; staleness comes from the producing step) and `remote`. A `remote` asset is any `scheme://` URL a step reads or writes, named in the graph by the URL as written, from SQL (`FROM 'https://…'`, `read_csv('s3://…')`, `COPY … TO 's3://…'`) or from a manifest's `depends_on:`, `produces:` or `assets:`; a glob URL is remote, not a pattern. arc cannot read one from disk, so it is never hashed and never checked as missing, and a step that reads or produces one is forced stale on every run, by an explicit check that holds for every kind of step rather than by leaving the asset out of the hash. `file://` counts as remote, because arc does not strip the scheme and so cannot hash the file; forcing the step stale never reports a false "unchanged". The run contract names the kind `remote`, with no path, size or hash, and its version tag is unchanged. `http_fetch`'s `url` is a configuration value, not an asset, since `fetch_cache` already handles its freshness. A follow-up would replace the forced rerun with a conditional check, an ETag or Last-Modified comparison for `https://` and the object's ETag for `s3://`.

### Declared outputs

A Protocol names the finished files it leaves for publishing in an optional top-level `outputs:` list in `arcform.yaml`, each a path relative to the Protocol's folder, a file or a directory:

```yaml
outputs:
  - build/gleif.parquet
  - datapackage.json
```

Load refuses an absolute path, a `..`, `.` or empty component, a duplicate (a trailing `/` is dropped first), an output inside another declared output, whose files would otherwise be recorded and uploaded twice, `build` itself and anything under `build/.arcform/`, which holds arc's run state (`validate_outputs` in `src/manifest.rs`). After the last step of a run that would otherwise succeed, and before the hooks, arc checks each output is there and is a regular file or a directory holding only regular files and directories; anything else, a symlink at any depth among them (a folder on the declared path included), fails the run with a failed step's exit code, naming the path, so `on_failure` runs and `on_success` does not (`contract::list_outputs`). After the last hook arc hashes them, so the record holds each file as the run left it, and an output a hook removed fails the run there.

The run record (`build/.arcform/runs/<run_id>.json`) carries `outputs`: one entry per declared path, in manifest order, with `path` (without a trailing `/`), `kind` (`file` or `directory`) and `files`, each `{path, bytes, sha256}` relative to the Protocol. A file output lists itself; a directory lists every file under it, sorted by the bytes of their paths. A failed run records an empty list. The field was added under `b4/1` with `#[serde(default)]`, so a record written before it reads with the list empty. Beyond the check and the record, `outputs:` changes nothing about a local run.

The runner image uploads exactly the files this list names (see "The runner image"), which is why the declaration lives in arc rather than in the runner. The rulings behind it, from the design approved on 2026-11-13:

- **The Protocol declares its outputs; arc checks and records them, and the runner reads the record, never `arcform.yaml`.** Two alternatives were rejected. Uploading every file the record says a run produced would ship raw downloads (GLEIF's is about 470 MB) beside the dataset, and only finished outputs should leave a hosted run, since every byte out of AWS is charged and counts against a subscriber's allowance. Uploading what `datapackage.json` lists does not work because the open datasets' descriptors give each resource's published URL as its `path`, not the file in the build, and a Protocol without a descriptor would upload nothing. A fixed `outputs/` folder by convention was dropped because nothing would check it, and the open datasets' publish already reads `build/<name>.parquet` and `datapackage.json` where they are.
- **A missing declared output fails the run in arc itself, locally too**, so a Protocol that stops writing an output is caught before a hosted run uploads an incomplete set.

### Checks and measures

A Protocol asks questions of its own data with two step kinds beside `sql:`, `op:` and `command:`. A check is one SQL query that returns the rows that are wrong, and passes when it returns none. A measure is one SQL query that returns one row of named numbers, recorded in every run so later checks, in this run and in later ones, can compare against it. Both are steps in `arcform.yaml`, so a reader of the manifest sees every check and where it runs (`src/check.rs`, and the check and measure arms of the step loop in `src/runner.rs`):

```yaml
steps:
  - name: load
    sql: models/load.sql
  - name: size
    measure: measures/size.sql          # SELECT count(*) AS codes FROM codes
  - name: unique
    check: checks/unique.sql            # SELECT code FROM codes GROUP BY code HAVING count(*) > 1
    risk: a duplicated code publishes two meanings for one key
    severity: warn                      # optional; error by default
measure_history: { runs: 30 }           # the default; or { since: 90d }
check_samples: false                    # optional; keep samples out of the published record
```

**What a check does.** `risk:` is required: one line saying what would go wrong in published data without the check, which every failure leads with. A check that returns no rows succeeds. One that returns rows with `severity: error` (the default) fails its step with `check '<name>' failed: <risk> (<n> rows returned)`, and the run stops as it does for any failed step: exit code 2, every later step left unreached, `on_failure` and `on_exit` given `ARC_FAILED_STEP=<check>` and `ARC_EXIT_CODE=check`. A failed error check is not retried, since the same data gives the same rows. One that returns rows with `severity: warn` leaves its step succeeded, prints `warning: check '<name>' found <n> rows: <risk>` on stderr, and the run carries on and can finish green. A check whose SQL fails to run (a missing table, a type error) fails its step whatever its severity, and is retried as `retry:` says.

**What a measure does.** Its query returns exactly one row, and every column is a number: an integer of any width, signed or not, `FLOAT`, `DOUBLE` or `DECIMAL`. Each column becomes a measure named `<step>.<column>`, recorded as a double; SQL `NULL` is recorded as JSON `null`, and an infinity or NaN is refused. A column name may not contain `.`. Anything else fails the step, naming the column and the rule. DuckDB renames duplicate column names as it stores the rows (`SELECT 1 AS a, 2 AS a` gives `a` and `a_1`), so such a query records `<step>.a` and `<step>.a_1`; give each column its own name.

**Refused before any step runs.** A check or measure file holds exactly one query, read by the same reader as every SQL step (see "Reading a step's SQL"): two statements, or one that is not a query (a `CREATE`, an `INSERT`), is refused naming the step. A statement-level `PIVOT` counts as one query. `check:` and `measure:` steps refuse `produces:`, `output:` and `preconditions:`, and take `depends_on:`, `retry:`, `timeout_sec:` and `description:`; `risk:` and `severity:` are refused on any other step. A step name may not contain `:`. In a Protocol that declares a check or measure step, no step may produce a table named `measures` or `measure_history` (in any case); a Protocol with neither keeps any table name. Checks and measures are never skipped as fresh, and what they read is in the asset graph like any step's reads, so a checked table lists its checks in `consumed_by`.

**The ordering rule** (`check::refuse_publish_before_error_check`). A step whose operator publishes (`Operator::publishes`: `ducklake_write` and `ducklake_publish`) may not come before an `error` check that reads any table or file the publishing step reads, or any asset upstream of one in the graph. A check on `codes` therefore guards a publish of `build/codes.parquet` that an earlier `COPY codes TO …` wrote. The refusal names both steps and the asset, and says to move the check before the publish or make it `severity: warn`. A `warn` check may come anywhere, since it stops nothing. The rule sees only graph assets, and `measures` and `measure_history` are not graph assets, so a comparison check that reads only them is not seen by it: place such an `error` check before the publish yourself.

**The wrapper.** A check's or measure's SQL is Protocol SQL, so it runs on the DuckDB command line through `Engine::execute_sql`, as every SQL step does, and never through the linked library. arc cannot ask the command line for a query's rows directly, so it makes an answer directory of its own under the system's temporary directory (`AnswerDir` in `src/engine.rs`, a fresh directory per query, removed afterwards) and writes three files there: `measures.json`, `history.json` and a generated `wrapper.sql`. The wrapper creates `measures` and `measure_history` as temporary tables from the two JSON files, keeps the query's rows in a temporary table `__arc_rows`, and copies one answer row to `answer.json` with `COPY … (FORMAT json)`, which arc reads back. Temporary tables leave nothing in the Protocol's database. A check's answer is the row count, the column names and the first 20 rows, each cell cast to `VARCHAR` and cut to 201 characters in SQL (`left(COLUMNS(*)::VARCHAR, 201)`, packed into one list per row with `[*COLUMNS(*)]`), which arc then cuts to 200 characters followed by `…`. The cut happens in SQL so a huge value is never written out whole, and one character past the cap tells arc which cells to mark. The cast comes before the packing because `[*COLUMNS(*)]` builds a list only when every column has one type, while DuckDB 2.0 expands `[COLUMNS(*)::VARCHAR]` into one single-element list per column. A measure's answer is the row count, each column's name and type from `DESCRIBE`, and the first row's values cast with `TRY_CAST` to `DOUBLE` and then to text, so an infinity or NaN reaches arc to be refused rather than breaking the JSON. The query sits in the wrapper below as many blank lines as precede it in its file, so the `LINE n` in a DuckDB error is line n of the check's own file. A check's parameters reach it as `ARC_PARAM_*` variables, as a SQL step's do.

**Built-in measures.** Each step that produces a table, as the asset graph has it, has that table measured as soon as the step has succeeded and its process has exited (a failed step records no measures): arc opens the database once more, read-only, with the linked library, and records `table:<t>.row_count` (`count(*)`) and `table:<t>.bytes` in the step's own entry. `bytes` is the number of distinct storage blocks the table's columns occupy (`block_id` and `additional_block_ids` from `pragma_storage_info`, each `>= 0`) times the database's `block_size` from `pragma_database_size()`. It is coarse, since two tables sharing a block both count it, but stable and DuckDB's own account. It is not the `bytes` on a table's asset entry at the end of the run, an older figure from `duckdb_tables().estimated_size`. A table that cannot be measured (a name that is not a simple identifier, a view, a table since dropped) records nothing and is not an error. A step skipped as fresh is measured too when the run reaches it, so history has no gap on a run where nothing changed. The `table:` prefix keeps these apart from a measure step's names, which is why a step name may not contain `:`. This adds one database open to every table-producing step.

**`measures` and `measure_history`.** A check or measure can read two tables arc stands up for it. `measures (name, value)` holds this run's measures so far, measure steps' and built-in alike, one row per name; when two steps produce one table, the later measurement wins, while each step's entry keeps its own values. `measure_history (run_id, run_at, name, value)` holds earlier runs' measures, oldest first, read once before the first step from the run records in `build/.arcform/runs/`. It keeps a record only when its outcome is `success` (a run with warnings is a success), it ran with the same parameters as this run (the same keys with the same values, in any order and whatever supplied them), and it recorded at least one measure. `run_at` is the run's `started_at`. The window is `measure_history: { runs: N }`, the newest N such runs (30 by default), or `measure_history: { since: <duration> }` (`90d`, `12h`), the runs started within that span; exactly one of the two. A parameter value recorded redacted (`***REDACTED***` for a secret-looking key, `[redacted]` for a dotenv value in the published copy) matches any value, because the record no longer says what it was, and a record restored from the published copy would otherwise never match its own run again. A Protocol's first run gets an empty `measure_history`, so a comparison over it returns no rows and passes. Neither table is a graph asset, so a check reading them depends on nothing in the graph through them. A comparison is an ordinary check:

```sql
SELECT name FROM measures m JOIN (
  SELECT name, last(value ORDER BY run_at, run_id) AS prev FROM measure_history GROUP BY name
) p USING (name)
WHERE m.value < p.prev * 0.5;
```

**The record under `b5/1`.** `contract_version` is `b5/1` (`CONTRACT_VERSION` in `src/contract.rs`). A check step's entry gains a `check` section (`CheckSection`): `name`, `risk`, `severity` (`error` or `warn`), `success`, `rows_returned`, `sample` (at most 20 rows, each cell text or `null`) and `sample_columns`, and `error` only when the query did not run, in which case `success` is false, `rows_returned` 0 and the sample empty. The field names `name`, `success` and `severity` follow OpenLineage's data-quality assertions facet. A measure step's entry, and every table-producing step's entry, gains a `measure` section (`MeasureSection`), `{"values": {"<name>": <number or null>}}`: a measure step's columns in query order, then each produced table's `row_count` and `bytes` in table-name order. `run.checks` (`ChecksSummary`) counts `passed`, `warned` and `failed`; a check that failed to run counts as failed whatever its severity. Every new field reads with a default, so a `b4/1` record still reads, with no sections and a zero summary. The published copy of a record goes through the same scrubbing and secret refusal as the rest of it (see "Publishing into a lake"), samples included, and `check_samples: false` empties every `sample` in that copy while keeping `sample_columns` and `rows_returned`; the record on disk keeps its samples. A check's `error` is DuckDB's own message, which can quote the value it failed on, so the published copy always replaces it with `the check's query did not run; the local run record holds DuckDB's message`, whatever `check_samples` says.

**Rulings and their reasons.** The design chose checks and measures as steps over checks hanging off the step they check (which must file a check across several tables under one of them) and over a convention folder that runs every file as soon as its tables exist (which a reader of `arcform.yaml` cannot see). The calls made while building it:

- *The contract tag is `b5/1`*, and every new field defaults on read, so records written before checks existed still read, and so does history built from them.
- *A sample keeps 20 rows, each cell cut to 200 characters with a trailing `…`*, with SQL `NULL` kept as JSON `null`. Twenty rows are enough for a person to see the pattern of a failure, and the cut keeps a stray blob from swelling a record that may be published.
- *Built-in measures live in the producing step's own entry, as a `measure` section of the same shape a measure step has*, so `measure_history` reads one shape from every step. A step skipped as fresh is still measured, so history has no holes on runs where nothing changed.
- *`table:<t>.bytes` is storage blocks times block size.* `duckdb_tables().estimated_size` is a row estimate, not bytes; the block count is coarse but stable and DuckDB's own. `row_count` is `count(*)`. A table arc cannot measure records nothing rather than failing the run, since a measure no one asked for should never break a Protocol.
- *A check or measure whose SQL fails to run fails its step, whatever its severity.* A broken warn check is a broken Protocol, not a warning, and passing it over would let a check that no longer runs look like one that passes.
- *A measure whose value is SQL `NULL` is recorded as `null`*, and appears in `measures` with a `NULL` value, rather than being refused: a ratio over no rows is a real answer, and a check can test for it.
- *The ordering rule reaches through the graph.* An error check after a publish is refused when anything it reads is something the publish reads or an ancestor of one, because a publish usually reads a file an export wrote from the checked table, not the table itself.
- *`measures` and `measure_history` are reserved only in a Protocol that declares a check or measure step*, where a table of either name would hide arc's own. A Protocol without checks keeps any table name, so an existing Protocol with a `measures` table, such as the `brewtrend` example, still loads.
- *Step names may not contain `:`*, which the `table:` prefix relies on to keep built-in measure names from colliding with a step's.
- *A failed error check exits 2, as a failed step does.* Distinct exit codes for failed checks and for warnings belong to the work on telling the analyst, which should settle them all together.
- *Check and measure steps refuse `produces:`, `output:` and `preconditions:`*, since they produce nothing and are never skipped, and `risk:` and `severity:` are refused on any other step, so a misplaced line is caught rather than ignored.
- *History compares like with like.* `measure_history` keeps only earlier runs whose recorded parameters, key and value, equal this run's, so a run for another release is not a baseline. Where a value came from (default, dotenv, command line) does not matter, only what it was.
- *A check that fails to run counts as failed in `run.checks`*, with its section's `error` set, so the summary never reports a broken check as passing or as a warning.
- *A measure column name may not contain `.`*, so each `<step>.<column>` name maps back to one step and one column.
- *`measures` and `measure_history` are not graph assets.* No step makes them, so a dependency on them could never be satisfied; a check's reads of them are left out of the graph.
- *`measure_history: { runs: N }` counts earlier runs that recorded measures*, so records written before this change, which hold none, do not push useful baselines out of the window.
- *When two steps produce one table, the latest measurement wins in `measures`*, one row per name, so a comparison sees the table as it now stands; each step's entry keeps what it measured.

### Protocol tests

`arc test` runs a Protocol against checked-in fixture files in place of what its fetches would download, and asserts either that the run succeeds with every check passing or that it fails with a given message. The tests live in one file per Protocol, `tests.yaml` beside `arcform.yaml`, so a loader's refusals (a moved header, a mark it does not know) can be shown to fire without the source ever sending a bad file (`src/protocol_test/`, and the `Commands::Test` arm of `src/cli.rs`):

```yaml
- name: a moved definitions header is refused
  risk: the issuer moves the header row and titles load into the wrong columns
  fixtures:
    fetch_definitions: testdata/definitions.xlsx
  break:
    fetch_definitions: UPDATE fixture SET B = 'Code' WHERE row = 8
  expect:
    fails_with: definitions header row has moved

- name: every parent code exists
  risk: an orphaned code publishes a broken hierarchy
  fixtures:
    fetch_definitions: testdata/definitions.xlsx
  checks:
    - SELECT code FROM codes WHERE parent IS NOT NULL AND parent NOT IN (SELECT code FROM codes)
  params:
    release: "2018"
  measure_history: testdata/history.csv   # optional: run_id,run_at,name,value
```

**What a test says.** `name:` and `risk:` are required; `risk:` is one line saying what would go wrong in published data without the test, and leads its failure. `fixtures:` maps a step to a checked-in file, relative to the Protocol's folder, that stands in for what the step writes; the step does not run. A key is a step's name when that step writes exactly one file, or else an output path, and a step whose outputs are keyed by path must have every file it writes keyed. `break:` maps a fixture key to one SQL statement or a list of them. `expect: { fails_with: <text> }` asserts the run fails with a message containing the text; with no `expect:`, the test asserts the run succeeds, which means every `error` check in the Protocol passes, and every query under `checks:` returns no rows. `checks:` are inline queries of the same failing-rows shape as a check step. `params:` overrides the Protocol's parameters, a number or boolean read as its text. `measure_history:` names a CSV that stands in for earlier runs' measures.

**How one runs** (`protocol_test::run`). Each test gets a fresh copy of the Protocol, a hidden sibling folder `.<folder>.arc-test-<random>` in the Protocol's parent, holding everything in the folder except `build/` and the database `db:` names with its `.wal`; a symbolic link is copied as a link. The copy's `arcform.yaml` is rewritten as a YAML value, every other key kept: the fixtured steps and every publishing step (`Operator::publishes`) are taken out, each inline check is appended as a `check:` step named `arc-test-check-<n>` (from 1) with `severity: error` and the test's risk, and `db:` becomes `build/arc-test.duckdb` unless it names a path that stays inside the copy. The fixtures are copied into place, each break is applied, and arc spawns itself as `arc run --force` in the copy, with one `--param` per test parameter, standard input closed, standard output dropped, `NO_COLOR=1`, `ARC_PUBLISH` cleared, and two variables that are `arc test`'s own: `ARC_TEST_ERROR_FILE`, a file in the copy to which a failing `arc` writes its error, and `ARC_TEST_MEASURE_HISTORY`, the test's `measure_history:` CSV, which the runner then reads as `measure_history` in place of its run records, every row as given, with no window or parameter filter. The outcome comes from the child's exit status, that error file and the copy's run record, which says which inline check returned rows. The copy is removed on every return path. Each test copies the whole Protocol folder, apart from `build/` and the database, and a break test with a control copies it twice, so a large folder the Protocol does not need (downloads, notebooks, old outputs) belongs outside it. Tests run one after another in file order; `arc test <name>` runs one.

**Breaks** (`protocol_test::fixture`). A break is Protocol SQL, run on the Protocol's DuckDB command line against a scratch database in the copy, after the same extension refusals a step's file goes through. arc reads the placed fixture into a table named `fixture`, runs the statements, and writes the table back in the format it came in, over the placed file. Each statement is trimmed and terminated with `;` on a line of its own when it has none, and the statements are joined in order. For `.xlsx`, `fixture` has a `row` column numbering the rows from 1 and one text column per sheet letter (`A`, `B`, …), read with `header = false`, `all_varchar = true` and `stop_at_empty = false` over `A1` to the used range's last cell under `SET threads = 1`, and written back `ORDER BY row` with no header under the same sheet name. `row` orders the rows and is not a cell address, so the shift-and-insert idiom `UPDATE fixture SET row = row + 1 WHERE row >= 5; INSERT INTO fixture (row, A) VALUES (5, 'x')` puts a new row fifth. For `.csv` and `.tsv`, every column is read as text with the delimiter, quote, escape, line ending and header DuckDB's `sniff_csv` finds, and written back with the same. For `.json`, an array stays an array and one object per line stays so, with date and timestamp detection off. A control runs too: a test that expects a failure and has a break is run a second time, in a fresh copy, with each broken fixture rewritten through the same round trip and no statements.

**What a test reports.** A passing test prints `ok <name>`. A failing one prints `FAIL <name>`, then `  risk: <risk>`, then what happened, each line indented two spaces, one of:

- `expected the run to fail with "<text>"; it succeeded`
- `expected the run to fail with "<text>"; it failed with: <message>`
- `expected the run to succeed; it failed with: <message>`
- `check <n> returned <k> rows: <query>`, then up to five of its sample rows, cells joined with ` | `
- `the control run, with the fixtures rewritten and no break, also failed with "<text>", so the failure does not come from the break`
- a refusal, below.

The last line is `<n> passed, <m> failed`. `arc test --junit <file>` also writes JUnit XML: one `testsuite` named for the Protocol, a `testcase` per test with its time, and for a failure a `failure` whose `message` is `risk: <risk>` and whose body is what happened; characters XML cannot hold are replaced with U+FFFD. `arc test` exits 1 when any test fails, displaying `<m> of <n> tests failed`.

**Refused before any test runs**, exit 1, each message beginning `tests.yaml: `: a missing or unparseable file, an unknown key (a misspelt `brake:` is named), a test with an empty name, two tests with one name (`two tests are named '<name>'`), and per test (`test '<name>': …`) a missing `risk:`, a fixture or `measure_history` file that does not exist, a `break:` key with no fixture of that name or with only empty statements, `checks:` together with `expect:`, an empty `fails_with:`, and a parameter that is not a string, number or boolean. `arc test <name>` with a name no test has lists the tests.

**Refused tests.** A test that cannot be run as written is a failing test, reported with its risk and the refusal, and the rest still run:

- `step '<s>' fetches data (<operator>) and the test gives it no fixture; add one under fixtures:` for an ingress step (`Operator::ingress`: `http_fetch`, `html_link_discover`, `gleif_ra_fetch`, `opendal_fetch`) left without one.
- `<who> reads <url>, which a test cannot reach; read it through a fetch step and give that a fixture`, and `<who> writes <url>, which a test must not reach`, where `<who>` is `step '<s>'` for a `sql:`, `check:` or `measure:` step, `hook '<slot>'` for a `sql:` hook, or `the break of <key>`.
- `fixture '<key>' lands at <dest>, outside the Protocol's folder; a test writes only inside its copy`, and `<who> writes <path>, outside the Protocol's folder, which a test must not change`, for a fixture whose output path, or a file, folder or pattern that a kept `sql:`, `check:`, `measure:` or `op:` step, a `sql:` hook or a break writes, that is absolute or climbs above the folder with `..` (each `.` dropped and each `..` taking back the name before it, so `models/../out.csv` is inside). Reading through `..` is allowed. The same refusals are made again in the copy, before any fixture is placed, for a path that leads out through a copied link: the deepest part of it that exists is resolved, links and all, and must lie inside the copy.
- A fixture key that is neither a step nor a file a step writes; a step keyed by name that writes no file, or several (`key a fixture by each output path instead`); a step with some of its files fixtured and not others; a fixture for a step that makes a table, or for a publishing step; two fixtures for one file.
- A break arc cannot round-trip, each saying to check in a second fixture with the change made instead: a file that is not `.xlsx`, `.csv`, `.tsv`, `.json`, `.jsonl` or `.ndjson` (in any case); a workbook with more than one sheet; a CSV with lines above its header, which DuckDB skips; a CSV whose header DuckDB would rename (a blank, repeated or padded name). A break that installs an extension arc has not vetted is refused as a step's file would be, and one whose SQL fails is `the break of <fixture> did not run: <DuckDB's message>`.

**What `fails_with:` matches.** The text arc's own final error holds: what the child wrote to `ARC_TEST_ERROR_FILE`, colour codes stripped and DuckDB's echo of the failing SQL (each `LINE n: …` line and the caret line under it) removed. A child that wrote no file, one that crashed, is read from its standard error instead, from the last line beginning `error: `. For a failed `command:` step or `op:` step that runs a process (`uv`, `splink_resolve`), arc's error is `step '<s>' failed (exit code <n>):` followed by the last 20 lines with text on them of that step's own standard error, so `fails_with:` matches a script's own refusal and a refusal test fails when the script crashed with something else, a traceback the break caused for one. The step's standard error still streams to the terminal as it runs: arc reads it through a pipe, writes it on, and keeps the last 64 KiB. A step whose process left a child holding the pipe open is waited on for two seconds after it exits, and only when it failed.

**Acceptance.** A copy of a real 2018 occupational code-list Protocol, with three statistical-agency workbooks as fixtures for its three fetch steps, passed nine tests: one pass case carrying twenty inline checks (parents, levels and depths, ancestors, release, staging and illustrative-example counts, the shared title and crosswalk contracts), one break that still passes, and seven refusal breaks, among them a moved definitions header and an illustrative-example mark the loader does not know. The JUnit file listed each test.

**Rulings and their reasons.** The design chose fixtures in place of fetches, breaks as SQL over the fixture and a control for every break over hand-faked steps and checked-in broken copies of every file, which is what the earlier Python harnesses had to do. The calls made while building it:

- *A test never reaches the network for data.* An ingress step needs a fixture, and any SQL arc runs in the test (a step, a check, a measure, a `sql:` hook, a break) that reads or writes a URL refuses it. (`plan_test` would also refuse an `op:` hook that fetches, which has no output a fixture could stand in for, but the manifest loader refuses every `op:` hook, so that branch is only a guard.) Writing is refused as well as reading, so a test never sends a file anywhere. `command:` and `uv` steps run as written, since those are what tests most need to exercise; a tool such as `uv` may still download what it needs, a script that fetches by itself is not seen, and such a step runs with the environment `arc test` was given, credentials included.
- *A test writes only inside its copy.* The copy is a sibling, so a path above the folder or through a copied link reaches the user's real file, and a test once overwrote one. A fixture landing there, or a path a step arc runs writes there, refuses the test, at plan time as written and again in the copy through links. A `command:` step that writes outside the folder still does: arc cannot see what a script writes, only what it declares. So does a SQL step that writes somewhere its introspection does not see, such as a database it `ATTACH`es (`ATTACH '../x.duckdb'` and a write into it changes that file): the check covers only the outputs arc reads from the SQL, the files and folders a `COPY … TO` or reader names.
- *Publishing steps never run in a test.* A test must not change a published lake; `ARC_PUBLISH` is cleared in the child for the same reason.
- *The copy sits beside the Protocol, not in the system's temporary directory.* A Protocol reaches shared files with `..` (a script or contract two folders up), and a sibling at the same depth resolves every such path to the same file without arc having to find them. Its name starts with `.` and holds `arc-test`, so an `arc test` killed before it could remove one leaves a folder that is plainly safe to delete.
- *The copy leaves out `build/` and the database*, so each test starts with no state and no earlier run records, and `arc run --force` runs every step.
- *The copy's database is its own.* `db:` is kept only when it resolves inside the copy, and is then written with each `.` dropped and each `..` resolved, the same path the copy left out with its `.wal`, so `models/../data.duckdb` never brings the user's `data.duckdb` along; absent, null, absolute, reaching above the folder with `..`, or through a linked folder that leads out of it, it becomes `build/arc-test.duckdb`, so a test never touches the user's database or one in arc's data folder. A `command:` step that hard-codes a database path outside the folder still reaches it.
- *The child is `arc run`, not the runner in-process.* Each test gets a fresh process, `arc test`'s own output stays one line per test, and the outcome is read from the same record and exit status a user sees.
- *Fixtured steps are removed, not stubbed.* `depends_on:` names assets, not steps, so a removed step leaves the files it would have written as plain source files, which the fixtures are. A fixture stands in for a file, so a step that makes a table cannot have one.
- *Inline checks become real check steps*, appended after the Protocol's own, so the runner refuses a query that is not exactly one, gives it `measures` and `measure_history`, and records it, as for any check. `checks:` with `expect:` is refused because a run expected to fail never reaches them.
- *`fails_with:` matches arc's own final error, written to a file.* Reading standard error matched the wrong thing twice in review: DuckDB echoes the failing SQL, `error('…')` message included, so a message could match text that was never raised; and a step's own output can hold a line starting `error: `. `ARC_TEST_ERROR_FILE` gives the exact text; standard error is only the fallback for a child that crashed. A failed `command:` or process-running `op:` step's error carries the end of its own standard error, as a SQL step's carries DuckDB's, so a refusal raised inside a script is matched there and not in the run's standard error as a whole.
- *A control runs for every break that expects a failure.* Agents and people will not remember to write one, and it proves the refusal comes from the break, not from the round trip or from a message the Protocol prints whatever the data. A break test that expects success has nothing for a control to rule out.
- *A break writes the file back as it was, or is refused.* A refusal test against a different file proves nothing, so the round trip keeps what a loader can see: a CSV's delimiter, quote, escape, line ending and header; a JSON file's array or line form, with dates and timestamps kept as the text they were rather than shifted into the machine's time zone; a workbook's cells and blank rows. A CSV with lines above its header, or a header DuckDB would rename, would come back different, so it is refused. A workbook drops trailing empty rows, which a used range past the data would otherwise write back as rows of empty cells, and a stale `<dimension>` is widened to the furthest cell; so a break that blanks a workbook's last row removes that row. A JSON break keeps every value as its text, but not which keys each object had (a key missing from one object comes back as `null`) nor how a number was written (`1.50` may come back as `1.5`). Formatting and cell types are not kept: every cell comes back as text, which a loader reading `all_varchar = true` cannot tell apart. A workbook of several sheets is refused because DuckDB's writer writes one.
- *Each break statement is terminated on its own line*, so a trailing `-- comment` cannot swallow the `;`.
- *Break SQL is Protocol SQL*, run on the Protocol's DuckDB command line after the same extension refusals, so a break cannot do what a step could not.
- *`measure_history:` replaces the run records wholesale*, rows taken as given, so a test can show a comparison check failing without fabricating earlier runs; with none, a test's history is empty, as a first run's is. Its variable is `arc test`'s own, like `ARC_TEST_ERROR_FILE`.
- *Lifecycle hooks run as written*, like every step that is not a publish, apart from the network refusals above.
- *A refused test is a failing test, and the rest still run*, so one bad fixture key does not hide every other result; a `tests.yaml` that does not load stops before any test, since no result could be trusted.
- *JUnit's failure message is the risk line*, so a CI summary that shows only the message still says what is at stake.

### Publishing into a lake

`ducklake_write@1` (`src/operator/ducklake_write.rs`, on the building blocks in `src/lake/`, compiled under `http-fetch`) ends a Protocol by writing one or more tables into a DuckLake catalogue held in S3-compatible object storage, Cloudflare R2 for Meridian's open lake, as one snapshot. Publishing used to happen outside the run, in scripts that uploaded files and rebuilt the catalogue from scratch; now the run record showing the step succeeded is the provenance. Readers attach the catalogue over https with no credentials and no server, and R2 charges no egress.

**Where things live.** Every address is a key under the step's `public_base`. The catalogue is one object (`catalog/open.ducklake` for the open lake). Its persisted data path is the https address readers use, `public_base` plus `data_path` (`lake/`), and DuckLake records each data file relative to it, under names it chooses. The writer never writes through https: it attaches with `OVERRIDE_DATA_PATH` set to the write path, the same objects addressed through the S3 API (`r2://<bucket>/lake/` for an `r2` credential, `s3://<bucket>/lake/` for an `s3` one) with a temporary DuckDB secret, so one relative path names one object under both addresses. The scheme follows the credential because DuckDB applies a secret only within its scope: an `r2` secret covers `r2://` and nothing else, so an `s3://` write path would reach R2 unauthenticated. A table may also have a readable copy at a fixed key such as `<namespace>/<name>.parquet`: the Protocol's stamped Parquet byte for byte, which the catalogue never registers. Each live publish uploads a pinned copy of the catalogue, `catalog/open-<sha16>.ducklake`, keyed by its content's hash and cached forever, before it writes the stable one, unless that key is already present. The local lake pins none, since no reader fetches it by a pinned address.

**The step, in order** (`src/lake/publish.rs`, `src/lake/commit.rs`):

1. Resolve the target from the credential: the live lake, or the local lake (below).
2. Fetch the live catalogue and its ETag, or create one at DuckLake's current format (1.1) with the https data path.
3. In one transaction, per table: create the schema and table if missing; `UPDATE` rows whose key matches and whose values differ (`IS DISTINCT FROM` on every other column), `DELETE` rows whose key is gone, `INSERT` new keys; replace the table's `meta` rows and `COMMENT ON` text only where they differ; stamp the commit message with the run's identity and row counts only if something changed. Three statements because DuckLake's `MERGE INTO` takes only one action today; a table with no key is replaced whole, and says so. Nothing run-specific goes into a table, so an unchanged rebuild issues no write, DuckDB commits no snapshot, and the step reports `unchanged`. DuckLake writes new data files straight into the bucket; nothing references them until the catalogue does, so a lost commit leaves only orphans its cleanup can remove.
4. Upload the pinned copy, then the stable catalogue only if its ETag is still the one fetched. A lost race (412 or 409) or throttling (429 or 503; R2 allows one write per second per key) discards the local commit and starts again from step 2, up to five attempts, then fails naming the conflict.
5. Only once the catalogue holds the snapshot, upload the readable copies and extra files (`files:`), then the compatible manifest, so a failed publish leaves them as they were. An object that already holds the same bytes is not uploaded again: every upload carries its content's SHA-256 as user metadata (`x-amz-meta-sha256`), which a HEAD returns, so an unchanged publish writes nothing to the store while a stale copy is still replaced. Readable copies and extra files are overwritten in place at fixed keys, so each upload carries `Cache-Control: public, max-age=60`, as the stable catalogue and the manifest do: a CDN in front of the lake that respects the origin's headers then serves an old copy for at most a minute after a republish, where an upload with no header left it to the CDN's default edge TTL, which kept a replaced file live for over half an hour. Only the pinned catalogue and the content-addressed data files are cached as immutable. An object uploaded before this header was set keeps none until its bytes next change, which is when it matters.
6. Report each table's action, snapshot id, row counts by change type, the uploads with size and SHA-256, and the data files DuckLake wrote.

A column added at the end of a table is applied with `ALTER TABLE … ADD COLUMN` in the same snapshot. Any other shape change fails the step naming the difference, unless the table sets `on_schema_change: replace`: a silent replace would show the whole table deleted and reinserted in the change feed.

Before anything is written, each table's new descriptor is compared with the one `meta.descriptors` holds, ignoring the package's `created`, the resource's `bytes` and `hash` (none of which are stored) and each field's `x-finetype-confidence`, which moves on every re-inference while the label stays put. Every other value that differs is reported by JSON Pointer with its old and new value. Fields are matched by name, so a column added or removed mid-schema is one change, the whole field, rather than a shift of every field after it. The changes go to standard error beside the step's `+inserted ~updated -deleted` line and in the step's report as the table's `descriptor_changes`; a table the lake does not hold yet reports nothing. With `on_descriptor_change: fail` the comparison also refuses the publish, before any write, so the catalogue is untouched, when a field's `x-finetype-label` changed and the new field is not marked `"x-finetype-nominated": true`: a label that moves with no nomination is finetype's inference drifting, not a choice anyone made, and the error names the table, the field and both labels and says to nominate the label or fix the input. Since a refused publish reports nothing else, the error also lists the table's other changes. Every other change is still only reported under `fail`, since a descriptor edited on purpose is ordinary. The default, `report`, never refuses.

**The `meta` schema** (`src/lake/meta.rs`). Every catalogue arc publishes into holds `meta.descriptors` (`table_name` as `schema.table`, and the table's whole Frictionless descriptor, less the per-file `bytes` and `hash` and the package's `created`) and `meta.fields` (one row per column: name, ordinal, type, FineType label, description, constraints and whether it is in the key), written in the same snapshot as the rows. The descriptor lives here rather than in the data files' footers because DuckLake writes those files, and versioning it with the data means time travel returns the descriptor that matched. Lakes are reference data, and `meta.fields` is for users and agents solving a Protocol: an agent holding a column it cannot place, such as postal codes, can find which table holds those values as a key. `meta` is reserved for this; no published table may use it.

**One catalogue per owner.** A publisher writes only its own catalogue and prefix; Meridian's open lake is the first owner, and a user publishing their own data gets a catalogue of their own that readers attach separately. DuckLake's only permissions are read-only or read-write on a whole catalogue, so a shared one would let any publisher rewrite any other's tables. Hugh ruled this the right shape, and a separation future products and data security will need.

**Plain `arc run` publishes.** With every credential variable set, the step publishes live. With any missing, it publishes into a lake of its own at `local_catalog`, its data in `<file name>.files/` beside it, and the run stays green, naming the missing variables. Hugh's comparison was a local `npm` build: the person has done nothing wrong, so it is not a failure. The local lake starts empty and keeps its own history, so the contributor can attach it offline and query what the run built; starting it from a copy of the live catalogue was dropped, because a catalogue whose data path is the live https address cannot read files a local run adds. `arc run --publish` (`ARC_PUBLISH=required`) makes a missing credential fail the step, for scheduled jobs and anyone who means to publish, so a run never goes green having silently published nothing. A `ducklake_write` step is never skipped as fresh: a local publish is not a live one, so `--publish` after a plain run must still publish, and an unchanged publish costs one catalogue fetch and a few HEAD requests, and writes nothing.

**The credential.** The step's `credential:` names the type (`r2` or `s3`), the bucket and the environment variable for each secret parameter; the manifest never holds a value. Values come from the manifest's `dotenv:` files, then the process environment, which is how the maintainer's own publishes run and how managed runs will later inject them from a secret store. Dotenv values reach operators in their own `OpContext` field, read only by credential lookups and never put into a spawned process's environment, so a publish's secret is not handed to every other step. No value reaches a report, log or error: values go only into the DuckDB secret statement, whose errors are not passed on, and the object-store client (`src/lake/store.rs`), whose errors name only keys.

**Concurrency.** One writer per catalogue at a time, enforced by the conditional write and retry, is far more throughput than a published lake needs. Another publish can land between this one's commit and its uploads, so each readable copy is guarded per table: the step reads the copy's own ETag first, then asks whether a snapshot newer than its own changed that table (`newer_change`, through `ducklake_table_changes` and the table's `meta.descriptors` rows), and writes conditionally on that ETag. Asking costs one HEAD of the catalogue: it is fetched only when its ETag has moved from the one this publish landed, once per ETag, and each table's answer is cached for that ETag across the uploads and the manifest, so a publish where nothing moves fetches the catalogue once in all; the manifest's check starts from what the uploads' check learned. A newer change skips the copy and reports it superseded; a refusal no newer snapshot explains is retried up to three times, then fails. Guarding per table rather than by the whole catalogue's ETag means an older publish never overwrites a newer one's copy, while a commit to some other table never stops this one's uploads. Manifest entries follow the same rule, re-filtered on every manifest attempt after its read, so a retry never writes back an entry a newer publish has since taken.

**The compatible manifest** (`src/lake/manifest.rs`). With `manifest:` set, the step updates each published table's entry in the live `manifest.json` with the same conditional write, after the catalogue, so no entry names a snapshot the catalogue lacks. Entries keep the keys today's readers use: `url` (the readable copy), that copy's `rows`, `bytes` and `sha256`, `published`, and `run`, whose `id` is the run and whose `record` is `public_base` plus the record's key, `<runs><run_id>.json` (`runs` being the configured prefix, `runs/` by default); the top-level `catalog` names the pinned address, and `manifest_extra` adds keys such as a dataset's search parts. An entry whose `url`, `rows`, `bytes` and `sha256` match the manifest's keeps its `published` time and `run`: the copy is the one that run published, so an unchanged publish leaves the manifest untouched even after another step has committed to the same catalogue. Only an entry whose copy changed takes this publish's snapshot time and run. It still passes on the current catalogue's pinned address, so the next publish repairs a manifest an interrupted one left behind. It exists so datasets can move onto the step before the website and uptime monitor read the catalogue, and is removed after.

**The run record.** A live publish that commits a snapshot queues the run record for upload to `<runs><run_id>.json` as soon as its catalogue lands, and the snapshot's commit metadata names that address. An unchanged publish commits nothing, so it queues the record only when its manifest write changed the manifest, whose entries name the record as `run.record`. The runner uploads each queued record once it is complete at the end of the run. `runs` is a key prefix ending in `/`, validated like the other keys and defaulting to `runs/`; a lake under a prefix sets it beneath that prefix, as `lake-test/runs/`. Queuing on landing means a failure in the later uploads still leaves the record the snapshot names, and a failed record upload fails the run, naming the committed snapshot. The bucket is public, so the uploaded copy publishes each SQL text as its SHA-256, redacts the value of every param that came from a dotenv file, rewrites the Protocol directory to `.` everywhere and is refused outright if anything still names the home directory or a path under it, or holds a credential's key id or secret or the value of a dotenv variable whose name looks secret (`public_record` in `src/runner.rs`); the record on disk keeps its paths.

**Readers need DuckDB 2.0.** DuckDB 2.0's DuckLake extension writes the catalogue file in DuckDB's 2.0 storage format on every write, even to a catalogue 1.5 created, and DuckDB 1.x refuses the result; neither `storage_compatibility_version` nor `DUCKLAKE_VERSION '1.0'` prevents it. Hugh chose to move readers to 2.0 over writing the lake with a pinned DuckDB 1.5, and published `ATTACH` snippets say 2.0 or later from the first publish. Since readers need 2.0 regardless, new catalogues use DuckLake's current format, 1.1.

**`arc lake rebase` and the cutover.** DuckLake cannot change a catalogue's persisted data path, and the open lake's current catalogue names a local folder on the machine that built it, where readers could not resolve DuckLake-written files. `arc lake rebase --from <catalogue or https URL> --out <file> --data-path <https URL>` (`src/lake/rebase.rs`) builds a new catalogue with the new data path, creates each table, registers its current data files by address without touching them, and recreates the views in dependency order, in one snapshot. A table with deleted or inlined rows is refused by name, and only column names and types carry over. `--upload <catalogue URL> --bucket <name> --credential-env <type>:<param>=<VAR>,...` writes the result only if nothing is at that key. The old snapshots record rebuilds from scratch, not dataset history, so nothing is lost. Today's infrastructure rebuilds and overwrites the catalogue and manifest without checking what it read, and a version collector deletes files the manifest no longer names, which the new catalogue still registers. So the cutover runs in this order, before the first live publish: rebase the live catalogue; tell readers they need DuckDB 2.0; then stop the catalogue rebuild, the manifest flip and the collector together. A dataset whose Protocol has not moved keeps serving its current files until it does.

**Other rulings and their reasons.**

- *DuckLake writes the data.* Registering the run's own validated Parquet with `ducklake_add_data_files` would have kept the stamped footer and exact bytes in every lake file, but each publish would replace the whole table, so the change feed would show every row replaced and arc rather than DuckLake would own the files. Hugh judged upserting the better fit for the DuckDB ecosystem and its costs (the footer, moved into `meta`) solvable. One step per table was also rejected: several tables would become several snapshots, with windows where they disagree.
- *The readable copy stays.* Downloading a whole file with `curl`, without DuckDB or auth, is a use Meridian publishes for. The catalogue never registers it because DuckLake's maintenance may delete files it owns.
- *A file catalogue on R2*, with no server and no running cost, the pattern DuckLake documents for public lakes. Hosted Postgres would need a standing service and a credential for anonymous readers; it stays the step up if one lake ever has many concurrent writers, without moving any data.
- *Every open dataset moves onto this step* as follow-up work, so the step supports what all of them need, such as extra files for search parts.
- *The write path goes through S3, not a staging folder.* An override to a local folder hides the lake's existing files from DuckLake, so the upsert could not read them. Downloading each table into a local folder first remains the fallback if R2 does not behave.
- *A pinned catalogue address.* A reader whose attach spans an overwrite of the stable catalogue can read bytes from two versions; DuckDB fails loudly and a retry heals it, but the pinned copy keeps the zero-tear address readers have today.

**Proven live.** A live check on R2 on 2026-11-14 ran the operator itself against the open bucket under a test prefix, since deleted. DuckLake wrote and read data files through `r2://` with the temporary secret, and https readers resolved them. R2 refused a stale conditional catalogue write and the losing publish retried on top of the winner (attempts 2), both tables landing. The change feed and time travel read correctly over https. An unchanged re-run committed nothing and left the catalogue and the download copy byte-identical (same ETag and last-modified), so R2 keeps the stored content hash. The uploaded run records carried no local paths. The check showed run records landing at the bucket root, outside the test prefix, hence the `runs` key. `ducklake_publish@1`, the earlier operator that registers existing files, stays beside the new one for now.

### Release and distribution

The package and library are `arcform` and the binary is `arc`. The vendored sqlparser fork is published as its own crate, `arcform-sqlparser`, pinned exactly, because Cargo drops `[patch.crates-io]` on publish. A release binary is built with `mcp,bundled-duckdb`, so it carries DuckDB and starts on a machine with no DuckDB library; SQL steps still run through the `duckdb` command. A pushed `vX.Y.Z` tag builds four targets, publishes the GitHub release with the tag's `CHANGELOG.md` section as its notes, publishes both crates and updates the install script, behind a guard that refuses a tag not matching `Cargo.toml` and the changelog. `docs/RELEASE.md` describes the machinery.

### The runner image

`runner/Dockerfile` builds a `linux/arm64` image for hosted runs: a container that runs one Protocol at one commit, writes the run's declared outputs, its run record and its log to object storage and exits. Build it from the repository root with `docker build --platform linux/arm64 -f runner/Dockerfile -t arc-runner .`. It holds arc built from this tree, linked against DuckDB's v2.0.0 release library rather than built with `bundled-duckdb` (which takes tens of minutes from cold, where this build takes minutes), the DuckDB command line SQL steps run through, and curl, jq, git and procps (`pkill` and `pgrep`). Both DuckDB downloads are checked against the SHA-256 digests GitHub publishes for the release assets, and `scripts/check_duckdb_version.py` holds the Dockerfile's `DUCKDB_VERSION` to the version `Cargo.lock` links, with CI's and install.sh's. The image has no Python, so a Protocol whose operators need Python does not run in it yet.

**Inputs**, all in the environment:

- `RUN_ID`: the run's id, letters, digits, `_` and `-`.
- `RUN_TOKEN`: a one-time token for the credential exchange.
- `PROTOCOL_REF`: `<namespace>/<name>@<commit>`, the commit in full (40 hex digits). A branch, a tag or a short commit is refused, and so is a 64-digit commit from a SHA-256 repository, which the image does not fetch.
- `CREDENTIAL_EXCHANGE_URL`: the base URL of the service that exchanges the token.
- `PROTOCOL_FORGE_URL`: the base URL of the git server; the Protocol's repository is `<PROTOCOL_FORGE_URL>/<namespace>/<name>.git`, with `arcform.yaml` at its root.

Both URLs must be `https`. `ARC_RUNNER_INSECURE_HTTP=1` allows `http`, for the tests' stub; nothing else should set it.

**What the entrypoint does**, in order, each a named step:

1. **inputs**: checks each value against the shapes above, and removes `RUN_TOKEN` from its own environment before anything else starts.
2. **exchange**: `POST <exchange>/v1/runs/<RUN_ID>/credentials` with `Authorization: Bearer <RUN_TOKEN>`. The reply is
   ```json
   {
     "credential": {"access_key_id": "…", "secret_access_key": "…", "session_token": "…",
                    "expires_at": "2026-11-13T00:15:00Z"},
     "renewal_token": "…",
     "storage": {"endpoint": "https://<account>.r2.cloudflarestorage.com", "bucket": "…", "region": "auto"},
     "run_log": {"prefix": "<subscriber>/runs/<RUN_ID>/"}
   }
   ```
   `storage.region` defaults to `auto`. The renewal token lasts the run. The token is good for one exchange, so the request is sent again only when curl could not reach the host at all; after a timeout or an error answer the step fails, since the token may already be spent. The log's prefix must be a folder ending `runs/<RUN_ID>/`, either `runs/<RUN_ID>/` itself or under another folder; any other prefix is refused, so a reply meant for another run cannot direct this run's log there.
3. **fetch**: fetches the pinned commit alone (`git fetch --depth 1 <repo> <commit>`) into an empty repository, failing if the transfer stays under 1 KB/s for a minute, checks it out, and checks that `HEAD` is that commit and that `arcform.yaml` is at the root. A commit the server does not hold fails here.
4. **run**: `arc run` in the checkout. Its output goes to the run log and is streamed to standard output, which the operator's logs keep.
5. **outputs**, after a run that succeeded: uploads the Protocol's declared outputs (see "Declared outputs") and the run record, reading arc's record and never `arcform.yaml`:
   1. Kills every process left running as `protocol` (`pkill -KILL -u protocol`, repeated every tenth of a second for up to five seconds until `pgrep` finds none), so nothing rewrites a file between the check of its hash and its upload.
   2. Reads the one run record under `build/.arcform/runs/`; none, or more than one (a Protocol that committed its own), fails the step, naming them. The record must itself pass the file check below, and a copy is taken into the runner's state directory.
   3. For each file the record lists, in its order: refuses a path that is absolute, has a `.`, `..` or empty segment or a control character, so a key never leaves the run's prefix; refuses the file unless it is no symlink and resolves (`realpath -e`) to a regular file inside the checkout, so a link to the runner's own state is never read; refuses it over 5 GiB, the most one `PUT` carries; and refuses it when its size or SHA-256 differs from the record's.
   4. Uploads each file to `<prefix>outputs/<path>`, keeping its path, each segment percent-encoded once, signed as the log is with a fresh copy of the current credential.
   5. Uploads the record to `<prefix>run.json`, last. **`run.json` is the completion marker: it is uploaded only once every output has been, so a run folder without it holds no finished set.**
   6. Says how many declared outputs, files and bytes it wrote (`wrote 2 outputs: 3 files, 1234 bytes`), in the log and the container's output, so a hosted run's bytes out can be measured.
6. **upload**: puts the log at `<prefix>run.log` in the bucket with an S3 `PUT`, signed with AWS Signature Version 4 by curl's `--aws-sigv4` using the current credential and its session token, and with the body's SHA-256 as `x-amz-content-sha256`. Terminal colour codes are taken out of the uploaded copy.

Once the exchange has succeeded, every later failure still uploads the log, an unexpected one included (an `EXIT` trap ends in the same path, naming the step under way). The exit code names the first step that failed, and so does the last line of output (`arc-runner: failed at <step>: …`); for a failed Protocol step, that line also names the step arc reported, as `step '<name>' failed`:

| Exit | Step |
|---|---|
| 0 | the run and the upload succeeded |
| 10 | inputs |
| 11 | exchange |
| 12 | fetch |
| 13 | run: a Protocol step failed |
| 14 | outputs or upload, after a run that succeeded: an output or the record was refused or did not upload, or the log did not upload |
| 15 | interrupted: a `SIGTERM` or `SIGINT` reached the entrypoint; the git command or `arc run` under way is stopped, given ten seconds, and the log uploaded. A stop during the outputs step stops the upload under way, abandons the rest and `run.json`, and goes straight to the log |

What each outcome leaves under the prefix:

| Case | Uploaded | Exit |
|---|---|---|
| the run succeeds and its outputs upload | the outputs, `run.json`, `run.log` | 0 |
| the run succeeds and declares no outputs | `run.json`, `run.log` | 0 |
| a step fails, or a declared output is missing | `run.log` | 13 |
| an output is refused or its upload fails | the outputs before it, `run.log`; no `run.json` | 14 |
| stopped during the output upload | the outputs before the stop, `run.log`; no `run.json` | 15 |

The rulings behind the outputs step, from the design approved on 2026-11-13: outputs keep their paths under `<prefix>outputs/` and the record sits beside the log as `run.json`; a failed or interrupted run never uploads `run.json`, so a reader can tell a complete set from a partial one without trusting timing; a stop abandons the outputs for the log, because a Spot interruption gives two minutes and the log matters more than a partial dataset; and a file over 5 GiB is refused rather than split, since multipart upload is not needed for any open dataset today. The exchange's reply did not change: outputs go under the log's prefix.

Each git command and `arc run` run in the background while the entrypoint waits on them, because bash runs a signal's handler only between commands: a stop during a foreground fetch would wait for the fetch to end. A signal that arrives while the log is being uploaded lets the upload finish and keeps its exit code.

**Renewal.** While the run goes on, a background loop renews the credential once two thirds of its life has passed: `POST <exchange>/v1/runs/<RUN_ID>/credentials/renew` with `Authorization: Bearer <renewal_token>`, whose reply is `{"credential": {…}}`, in the exchange's shape. A network error, a 408, a 429 or a 5xx is tried again after a wait that doubles up to 30 seconds. Any other 4xx means the control plane holds the run as over, and the loop stops, so the credential lapses. The upload signs with a copy of the credential taken once, so a renewal that lands meanwhile cannot mix two credentials.

**What a Protocol step can reach.** The whole run is treated as hostile; these rules keep the token and the credential out of the run's environment and its log:

- The entrypoint starts as root. The credential, the renewal token and the log live in `/run/arc-runner`, which only root can read.
- Every git command and `arc run` itself run as the user `protocol`, through `setpriv` with no capabilities and `no_new_privs`, under `env -i`: a step's environment holds `HOME`, `PATH`, `LANG`, `NO_COLOR`, `RUN_ID` and `PROTOCOL_REF`, and what arc adds. Running as another user also keeps a step from reading the entrypoint's environment through `/proc/1/environ`.
- Tokens and credentials reach curl on standard input, as a `--config` file, never as arguments, which any process can read from `/proc/<pid>/cmdline`. A value that could break out of that file's quoting is refused when it is read.

**Tests.** `runner/tests/run.sh [IMAGE]` runs the image's acceptance tests. Each test starts a fresh stub on a private Docker network and runs the image once with `docker run --platform linux/arm64`. The stub (`runner/tests/stub/stub.py`) stands in for the credential exchange, minting throwaway credentials and refusing a spent token; for the S3 endpoint, verifying each upload's Signature Version 4 against the credential it names and refusing an expired one; and for the forge, serving the repositories `stub/make-forge.sh` commits from `runner/tests/protocols/` through `git http-backend`. The tests:

- `runs_pinned_protocol`: a Protocol with a SQL step and a command step, pinned to its first commit while its branch has moved on, exits 0 and writes `sub_test/runs/<run_id>/run.log`, which shows the pinned commit's output and not the branch head's.
- `fails_named_step`: a Protocol whose second step fails exits 13; the log shows the first step's output, names step `second`, and shows nothing of the third.
- `token_and_credential_kept_out_of_step_env`: a step that prints its environment, `/proc/1/environ` and the runner's state directory leaves none of the one-time token, any issued credential part or any renewal token in the log.
- `renews_credential_while_running`: with credentials lasting four seconds and a Protocol running for seven, the credential is renewed and the log is signed with a renewed credential.
- `uploads_the_log_when_stopped`: `docker stop` during a step, as a Spot interruption would, exits 15 within ten seconds and still writes the log, which names the interruption.
- `uploads_the_log_when_stopped_during_fetch`: the same against a git server that never answers, so the stop lands during the fetch.
- `fails_a_stalled_fetch`: left alone, a run against that silent server fails at fetch after a minute, exits 12, and uploads the log with git's reason. The test takes that minute.
- `refuses_a_reference_without_a_full_commit` (a branch name, and a 64-digit commit), `fails_fetch_of_an_unknown_commit` and `refuses_a_spent_token`: exits 10, 12 and 11, and a refused reference does not spend the token.
- `does_not_repeat_an_exchange_that_was_answered`: an exchange that spends the token and answers 503 gets one request, and the run exits 11.
- `runs_pinned_protocol_with_outputs`: a file output and a directory output with a nested folder and a file whose name starts and ends with a space, from a Protocol that leaves a writer running, exit 0; each of the record's files lands under `outputs/` with the record's SHA-256, in the record's order, then `run.json`, then `run.log`, and the log counts them.
- `uploads_no_outputs_when_a_step_fails`: a Protocol that declares outputs and fails a step exits 13 and writes `run.log` alone.
- `refuses_an_output_outside_the_checkout`: a leftover process swaps a hashed output for a link to the runner's credential once arc has written its record; the step exits 14, writes `run.log` alone, and no object holds any credential part.
- `refuses_an_output_changed_after_the_run`: a leftover process appends to an output once arc has written its record; the hash check refuses it, and only `run.log` is written.
- `uploads_an_output_with_a_space_in_its_name`: `build/my out.csv` lands at `outputs/build/my out.csv`, its signature checked.
- `refuses_more_than_one_run_record`: a Protocol that committed a run record of its own exits 14, naming both.
- `stopped_during_output_upload`: with each output's `PUT` held five seconds, `docker stop` two seconds into the upload exits 15 and writes `run.log` without `run.json` or the second output.

CI's `runner-image` job builds the image on an arm64 runner, shellchecks the scripts and runs these tests.

### Agent skills

`skills/` at the repository root holds six agent skills, one folder each, that teach an agent the analyst workflow through arc: `using-arcform` (the entry point: the safety model, where results land, the sizes of a task, the environment check and the full CLI-to-MCP verb map), then one per stage, `scoping-an-analysis`, `profiling-and-typing-data`, `building-and-checking-a-protocol` (Build and Check) and `presenting-findings`, and `dashboard-from-data`, which the entry skill routes to when the user wants to see what is in a dataset rather than ask a question of it. A skill is a `SKILL.md` with YAML frontmatter (`name`, `description`, `metadata.arc_version`) and, where it helps, a `references/` folder; each shows every step both as an `arc` command and as the matching `arc mcp` tool. The workflow outline in `INSTRUCTIONS` (`src/mcp/mod.rs`) names the same stages and skills, and its test fails when the outline names a skill that has no folder. `dashboard-from-data` sizes the work in one line, explores the data with queries to find what drives it, states that as a claim, and composes one Protocol panel: a focal view, the views that test the claim and a view of the data's quality, all over one table and one shared crossfilter selection. Brightfield draws the table's grid itself, so the panel draws none; when the data has no story, the skill hands back the profile. `using-arcform` routes a request to see what is in a dataset, or for a dashboard, to it once the environment check passes; a specific question still goes to `scoping-an-analysis`. The maintainer's `release` skill is separate, in `.claude/skills/`.

The skills exist so that an agent given a tabular dataset and a question reaches for arc, not a throwaway script, and leaves the analyst a Protocol they can re-run, inspect in Brightfield or share. Their design follows from that:

- **The method is in the skills; the tool stays thin.** A short entry skill routes to one skill per stage, each with a checkpoint where the analyst can redirect, and the work is sized up front (a quick look, an analysis or a project) so the checkpoints scale with it. The skills spend their words on arc's method, checks and traps, not on SQL agents already know. Routing is left to the skills' descriptions and the `arc mcp` instructions; there are no routing hooks.
- **An agent with only `arc mcp` must be able to follow every step.** That includes a desktop chat app with no file access of its own, so every file the workflow produces (a schema, a panel, the project's `README.md`, the report) is written by an arc verb with a matching tool, inside the Protocol folder and recorded in history. The CLI stays canonical: each MCP tool has its CLI verb.
- **arc draws no chart.** A chart is a Mosaic spec the agent writes to `panels/<name>.yaml`, which Brightfield opens and history versions. `arc panel check` checks only that a panel's tables and columns exist; whether Brightfield can draw it is left to the release eval, which opens every panel. A PDF of the report comes from Brightfield too, so arc gains no renderer and stays local-first.
- **The report is a verb, not a step.** It is a snapshot of one session's findings, cited to the run it describes and versioned by history, so a re-run does not rewrite it; the Protocol stays the reproducible record.
- **A skill never describes a different arc from the one running.** `arc skills install` writes the skills embedded in that binary. Channels that serve the repository instead (a plugin, GitHub, a skills directory) can drift from the user's arc, so each skill names the version it was written for and the entry skill's environment check compares it with `arc --version`.

Model training and per-operator recipe skills are outside the set: the modelling the skills teach is what the existing operators do, and the build skill points at the operators and `operator_describe`.

The skills ship inside the binary. `build.rs` embeds every file of each skill folder (a directory under `skills/` holding a `SKILL.md`; hidden files and the maintainer's `skills/README.md` stay out) as `SKILLS` in `$OUT_DIR/skills.rs`, and reruns when `skills/` changes. `arc skills install` (`src/skills.rs`) writes them into each agent whose folder exists under the home directory: Claude Code `~/.claude/skills`, and the shared `~/.agents/skills` for Codex, Cursor and Gemini CLI (when `~/.codex`, `~/.cursor`, `~/.gemini` or `~/.agents` exists), one target per distinct folder. Cursor and Gemini CLI each read their own folder as well as the shared one, so writing both would give them two copies of every skill, and refreshing only their own would leave a stale copy in the shared folder, which Gemini CLI reads first; `--agent` and `--target` name them instead. Each folder written gets a `.arc-skill` marker whose first line is `arc <version>`. Each target is all or nothing as far as refusal goes: every destination in it is checked before any is written; one with the marker is replaced, an absent one is written, and any other is refused, which writes nothing into that target while other targets still install, and the command exits 1. A target that passes has every skill staged in a hidden folder beside its destination before any is swapped in; a swap renames the old folder aside, renames the new one in, then deletes the old one, putting it back if the rename fails, so an error leaves each skill folder one version whole unless the put-back fails too. That case, and a process killed between the two renames, leave no folder and the old one set aside as `.<skill>.arc-old` (a failed put-back's error names it); the next run writes the skill afresh and clears that folder, as it clears any `.arc-old` once a new folder is in place. With no agent found and none named, it prints where each would go and exits 1. `tests/skills_install.rs` drives it with `HOME` set to a temporary folder.

The `publish-skills` job of `.github/workflows/release.yml` mirrors `skills/` at each release tag into the public `meridian-online/data-analysis-skills` repository, which `npx skills add meridian-online/data-analysis-skills` installs from; arcform stays the source and that repository is never edited by hand. The job replaces the repository's `skills/` with the tag's, commits "Skills from arc <tag>" only when they differ, and skips when the newest such commit already names a higher version, so re-running an older tag cannot roll the skills back. It fails, naming the secret, when `SKILLS_REPO_TOKEN` is not set. Skills installed this way carry no `.arc-skill` marker, so `arc skills install` refuses them, and the environment check in `using-arcform` says what to do when their version and arc's differ.

The repository is also a plugin for Claude Code, Codex and Cursor and an extension for Gemini CLI, each bringing the skills and starting `arc mcp` from `PATH`. No agent's format is the source: `scripts/generate-plugins.py` (standard library Python) writes every manifest from `plugin/plugin.meta.json`, with the version from `Cargo.toml`, and `tests/plugin_manifests.rs` runs it into a temporary folder and fails, naming the source file to edit, when a committed manifest differs. The marketplace that Claude Code and Codex read names the plugin at the release tag `v<version>`, not the default branch, so those agents install the newest release's skills; Gemini CLI and Cursor install at the tag the user names. `skills/using-arcform/references/agents/` holds the notes for each agent and for a desktop chat app, which has no plugin route and uploads the skills `arc skills install --target` writes.

`tests/skills.rs` (feature `mcp`) holds the skills to the binary they teach. It checks every MCP tool and argument a skill names against a live `arc mcp` `tools/list`, and every `arc` verb, subcommand and flag against `arc … --help`; requires every row of a CLI and MCP table to fill both columns, an MCP cell naming a tool or saying `None:` and why (the test prints those gaps); checks the frontmatter loads and names this crate's version; and runs each `sh arc-example` block under `set -e` in a fresh copy of a fixture Protocol, matching the `text expect` block after it against the output. An example declares what it needs (`needs=finetype`, `needs=finetype-ext`) and is skipped without it, except that `ARCFORM_REQUIRE_FINETYPE_CLI` and `ARCFORM_REQUIRE_FINETYPE_EXT`, which CI sets, turn a missing CLI or extension into a failure. The notation the checker reads is specified in the module doc at the top of the file. Its fixtures: `tests/fixtures/skills/`, the default Protocol for examples (one step loading a 200-row `sales.csv`, beside an `orders.json`); `tests/fixtures/skills-empty-filter/`, whose filter step leaves an empty table to trace; `tests/fixtures/skills-many-series/`, a year of monthly revenue for twelve stores, for the chart past eight series; and `tests/fixtures/skills-docs/`, test-only skills that exercise the checker itself, `good/` passing every check and `bad/` and `bad_name/` failing each at the line the test asserts.

`tests/finetype_mcp.rs` (feature `mcp`) calls the five FineType tools through `arc mcp` against the real `finetype`, with every property and enum value their `tools/list` schemas advertise; a property with no call, or a call setting one no schema advertises, fails the test. The unit tests in `src/mcp/finetype.rs` use a stand-in that accepts any arguments, so this is the test that catches a flag finetype drops. CI's build job installs the finetype release pinned by `FINETYPE_VERSION` and `FINETYPE_SHA256` in `.github/workflows/ci.yml` and sets `ARCFORM_REQUIRE_FINETYPE_CLI`, under which this test, the CLI tests in `tests/table_profile.rs` and the `needs=finetype` skill examples fail rather than skip when the CLI is missing; `tests/common` resolves the binary as arc does, from `FINETYPE_BIN` or `PATH`, against the floor in `src/finetype_cli.rs`.

The structural test proves a skill names only what arc has, not that an agent picks arc up and follows the method. `eval/analyst-workflow/` is the release test for that: ten analyst tasks on public datasets, across the three sizes, run by hand before each release in Claude Code, Codex and a desktop chat client with only `arc mcp`. A task passes in an agent when the agent chose arc unprompted and ended with the seven outcomes the skills promise; failures are clustered by cause and fixed with the smallest skill edit, and the scored sheet goes in the release pull request. It is not a CI job, because it needs paid agent sessions. Its `README.md` is the runbook. `dashboard-from-data` answers "show me what's in this", which none of those ten tasks asks, so `dashboard-tasks.yaml` holds three dashboard tasks (`size: dashboard`) on datasets outside Brightfield's start gallery, run the same way and scored with `score-dashboard.md`: chose arc, a first picture within the first few minutes, a claim checked against a query, a quality view in the panel, at most one question, no template across the three tasks, and a clean `panel_check`. That rubric is proposed for review and waits on the maintainer's approval; until then the tasks are run for practice and no release is scored against it.

## Key types

- **`Manifest`** — top-level project config loaded from `arcform.yaml`. Contains `name`, `engine`, `engine_version`, `db`, `steps`, `assets`, `outputs`, `measure_history`, `check_samples`.
- **`Step`** — a pipeline step: one of `sql` (path to .sql file), `check` or `measure` (path to a one-query .sql file), `op` (an operator) or `command` (shell string). Has `produces`, `depends_on`, `preconditions`; a check also has `risk` and `severity`.
- **`Precondition`** — typed freshness check. Variants: `modified_after` (file age), `fresh` (a fetched artifact's recorded identity vs. the remote), `command` (shell exit code), `tool` (the identity of an external binary or artifact the step did not produce — a reported version or a content hash). AND semantics — all must pass to skip.
- **`AssetOverride`** — manual asset dependency declaration (for command steps; SQL steps auto-discover).
- **`MeasureHistory`** — the window `measure_history` reads: `Runs(n)` (default 30) or `Since(duration)`.
- **`CheckSection`** — a check step's entry in the run record: `name`, `risk`, `severity`, `success`, `rows_returned`, `sample`, `sample_columns`, and `error` when the query did not run.
- **`MeasureSection`** — `values`, the measures a step recorded: a measure step's `<step>.<column>` names, and `table:<t>.row_count` and `table:<t>.bytes` for each table a step produced.
- **`ChecksSummary`** — `run.checks` in the record: how many checks `passed`, `warned` and `failed`.
- **`ProtocolTest`** — one test from `tests.yaml`: `name`, `risk`, `fixtures`, `breaks`, `expect` (`fails_with`), `checks`, `params`, `measure_history`.
- **`TestPlan`** — what one test changes in its copy: `removed_steps` (fixtured and publishing steps, in manifest order) and `placements`, each a fixture, the output it lands at and its break statements.

## Execution model

1. Load `arcform.yaml` manifest
2. Build asset dependency graph (SQL introspection + manual overrides); refuse the manifest if two produces:/depends_on: declarations collapse onto one asset by case alone
   - Refuse a check or measure file that is not one query, a step producing a reserved table in a Protocol with checks, and a publishing step placed before an `error` check on what it publishes
   - Read `measure_history` from earlier successful runs' records with the same parameters
3. For each step in order:
   - Evaluate preconditions (if any) + SQL/op config hash staleness + produced/read artifact hash staleness
   - Skip if fresh; execute if stale (check and measure steps are never skipped)
   - SQL steps: delegate to engine CLI (`duckdb <db> -f <file.sql>`)
   - Check and measure steps: the one query inside arc's wrapper on the same CLI, with `measures` and `measure_history` stood up; a failed `error` check stops the run, a failed `warn` check prints a warning
   - Command steps: shell execution with real-time stdout streaming
   - After a step that produces tables succeeds or is skipped as fresh: measure each table's `row_count` and `bytes` into the step's entry and this run's `measures`
4. Update run state after each step
5. Check the declared `outputs:` are there (before the hooks), run the hooks, then hash the outputs into the run record

`arc test` runs this whole model once per test, as a child `arc run --force` in a copy of the Protocol with fixtures in place of its fetches and its publishing steps taken out (see "Protocol tests").

## Runtime dependencies

- **clap** — CLI argument parsing
- **serde / serde_yaml** — manifest (de)serialization
- **sqlparser** — SQL introspection fallback (the vendored `arcform-sqlparser` fork), for statements DuckDB's reading cannot take or when `ARC_SQL_READER=sqlparser`
- **duckdb** — DuckDB 2.0 Rust bindings (state backend; reads the database the command line writes)
- **semver** — engine version constraint checking
- **sha2** — SQL/op config hashing AND produced/read artifact content hashing, both for staleness detection
- **humantime** — duration parsing for preconditions

## Conventions

- Manifest filename: `arcform.yaml`
- SQL files live alongside the manifest, referenced by relative path
- Engine delegation: SQL runs via `duckdb <db> -f <file.sql>`, with `DUCKDB_AGENT_MODE=0`
- State is persisted in the DuckDB database itself (run metadata tables)
