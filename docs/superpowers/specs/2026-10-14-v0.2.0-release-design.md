# arcform v0.2.0: a release a stranger can install, with `arc mcp` in it

Date: 2026-10-14. Status: design, awaiting approval.

## Intent

arcform has never been released. v0.2.0 is the first tag, and it is the first time someone outside the project can install `arc` and use it.

The stranger it serves works anywhere in a quadrant: greenfield or brownfield data, and quick exploration or the maintenance of a larger data asset. Arc is meant to be the one tool that covers all four corners, and the command line and `arc mcp` are how a person or their agent reaches it. Two things make arc different, and the release has to show both:

- **Batteries included.** One binary covers ingress, SQL modelling on DuckDB, advanced analytics through the operator catalogue, egress, charts, local history and re-runnable Protocols. A wide range of analysis needs one command and nothing assembled first.
- **The preferred framework for agentic data analysis.** Agents will have many ways to analyse data. Arc's case is that an agent exploring through it leaves behind a versioned, reproducible Protocol rather than a scratchpad.

Success: within a few minutes of the install line, a stranger (or their agent) has used arc on their own data in one corner of the quadrant, and can see that the same binary covers the other three.

## Goals

1. **A one-line install with no Rust toolchain.** `curl -fsSL https://install.meridian.online/arc | bash` installs `arc` at the newest version tag, built with the `mcp` feature, on macOS (Apple silicon and Intel) and Linux (x86_64 and aarch64). `arc --version` prints the tag's version and `arc mcp` serves.
2. **A build-from-source route.** `cargo install --git https://github.com/meridian-online/arcform --tag v0.2.0 --locked --features <release features>` builds the same binary, including with the vendored `sqlparser` patch.
3. **A guarded release workflow modelled on finetype's corrected one.** A pushed tag publishes nothing unless it is shaped `v` plus three numbers, equals `Cargo.toml`'s version, and has a non-empty `CHANGELOG.md` heading. A test drives each refusal. The GitHub release's body is that heading's section.
4. **`arc mcp` is correct and complete enough for an agent to work in every corner:**
   - stdout carries only JSON-RPC messages, including during `protocol_run`;
   - `initialize` negotiates the protocol version from a fixed allowlist;
   - the read-only tools say so;
   - an agent can create a Protocol, describe a table and run a read-only query.
5. **A README a stranger can start from.** A new front section shows what's in the box and gives the first command. An agent section covers connecting arc to Claude Code and other clients. The library snippet resolves to arcform at the tag, not to crates.io's unrelated `arc`.
6. **The web repo's release check stays green with the release listed.** The arcform docs' install section points at the tagged install.

## Non-goals

- A crates.io package. The name `arc` is taken there, and that is a separate decision of Hugh's.
- Windows binaries. Command steps run through `sh -c`.
- A Homebrew tap formula.
- Moving the MCP server to the `rmcp` SDK. The server stays hand-rolled through v0.2.x.
- Serving the 2026-07-28 MCP revision natively.
- Renaming existing MCP tools. Their names become a contract at the tag and mirror the CLI verbs.

## Anti-goals: these would make the release a failure even if it technically works

- The install line succeeds but `arc` will not start on a clean machine, because it is dynamically linked to a `libduckdb` that machine does not have.
- `arc mcp` writes anything other than a JSON-RPC message to stdout, so a strict client fails mid-call.
- A tag publishes a release whose version, notes or assets disagree with the source.
- The README front section is a wall of contract detail. The current README opens with design principles and moves straight into the engine and extension-pinning rules.

## Constraints

- **DuckDB linking.** arc links the DuckDB library in-process: `duckdb = "1.2"`, resolving to 1.10502.0, with no `bundled` feature. It uses that library in `sql_recognise`, `ducklake_publish`, state and contract reads, and several operators. A prebuilt binary must therefore carry DuckDB statically.
  - finetype avoids the question by not linking DuckDB at all, so arcform cannot copy finetype's build legs verbatim.
  - SQL steps still run through the external `duckdb` command, which stays a prerequisite.
- **One cargo build at a time on Hugh's Mac (16 GB).** Bundled DuckDB makes a cold build much heavier, so the bundled build must not become the default for everyday development.
- **Agents cannot merge, and cannot push to `main` or push tags.** Hugh merges each pull request and pushes the tag. The release process must therefore work as a pull request that bumps the version and rolls the changelog, followed by Hugh's tag.
- **The repo is public.** No private planning ids or private repo paths go in code, docs, commits or pull requests.
- **Install-site convention.** The install site (`meridian-online/install`) expects the following:
  - per-tag assets named `arc-<tag>-<target>.tar.gz`, with the binary at the archive root;
  - an `<archive>.sha256` sidecar for each, in `hash  filename` form;
  - a `repository_dispatch` of type `update-install-script` with `{tag, repo, script_base64}`, sent with a token the arcform repo holds as a secret;
  - a matrix row plus `_redirects` and `_headers` entries in that repo.
- **The web repo's release check** (`scripts/check-release-coverage.mjs`) reads arcform because arcform has docs. Once a release exists, the web repo needs a `releases.json` row whose date equals the release's publish date, and a `content/changelog/arcform-v0-2-0.mdx` entry. Both can only be written after Hugh pushes the tag.

## What Hugh decided

- The first tag is v0.2.0, and pushing it is Hugh's job.
- The release workflow is modelled on finetype's corrected one: the tag filter `v[0-9]+.[0-9]+.[0-9]+`, a first `tag-guard` job that every other job needs, the check script's exit codes (4 for a version mismatch, 5 for a missing heading, 6 for an empty one), the heading's section reaching the release body as a job output, and CI running the script's `--wiring` and `--release-rehearsal` on every pull request.
- The install line includes `arc mcp`, and the stdout defect is fixed before the tag.
- The stdout fix runs the Protocol as a child `arc run` process. It uses `current_exe()`, `run`, `--force`, `--param K=V` from the tool's arguments, the tool's directory as working directory, null stdin, piped stdout and stderr, and `NO_COLOR=1`. It then reads the newest run contract from its file, as `protocol_run` does now, and attaches a bounded tail of the captured output to an error result. The test fixture includes a command step that writes to stdout, so the test fails on any child writer and not only on the runner's own prints.
- `initialize` returns the requested version when it is in the allowlist {2025-06-18, 2025-11-25}, and otherwise the newest arc supports. A unit test covers a version outside the set.
- The handshake is observed, not assumed. The built `arc mcp` is connected to a current Claude Code (with default negotiation, and with `MCP_PROTOCOL_NEGOTIATION=legacy`) and to the MCP Inspector CLI pinned at 2.11.0 (`tools/list --strict`, and one `tools/call` per tool). The results are recorded on the tracking issue.
- `protocol_run` asks for confirmation through annotations alone: it is not read-only, and it has `openWorldHint: true`.
- The table-describe verb and its MCP tool land before the tag. The command-line verb is canonical, and MCP does not exceed it. The database is opened read-only, a describe records no history, and a missing table or missing database is refused with a message naming what is missing and how to make it.
- The read-only query verb and its MCP tool land before the tag. The database is opened read-only; a writing statement is refused before it runs; a query with no `LIMIT` gets a default cap, and the result says it was capped; several statements return one result each. The result can point to `arc sql record` for keeping a query.
- Prebuilt binaries ship through `install.meridian.online` as the front-page first command, and `cargo install` stays as the fallback. This reverses the tracking issue's earlier exclusion of binaries and the install site.
- An MCP `protocol_create` tool mirrors `arc create-protocol`, so an agent that only speaks MCP can start from nothing.
- The README gains a front section showing what's in the box and the one first command.

## The design

### 1. MCP correctness (one pull request)

- **`protocol_run` keeps its `force` argument.** *My call:* the child `arc run` gets `--force` only when the tool's `force` argument is true, as today, so an agent's run still skips fresh steps. Hugh's wording listed `--force` among the child's arguments; read as "passed through from the tool's arguments".

- **stdout fix,** as Hugh decided above. The new test parses every stdout line of a `tools/call` to `protocol_run` as JSON-RPC, on a Protocol with a SQL step and a command step that both write to stdout, and fails on the first line that does not parse. The existing helper in `tests/conflicted_copy.rs` keeps only the line that parses. It should stop doing that, so the suite would catch a regression.
- **Version allowlist,** as Hugh decided above. Replace the echo in `initialize_result`.
- **Annotations.** `readOnlyHint: true` goes on the tools that only read: `infer`, `profile`, `taxonomy`, `validate`, `generate`, `operator_describe`, `operation_describe`, `sql_recognise`, and the new `table_describe` and `sql_query`. `protocol_run` gets `readOnlyHint: false` and `openWorldHint: true`. The recording tools and `protocol_create` get `readOnlyHint: false`.
- **Server instructions** open with when to use arc: for analysing data an agent should keep, versioned and re-runnable, over DuckDB.

### 2. `protocol_create` (in the MCP pull request, or its own)

The tool mirrors `arc create-protocol`'s arguments: `dir` (required), `name`, `engine` and `db`. It goes through the same code path, so it writes the same `arcform.yaml`, `.gitignore` and `.gitattributes`, and records the first save in local history with interface `mcp`. It refuses when a spec already exists, as the verb does, and the result names the files written.

### 3. Table describe (one pull request)

- **Command-line verb:** `arc table describe <table> [--dir DIR]`, printing JSON. The MCP tool is `table_describe`, with `table` and `dir`. *My call on the names:* `table` follows the noun-verb shape of `arc operation describe` and `arc sql recognise`.
- **Output:** columns with their DuckDB types, the null count per column, the row count, and a few sample rows. *My call:* five sample rows, fixed and not configurable in v0.2.0.
- **Database:** found the way `arc run` finds it (the `db:` key, or the default under arc's data folder), and opened read-only through the linked library.
- **Tests** cover the issue's cases:
  - the output matches DuckDB's own `DESCRIBE` and counts;
  - a missing table is refused with its message;
  - a missing database is refused, with a message saying to run the Protocol;
  - the database file's bytes are unchanged after a describe;
  - `tools/list` shows the tool with `readOnlyHint: true`.

### 4. Read-only query (one pull request)

- **Command-line verb:** `arc sql query '<sql>' [--dir DIR] [--limit N]`. The MCP tool is `sql_query`, with `sql`, `dir` and `limit`. *My call on the names:* it sits beside `arc sql recognise` and `arc sql record`.
- **Database:** opened read-only.
- **Refusals:** a writing statement is refused before it runs. Classification uses the linked DuckDB's parse, the same route `sql_recognise` takes. Read-only mode is the backstop, not the gate. `INSERT`, `CREATE`, `COPY … TO` and `ATTACH` are each refused, and the database file's bytes are unchanged afterwards.
- **Cap:** *my call:* a default of 100 rows. A capped result says it was capped and, where DuckDB can say, how many rows were held back.
- **Several statements** return one JSON result each, with its own state. *My call:* the whole text is classified before any statement runs, and if any statement would write, the whole batch is refused and nothing runs.
- **Results** can point to `arc sql record` for keeping a query.
- **`tools/list`** shows the tool with `readOnlyHint: true`.

### 5. Release machinery (one pull request)

- **Bundled DuckDB behind a feature.** Add a feature, *my call:* `bundled-duckdb`, which enables the `duckdb` crate's bundled build together with the parquet, json and ICU extensions the official library carries. arc reads parquet in-process, so the plain `bundled` feature, which compiles DuckDB with `cc` and leaves those extensions out, would ship a binary that loses behaviour the tests never see. The builder chooses between `bundled` plus the extension features and `bundled-cmake`, which needs cmake on each leg. The release legs and the `cargo install` line enable it alongside `mcp`. Everyday development stays on the dynamic library, so local builds remain fast, and the known issue in `CLAUDE.md` stays true for development builds only. *My call:* keep this a feature rather than the default, because of the 16 GB build constraint.
- **One DuckDB version throughout.** Today three disagree: the crate resolves to DuckDB 1.5.2, CI installs 1.5.4, and the vetted-extension list names 1.5.5. arc loads the finetype extension in-process, and an extension must match the library's exact version. *My call:* the `duckdb` crate, CI's `DUCKDB_VERSION` and the vetted list move to one 1.5.x release, the newest with a published `duckdb` crate (1.10506.0, DuckDB 1.5.6, if that release is out; otherwise the newest that is). The README and `install.sh` name that version as the recommended `duckdb` command, within arc's existing `>=1.3, <2` range.
- **CI builds the bundled binary before the tag does.** *My call:* a CI job builds with `--features mcp,bundled-duckdb` on Linux and runs the test suite against it on each pull request, so the binary the release ships is tested before a tag. The comment at the top of `ci.yml` that says `libduckdb-sys` has no bundled feature is wrong for the current crate and is corrected.
- **Linux baseline.** *My call:* the Linux legs build on Ubuntu 22.04 runners (glibc 2.35), x86_64 and native ARM, and the README states that glibc as the minimum. Older distributions build from source. musl targets are out, since they would change the asset names and DuckDB's C++ build is harder there.
- **`.github/workflows/release.yml`** has the following jobs:
  - `tag-guard` runs `scripts/check_release_tag.py` and outputs `notes`.
  - `build` runs a matrix over `aarch64-apple-darwin`, `x86_64-apple-darwin`, `x86_64-unknown-linux-gnu` and `aarch64-unknown-linux-gnu`, building `--release --features mcp,bundled-duckdb`. Each leg archives `arc-<tag>-<target>.tar.gz` with a `.sha256` sidecar.
  - `release` uses `softprops/action-gh-release` with `body: ${{ needs.tag-guard.outputs.notes }}` and `fail_on_unmatched_files: true`.
  - `update-install-site` sends `scripts/install.sh` to the install repo.
  - Every job after `tag-guard` needs it, and none uses `always()`, `cancelled()` or `failure()`.
  - *Left to the builder:* native ARM Linux runners rather than `cross`, because compiling bundled DuckDB's C++ under emulation is slow. Also whether the build legs smoke-test `arc --version` and a scripted `initialize` against `arc mcp`. They should.
- **`scripts/check_release_tag.py`:** an arcform copy of finetype's script. It reads `[package] version` (arcform has no workspace table) and exits 3, 4, 5, 6, 7 and 8 as finetype's does. finetype's script imports a workflow reader from finetype's own gate scripts, so arcform's copy must be standalone. *Left to the builder:* how to read the workflow YAML without that import.
- **`ci.yml`** runs `--wiring` and `--release-rehearsal` on every pull request, and `--self-test` as well (it is cheap).
- **`scripts/install.sh`**, modelled on finetype's:
  - it resolves the target with `uname`, takes a version argument or else reads the latest release, and verifies the checksum;
  - it installs into `~/.arcform/cli/<version>` with a `latest` symlink, and links into `~/.local/bin`;
  - after installing, it warns when `duckdb` is not on `PATH`, because SQL steps need it.
- **`.claude/skills/release/SKILL.md`** is rewritten to the real process:
  1. On a branch, bump `Cargo.toml`'s version and roll `[Unreleased]` into `## [X.Y.Z] - <date>`.
  2. Open a pull request and wait for CI.
  3. Hugh merges it and pushes the tag.
  4. The workflow publishes the release.
  5. A web pull request adds the release row and the changelog entry.

  The rewrite drops direct pushes to `main`, the inference from Conventional Commits prefixes, generated notes, and the Homebrew-linked binary.

### 6. The install repo (one pull request there)

- Add `{tool: arc, repo: meridian-online/arcform}` to `update.yml`'s matrix.
- Add `/arc /arc.sh 200` to `_redirects`.
- Add `text/plain` headers for `/arc.sh`, `/arc` and `/arc/` to `_headers`.
- Add a row to the README table.

*Hugh's step:* the arcform repo needs an `INSTALL_SITE_TOKEN` secret (the same kind finetype uses). An agent cannot set it.

### 7. README (one pull request, after the features land)

- **Front section,** new, at the top:
  - one paragraph on what arc is for (the quadrant, and batteries included);
  - prerequisites: the `duckdb` command, plus `finetype` 0.6.54 or later for the five FineType tools and `uv` for Python operators, when those are used;
  - the install line;
  - a short list of what's in the box;
  - the first steps: `arc create-protocol`, a recorded step, `arc run`, `arc table describe`, `arc sql query`.

  The existing material stays, below it.
- **Agent section:**
  - the install line, with `cargo install … --features mcp,bundled-duckdb` as the alternative;
  - the prerequisites;
  - `claude mcp add arc -- arc mcp`;
  - a `.mcp.json` form with an absolute path and an `env.PATH`;
  - a Codex block raising `tool_timeout_sec` above its 60-second default;
  - one sentence on what an agent can do, with the tool list.
- **Library snippet** becomes `arc = { git = "https://github.com/meridian-online/arcform", tag = "v0.2.0", default-features = false }`, plus the `[patch.crates-io]` entry the README already says a consumer must carry.
- The README's links to `github.com/meridian/…` point at an organisation that is not this one. They are fixed to `meridian-online` in passing.

### 8. Changelog and version (the release pull request)

- `[Unreleased]` currently runs to 76 entries and 116 KB, with `Added` and `Changed` each appearing twice.
- Merge the duplicate headings, and add a short summary at the head of the section, written for the stranger. *My call:* about ten lines. Then roll the section into `## [0.2.0] - <date>`.
- The release body has to stay under GitHub's 125,000-character limit. *My call:* the check script fails a section over 120,000 characters, so a long changelog cannot silently truncate the notes.
- Bump `Cargo.toml` to 0.2.0.
- This pull request is the last one before the tag.

### 9. Before and after the tag

- **Before:** on `main` after the release pull request merges, the agent builds the release binary locally and runs the handshake observations Hugh specified, recording them on the tracking issue. It also runs `cargo install --git … --branch main --locked --features mcp,bundled-duckdb` once, to prove the source route builds with the vendored patch.
- **Hugh** pushes `v0.2.0`.
- **After:** a pull request in the web repo adds the `releases.json` row (dated to the release's publish date), `content/changelog/arcform-v0-2-0.mdx`, and the docs page's install section, which today says there are no release binaries and gives a `LIBRARY_PATH` hint.
