# arc on DuckDB 2.0: design

Branch `duckdb-2.0`, cut from the `0.2` release line at v0.2.1 (2254a6d). Written 2026-10-17, before DuckDB 2.0.0 (due 2026-10-21) and before duckdb-rs publishes its 2.0 crate, from DuckDB main at `1b4c3e54ba`, the Python dev wheel `2.0.0.dev2610161340` (engine `ffe0b8b7a2`), the macOS preview CLI `v2.0.0-alpha48730` (`f8f3f4dcd9`) from `artifacts.duckdb.org/v2.0-cyanoptera/`, and duckdb-rs main at `4014db7`. Every behaviour below marked *probed* was run on those builds; the build re-checks each against 2.0.0 itself.

## Intent

arc's next release links DuckDB 2.0, runs its SQL steps on a 2.x DuckDB command line, and reads each step's SQL as DuckDB 2.0 reads it. Homebrew moves to 2.0 within days of its release, and arc v0.2.x refuses a 2.x command line, so arc's few early users either set `ARC_ALLOW_UNTESTED_ENGINE` or stop. The maintainer ruled (2026-10-15) that there is no stopgap in the meantime, and (2026-10-17) that the move is built and released from the 0.2 line, then carried forward to main, because main holds the unreleased analyst skills.

2.0 is also the moment arc stops reading SQL with rules copied by hand from DuckDB's source. Before 2.0, DuckDB gave a parse tree only for a `SELECT` (`json_serialize_sql`) and no tokens at all, so arc read SQL with sqlparser-rs for the asset graph and with a lexer copied from DuckDB 1.5.5's `scan.l` and `shell.cpp` for its refusals. 2.0 adds `sql_tokenize`, and its PEG parser is the only parser. The maintainer's direction (2026-10-17): use DuckDB 2.0's own reading wherever it can carry the job; sqlparser-rs stays as the fallback, and is the reader that matters later for other dialects (Postgres, BigQuery, Redshift) when arc runs them.

arc is in early access and its users have been told to expect breaking changes. The maintainer's direction: take 2.0 as a clean break, with no compatibility shims for 1.5 behaviour.

## Goals

1. **arc links DuckDB 2.0 and accepts only a 2.x command line.** The `duckdb` crate moves to the 2.0 release (`=1.20000.x`; duckdb-rs maps DuckDB 2.0.0 to crate `1.20000.0`, not a 2.x crate). `SUPPORTED_ENGINE_RANGE` becomes `">=2.0, <3"` and `OLDEST_ENGINE` `2.0.0`. A 1.x command line is refused as too old, with a message that names arc 0.2.1 as the release for DuckDB 1.5. The linked library and the command line must share a major version because arc opens the Protocol's database through the linked library (run state, `src/contract.rs:427-431`, `src/inspect.rs`) on the file the command line writes: *probed*, a file 2.0 creates carries storage version 69, which 1.5.6 refuses ("we can only read versions between 64 and 68"); 2.0 writing to a 1.x file keeps it readable by 1.5.6.
2. **DuckDB's reading is the default asset-graph reader.** What `ARC_SQL_READER=duckdb` does today becomes what arc does with the variable unset. sqlparser-rs reads a statement only when DuckDB gives no tree for it and the token reading cannot say what it produces and reads; when neither can read a statement, arc warns, naming the step and the statement, as the default reader warns today ("could not parse … treating as opaque step").
3. **The refusals read SQL through DuckDB 2.0's tokens.** The extension-install refusal and the parser-switch refusal take their tokens from `sql_tokenize`, asked of the same DuckDB command line that runs the step, instead of arc's copy of 1.5.5's `scan.l`. *Probed*: `sql_tokenize` tokenises SQL that does not parse (`selec 1 frm ;; INSTALL h3 FROM community` returns the `INSTALL`, `h3`, `FROM`, `community` tokens), returns an unterminated string or comment as one token to the end of the text, and returns comments as `COMMENT` tokens. It runs nothing.
4. **The command-line layer stays arc's own, re-derived from 2.0's `tools/shell`.** What the DuckDB command line does to a `-f` file before the parser sees it is not in `sql_tokenize` (*probed*: it reads `.shell ls` as a number and two identifiers). arc keeps its own reading of that layer: dot commands, `#` lines, the `0x03` byte, NUL bytes, how lines batch into statements, and the 2.0 shell grammar extension, which runs a bare name as `SELECT * FROM name` (*probed*), so a bare-name statement is a read in the asset graph. Each rule cites the 2.0.0 source it was read from, as the 1.5.5 rules do now.
5. **A file's tokens are asked for once and shared.** The refusals and the asset graph read the same token answer for a step's file; the trees are a second question, because the statements to ask about come from the tokens. A file read again before a step runs (docs/VETTED_EXTENSIONS.md, "Each file, read again") is asked again only when its text changed. (Revised while planning: one question for both tokens and trees would mean splitting statements in SQL, which the reader does in Rust.)
6. **arc's own DuckDB processes run out of agent mode.** The 2.0 command line switches to markdown output, a row cap and a stderr banner when it finds one of eleven environment variables (`AI_AGENT`, `AGENT`, `CLAUDECODE`, `CODEX_*`, `CURSOR_AGENT`, `GEMINI_CLI`, `COPILOT_*`; `tools/shell/shell.cpp`, `AGENT_ENVIRONMENT_MARKERS`), stdout is not a terminal and no output-mode flag was given. *Probed* in this session, where `AI_AGENT` is set: a piped `-f` run printed `| a:INTEGER |` and the banner went to stderr, which arc captures as the step's error text. Every DuckDB process arc starts itself (SQL steps and hooks, `ask_duckdb`, the reader, the extension checks, the run-record question) gets `DUCKDB_AGENT_MODE=0`. *Probed* on the v2.0.0 release (2026-10-23): with `AI_AGENT` set, `-f` printed markdown and the banner, and with `DUCKDB_AGENT_MODE=0` it printed the normal box output and no banner; v2.0.0's `tools/shell/shell.cpp:3561-3578` reads the variable (`1`/`0`, `on`/`off`, `true`/`false`, `yes`/`no`, or `auto`). `ask_duckdb` (`-noheader -list`) and the reader (`-json`) already pass an output-mode flag, so the exposure today is the `-f` step runs and hooks; the variable covers all of them in one place. A `command:` step's environment is the author's and is left alone.
7. **A run on a new engine says so.** When the newest run record under `build/.arcform/runs/` names a `duckdb_cli` whose major.minor differs from the engine about to run, `arc run` prints one notice before the first step: the Protocol last ran on DuckDB X, this run uses Y, and results can differ; for a 1.x → 2.x change it names the four changes that alter results without an error (`~`/`!~` match part of a string; integer `//` and `%` by zero raise an error; `x -> …` lambdas are rejected; `ORDER BY` a non-integer literal is rejected). The notice does not stop the run and arc changes no setting: no compatibility shims (maintainer's ruling, 2026-10-17). A Protocol with no run record draws no notice.
8. **One DuckDB version throughout, checked by CI.** The crate pin in Cargo.toml, `DUCKDB_VERSION` in ci.yml and text-embed-parity.yml, `DUCKDB_RECOMMENDED` in scripts/install.sh, every `duckdb_versions` entry in src/vetted_extensions.json, and the README's prerequisites name the same release, and a CI step fails when the version Cargo.lock's `libduckdb-sys` decodes to differs from `DUCKDB_VERSION`. It carries a comment fix (ci.yml says arc does not enable the crate's `bundled` feature in development builds, not that the feature is absent).
9. **The vetted extensions are re-vetted on 2.0.** Each of the 16 entries in src/vetted_extensions.json is probed against the community registry's 2.0.0 builds for linux_amd64 and osx_arm64 and its proof statement re-run on 2.0.0; an entry whose 2.0 build is missing or whose proof fails is removed from the list, with the reason in the changelog, except finetype, which the release waits for (below). The `duckdb_settings()` lists arc copied from 1.5.5 (`EXTENSION_DIRECTORY_SETTINGS`) are re-read from 2.0.0.
10. **The examples, tests and Python operators run on 2.0.** Both examples' `engine_version:` becomes `">=2.0"`. Test SQL that uses `x -> …` lambdas moves to `lambda x: …`. The Python operators' inline dependency `duckdb>=1,<2` becomes `duckdb>=2,<3`, because an operator that loads a DuckDB extension or opens a Protocol's database must run the same major version.

## Non-goals

- **No 1.5 compatibility.** arc does not set `regex_match_operator_semantics`, `error_on_division_by_zero`, `lambda_syntax` or `order_by_non_integer_literal` for a Protocol, and does not accept a 1.x command line, even with `ARC_ALLOW_UNTESTED_ENGINE`. The reason is the clean break above, and the shared database file makes it hard: DuckDB 2.0 opens a 1.x file and keeps its version, but a database arc's linked 2.0 library or a 2.0 command line creates carries storage version 2.0, which a 1.x DuckDB refuses to open, so a Protocol could not move between a 1.x command line and arc. The variable still lifts the range for a 2.x pre-release or a 3.x, as it lifts the 1.x range today. A 3.x command line is the direction that can break the shared file (it may write storage the linked 2.x library cannot read), which is why the variable is named untested: it is the user's explicit choice, and arc's run state or `arc inspect` failing to open that file is an expected failure of that choice, reported as DuckDB's open error.
- **No Protocol format change beyond what 2.0 forces.** `arcform.yaml` gains no field. Pins keep their shape (`extensions.<name>.v2.0.0.<platform>`). The maintainer named simpler nested-JSON modelling, embedding and ML operators, and OpenDAL-backed data and artefact interfaces as directions after 2.0; each is its own project.
- **Other dialects.** sqlparser-rs keeps its dialect support; no non-DuckDB engine is added.
- **brightfield and finetype's extension.** Brightfield and finetype's extension move in their own repos on this arc release. infra's publish pipeline (pinned to 1.5.4) and web's browser DuckDB move on their own schedule.
- **The default reader's own bugs.** sqlparser-rs reading `COPY t FROM 'f'` backwards is left out: the DuckDB reader reads it the right way round, and sqlparser-rs reads such a statement only as the fallback after this move.

## Anti-goals

- The refusals become weaker than today's on any input. A statement today's refusal refuses must still be refused, unless the thing it guards against no longer exists in 2.0 and the spec's builder shows that from 2.0.0's source and a probe.
- The asset graph silently loses edges. A Protocol whose graph differs between the two readers must be explained (below), not discovered by a user.
- A green CI that ran 1.5. Every job that runs DuckDB runs 2.0.0.

## Decisions taken in the brainstorm

- **The release is arc 0.2.2.** The maintainer's ruling, 2026-10-17: the 0.2 line keeps its numbering and main's skills release can take 0.3.0. Accepted risk: `cargo install` and the install script treat 0.2.2 as a compatible upgrade, so a DuckDB 1.5 user moves onto a release that refuses their engine; the changelog's 0.2.2 section opens with that, and the too-old refusal names 0.2.1 as the release for DuckDB 1.5 (`cargo install arcform --version 0.2.1`).
- **The release waits for finetype's 2.0 extension.** The maintainer's ruling, 2026-10-17: arc 0.2.2 ships once finetype's 2.0 build is in the community registry, so finetype stays vetted and CI keeps installing it. Any other vetted community extension with no 2.0 build when it is probed comes off the list for 0.2.2, named in the changelog, and returns in a later patch.
- **Accepted range `>=2.0, <3`.** As the 1.x range accepted each 1.x minor, a 2.x minor is accepted; extension pins are keyed by exact version, so a new minor draws the unpinned warning until the Protocol's pins are written. (Claude's call; follows the existing policy.)
- **The reader asks the command line, not the linked library.** The linked library is also 2.0 and could tokenise in-process, but `ARC_DUCKDB_BIN` or the search path can give the steps a different 2.x patch than the one linked, and the refusals must read as the program that runs the step reads. The existing reader already asks the command line. (Claude's call.)
- **The parser-switch gap closes with the move.** On 2.0, no SQL a `SELECT` can hold switches the parser. *Probed*: the `enable_peg_parser()` table function is gone (`duckdb_functions()` lists only `check_peg_parser`); `query()` refuses anything but one `SELECT` ("Expected a single SELECT statement"), so `query('SET allow_parser_override_extension=…')` and `query('INSTALL …')` fail; `json_execute_serialized_sql` takes a serialised `SELECT`. The one switch left is the statement `SET allow_parser_override_extension` with an extension that registers a parser override, which the refusal keeps refusing by name. The earlier gap in the parser-switch refusal (a repeated JSON key, or an escaped name, hiding `enable_peg_parser` inside serialised SQL) therefore reaches nothing on 2.0. `enable_peg_parser` leaves `PARSER_SWITCHES`; the builder re-reads 2.0.0's source for any other path from a `SELECT` to a parser override before removing the `query()`/`json_execute_serialized_sql` warning's parser-switch rationale from docs/VETTED_EXTENSIONS.md. (Claude's call; a ruling was asked for.)
- **The yanked opendal fix folds in.** Cargo.lock changes in this move anyway; `opendal` moves from the yanked 0.58.0 to 0.58.2 (published 2026-08-20, not yanked, same `0.58` requirement) with `cargo update -p opendal --precise 0.58.2`, and CI builds the `opendal` feature. (Claude's call; a ruling was asked for.)
- **`ARC_SQL_READER` stays, with the values reversed in purpose.** Unset or `duckdb` reads with DuckDB; `sqlparser` forces sqlparser-rs for every statement, as a user's way round a mapping bug in DuckDB's reading while it is fixed. Any other value is refused as today. (Claude's call, from the builder check.)
- **No usable 2.x DuckDB outside a run means sqlparser-rs, with one warning.** `arc run` refuses before reading, as goal 1 says. The commands that build the graph without running (the run contract's per-statement reading, `arc sql record` and `arc operation record` through `made_by_a_step`, the MCP tools) read with sqlparser-rs when the DuckDB they would ask is missing, is not 2.x, or fails, and print one warning saying the graph is arc's own reading because no DuckDB 2 answered. Unit tests of the mapping answer from recorded DuckDB output through `duckdb_lineage`'s `Ask` trait; tests of the fallback call it directly; only the parity gate and the reader-switch suite need a real 2.0 command line. (Claude's call, from the builder check.)
- **The refusals fail closed.** When the DuckDB asked for a file's tokens fails or answers in a form arc cannot read, the run stops with an error naming the step and why; it does not fall back to arc's own reading for the refusals. An empty token list is a valid answer, not a failure: an empty or whitespace-only file, or one that is only the command-line layer arc strips before tokenising (dot commands, `#` lines), reads as nothing to refuse. (Claude's call, from the builder check; follows the anti-goal.)
- **Statement byte ranges come from DuckDB's tokens.** The run contract's per-statement ranges split where DuckDB splits, so the contract stops dropping ranges when the two readers count statements differently. (Claude's call, from the builder check.)
- **The reader-mapping tests fold in.** They are the tests that keep the DuckDB reader's mapping honest; once that reader is the default, its untested mappings are the default graph's. Its six cases join the parity corpus. (Claude's call.)

## The parity gate

Before the default flips, both readers read every SQL file in the repo (tests/fixtures, examples, and the recorded steps in src/duckdb_lineage.rs; 22 files on 2026-10-17, plus the reader-mapping cases) on DuckDB 2.0.0, and a test compares their produces and reads per statement. Each difference is fixed in the DuckDB reader's mapping, or recorded in the test as a case where DuckDB's reading is the right one, with the reason. The test stays after the flip, reading the fallback against the default.

## Constraints

- **Timing.** duckdb-rs has published its crate 1–2 days after each DuckDB release (1.4.0, 1.5.0, 1.5.6). Nothing that needs the crate is built until `1.20000.0` is on crates.io; the plan orders work that needs only a 2.0 command line first.
- **One cargo build at a time on the development machine**, and no implementers in parallel.
- **Linking.** duckdb-rs's 2.0 crate downloads libduckdb by default (`download-lib`) when `DUCKDB_LIB_DIR` is unset, and `DUCKDB_LIB_DIR` still wins. A developer's `DUCKDB_LIB_DIR` pointing at Homebrew's 1.5.6 would link 1.5.6 against 2.0 bindings; CLAUDE.md's known-issue note moves to 2.0 and says so. Release builds keep `--features mcp,bundled-duckdb`. The crate's MSRV becomes 1.88; CI's toolchain is 1.94.
- **Rust API.** arc's use of the crate compiles unchanged on duckdb-rs main (Connection, Config, `execute_batch`/`query_row`/`prepare`, `Error::QueryReturnedNoRows`, and the raw FFI in `src/record.rs:1623-1652`, now under `ffi = libduckdb_sys::v1`, on by default via `capi-v1`). arc must not set `default-features = false` on `duckdb`.
- **Release line.** The pull request targets `0.2`; the release is cut from it; the change is then carried forward to main in its own pull request. The maintainer merges and tags.

## Left to the builder

- How the refusal code is reshaped around DuckDB's tokens: the existing scan functions in `src/engine.rs` take a token stream; the builder picks whether that stream comes from an adapter over `sql_tokenize`'s rows or a rewrite.
- The exact wording of the new-engine notice and the too-old refusal, in the style of arc's existing messages.
- Which tests assert on 1.5.x literals and how each moves (MockEngine defaults, pin keys, recorded stdout in tests/duckdb_reader_switch.rs, the v1.5.4 header of tests/fixtures/signups.duckdb, which 2.0 reads and arc opens read-only).
