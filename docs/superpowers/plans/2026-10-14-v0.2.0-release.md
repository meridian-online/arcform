# arcform v0.2.0 Release Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Ship arcform's first release, v0.2.0, so that a stranger can install `arc` in one line, or from crates.io, with a complete and correct `arc mcp` server.

**Architecture:** The plan is seven pull requests, built in order. The first three complete the MCP surface: the stdout fix, version negotiation and annotations, `protocol_create`, table describe, and the read-only query. A single new module, `src/inspect.rs`, holds the describe and query logic, and both the command-line verbs and the MCP tools call it. The fourth pull request adds the release machinery: bundled DuckDB, the crates.io packaging, and a tag-guarded workflow modelled on finetype's. A fifth goes to the install repo, and the last two cover the README and the changelog roll. Hugh pushes the tag. A web-repo pull request follows the tag.

**Tech Stack:** Rust 2024, `duckdb` crate (in-process, read-only connections), hand-rolled JSON-RPC 2.0 over stdio, GitHub Actions, Python 3 (stdlib only) for the tag check, POSIX sh for `install.sh`.

**Branches:** the spec and this plan reach `main` through their own docs-only pull request from `plan/v0.2.0-release`, which Hugh merges first, so each build branch below starts from `main` with both present. Pull request G deletes them. The tracking issue's existing children cover Task 1 (stdout), Task 4 (describe) and Task 5 (query); each other task has its own child.

**Spec:** `docs/superpowers/specs/2026-10-14-v0.2.0-release-design.md`. Read it before starting any task. It records Hugh's decisions and the calls made on his behalf.

## Global Constraints

- **Names.** The command stays `arc`. The package and library become `arcform` in Task 7. Until then the library is `arc`, so tasks before Task 7 write `arc::` and Task 7 renames them.
- **Release features:** `mcp,bundled-duckdb`. Release targets: `aarch64-apple-darwin`, `x86_64-apple-darwin`, `x86_64-unknown-linux-gnu`, `aarch64-unknown-linux-gnu`. Linux legs run on Ubuntu 22.04 (glibc 2.35). There are no Windows or musl builds.
- **Tag shape** `v[0-9]+.[0-9]+.[0-9]+`. The check script's exit codes: 3 (wrong shape), 4 (version differs from `Cargo.toml`), 5 (no `## [X.Y.Z]` heading), 6 (empty section), 7 (wiring), 8 (rehearsal), 2 (cannot run), 1 (self-test failed). It also refuses a notes section over 120,000 characters, with exit 6 and its own message.
- **MCP protocol versions allowed:** `2025-06-18` and `2025-11-25`. The newest is `2025-11-25`.
- **Describe** returns 5 sample rows. **Query** caps at 100 rows by default.
- **Asset names:** `arc-<tag>-<target>.tar.gz`, with `<archive>.sha256` beside each in `hash  filename` form and the binary at the archive root.
- **DuckDB:** one 1.5.x version across the `duckdb` crate, `DUCKDB_VERSION` in `ci.yml`, and `src/vetted_extensions.json`. Use the newest version that has a published `duckdb` crate (1.10506.0 is DuckDB 1.5.6).
- **Public repo:** no private planning ids or private repo paths in code, docs, commits or pull-request text. Use British English in prose.
- **On Hugh's Mac, run one cargo build at a time.** Local builds need `DUCKDB_LIB_DIR` pointing at a libduckdb unless built with `bundled-duckdb`.
- **Gate before each commit:** `cargo fmt --all --check`, `cargo clippy --all-targets --features mcp -- -D warnings`, and the tests the task touches. CI is the full gate.
- **Agents never merge, never push to `main`, and never push tags.**

## Review Focus

1. **A Protocol whose database another process holds open for writing** (a run in progress, or the app). Describe and query should fail with a message saying the database is in use, not hang or panic. The test goes in Task 4: `describe_while_locked_is_refused_with_message`.
2. **A table or column name that needs quoting** (mixed case, a space, a reserved word such as `order`). Describe must quote identifiers and not interpolate them raw. Test in Task 4: `describe_quotes_identifiers`.
3. **A SELECT that DuckDB serialises but that still writes or reaches out**, such as `SELECT * FROM query('CREATE TABLE x(i INT)')`. The read-only connection must stop it and the file's bytes must stay unchanged. Test in Task 5: `query_side_effect_inside_select_is_stopped`.
4. **A `protocol_run` child whose output is large** (a command step printing megabytes). Pipes must be drained while the child runs, or it deadlocks. The tail attached to an error is bounded. Test in Task 1: `protocol_run_survives_large_child_output`.
5. **`install.sh` on a machine with no `duckdb`, or with no `~/.local/bin` on `PATH`.** The script installs and then warns, naming the step to take. It does not fail. Test in Task 8: `install.sh` self-test run under `sh` with `PATH` stripped.

**Files:**

- Modify: `src/cli.rs` (`SqlCmd::Query { sql: String, #[arg(long, default_value = ".")] dir: PathBuf, #[arg(long, default_value_t = 100)] limit: usize }`)
- Modify: `src/mcp/hero.rs` (tool `sql_query`, args `sql` (required), `dir`, `limit`, `READ_ONLY`)
- Create: `tests/sql_query.rs`

**Interfaces:**
- Consumes: `open_read_only` from Task 4.
- Produces: `pub(crate) fn query(dir: &Path, sql: &str, limit: usize) -> Result<serde_json::Value>`, returning:

```json
{"results":[{"statement":1,"columns":[{"name":"i","type":"INTEGER"}],
  "rows":[{"i":1}],"row_count":1,"capped":false,"rows_held_back":null}],
 "keep":"to keep a query as a step: arc sql record '<statement>' --name <name>"}
```

- **The gate (an algorithm the tests don't fully determine):** before anything runs, ask the read-only connection `SELECT json_serialize_sql(?::VARCHAR)` for the whole text. If the answer's `error` is true, or any statement in it is not a SELECT node, refuse the whole batch with `only read-only SELECT statements can be queried; refused before anything ran: <DuckDB's message>`. `json_serialize_sql` serialises SELECT statements only, which is what makes it the gate. The read-only connection is the backstop.
- **Each statement** is split with DuckDB's own split (`duckdb_statement_count` and its splitter in `src/record.rs`; reuse, don't re-parse). Types come from `DESCRIBE <stmt>`. Rows come from `SELECT to_json(t) FROM (<stmt>) t LIMIT <limit+1>`. If `limit+1` rows come back, set `capped: true`, keep `limit` rows, and set `rows_held_back` from `SELECT count(*) FROM (<stmt>)` minus `limit`.
