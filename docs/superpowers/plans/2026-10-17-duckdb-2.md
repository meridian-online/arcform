# arc on DuckDB 2.0 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** arc 0.2.2 links DuckDB 2.0, runs SQL steps on a 2.x DuckDB command line, and reads each step's SQL through DuckDB 2.0's own tokens and parse trees for both its asset graph and its refusals.

**Architecture:** The `duckdb` crate and every pinned DuckDB version move to 2.0.0 in one step, and the accepted CLI range becomes `>=2.0, <3`. The DuckDB reader (`src/duckdb_lineage.rs`) becomes the default asset-graph reader behind a parity gate, with sqlparser-rs as the per-statement fallback. The refusals in `src/engine.rs` keep arc's own command-line layer (`cli_batches`), re-derived from 2.0's shell, but take their tokens from `sql_tokenize` in place of the copied 1.5.5 lexer.

**Tech Stack:** Rust 2024, duckdb-rs `=1.20000.0` (DuckDB 2.0.0), the DuckDB 2.0.0 command line, GitHub Actions.

**Spec:** `docs/superpowers/specs/2026-10-17-duckdb-2-design.md`. Read it before any task; its "Decisions" section carries the rulings each task cites.

A developer build links the library through `DUCKDB_LIB_DIR`, so point it at a 2.0.0 libduckdb (`libduckdb-osx-universal.zip` from the v2.0.0 release) or unset it so the crate downloads its own. Never leave it pointing at Homebrew's 1.5.6.

## Global Constraints

- Crate: `duckdb = "=1.20000.0"` (or the newest `1.20000.x` on the build day). Never set `default-features = false` on it, because arc's FFI in `src/record.rs` needs `capi-v1`.
- `SUPPORTED_ENGINE_RANGE = ">=2.0, <3"`; `OLDEST_ENGINE = "2.0.0"`.
- `DUCKDB_VERSION: v2.0.0` in `.github/workflows/ci.yml` and `text-embed-parity.yml`; `DUCKDB_RECOMMENDED="v2.0.0"` in `scripts/install.sh`; `"duckdb_versions": ["v2.0.0"]` in `src/vetted_extensions.json`.
- Every DuckDB process arc starts itself carries `DUCKDB_AGENT_MODE=0`. A `command:` step's environment is left alone.
- No 1.5 compatibility settings are ever set (`regex_match_operator_semantics`, `error_on_division_by_zero`, `lambda_syntax`, `order_by_non_integer_literal`).
- `arcform.yaml` gains no field.
- Each rule copied from DuckDB's source cites the v2.0.0 file it came from, as the 1.5.5 rules cite theirs.
- Messages follow arc's existing style: full sentences, naming the step, the file and the line.
- Release version: 0.2.2. The version bump and the changelog roll are done by the `release` skill after the branch merges. This branch only adds `[Unreleased]` entries.
- Before each commit: `cargo fmt --check`, `cargo clippy --all-targets -- -D warnings`, and the task's focused tests. CI is the full gate.

## Review Focus

1. **A step file with CRLF line ends, a byte-order mark or a zero-width space.** The refusals should still find an `INSTALL … FROM community` in it, and the asset graph should read it as with LF. Tested in Task 4.
2. **`ARC_DUCKDB_BIN` names a different 2.x patch from the one on PATH.** The reader and the refusals should ask the program the steps run on, not PATH and not the linked library. Tested in Task 3.
3. **A large step file (a 5 MB `INSERT … VALUES`).** It should be tokenised and read without a pipe deadlock and within seconds, not refused as unreadable. Tested in Task 4.
4. **The newest run record is unreadable** (truncated JSON, or an older contract without `duckdb_cli`). The run should go ahead with no error, and the notice compares against the newest record that is readable and names `duckdb_cli`; with none, no notice. Tested in Task 9.
5. **The user's `~/.duckdbrc` sets `.mode markdown` or prints text.** arc's own answers (`ask_duckdb`, the reader) should still parse, and a step's failure should still be detected by exit status. Tested in Task 3.

**The dev-build rule** (The maintainer's ruling, 2026-10-23). Homebrew's DuckDB 2.0.0 is built from the v2.0.0 commit (`d54cbbe3df`) but reports `v2.0.0-dev88614 (Development Version) d54cbbe3df`. `parse_version_output` keeps the pre-release, and semver matches a pre-release only against a comparator on the same major.minor.patch, so both arc's range and a Protocol's `engine_version: ">=1.0"` refuse it. Hold a table of release tags and their commits (`v2.0.0` → `d54cbbe3df17e8e5ce68312f483b4155836112aa`, from `gh api repos/duckdb/duckdb/git/ref/tags/v2.0.0`); when the version carries a pre-release and the source id printed after it is a prefix of the commit of the tag for that major.minor.patch, the engine's version is that release, everywhere arc compares it: arc's range, the Protocol's `engine_version`, the extension pin keys, and the new-engine notice (Task 9). The run record keeps the raw string. Such a build looks community extensions up under its commit hash (`community-extensions.duckdb.org/d54cbbe3df/osx_arm64/…`), which the registry does not serve, so when it is about to run a Protocol whose SQL installs a community extension, arc prints one warning before the first step: this DuckDB build (`v2.0.0-dev88614`) cannot download community extensions, and DuckDB's own release binary (the install script's, or `github.com/duckdb/duckdb/releases/tag/v2.0.0`) can. The warning does not stop the run.

- Produces, in `src/duckdb_tokens.rs`:
  - `pub(crate) struct Token { pub start: usize, pub token_type: String, pub word: String }`
  - `pub(crate) struct FileTokens { pub version: String, pub batches: Vec<BatchTokens> }`
  - `pub(crate) struct BatchTokens { pub lines: Vec<usize>, pub tokens: Vec<Token> }`
  - `pub(crate) fn tokenize_file(program: &DuckDbProgram, file: &[u8]) -> Result<FileTokens, duckdb_lineage::Refusal>`: splits with `engine::cli_batches`, then asks one DuckDB process for every batch's `sql_tokenize`, one `SELECT … FROM sql_tokenize('<batch>')` per batch in one script.
  - `pub(crate) fn to_tok(batch: &[u8], tokens: &[Token]) -> Vec<(Tok, usize)>`: classifies by the token's text, never by `token_type`, following the reader's rule. A word opening with `'`, `E'`/`e'` or `$tag$` becomes `Tok::Str` with its content unescaped. One opening with `"` becomes `Tok::Word { quoted: true }` with `""` undoubled. A letter or `_` start becomes `Tok::Word { quoted: false }`. A token whose text opens with `--` or `/*` is a comment and is dropped (text, as the rest of the rule; `token_type` is not read). Anything else becomes `Tok::Other` per character. The line is the batch's line at the token's `start`.
  - `pub(crate) struct TokenCache`: keyed by the SHA-256 of a file's bytes, so a file read again unchanged is not asked again (spec goal 5).
- Consumes: `DuckDbProgram` and `AGENT_MODE_ENV` (Task 3).
- `scan_extension_sql(file: &[u8], tokens: &FileTokens) -> Vec<(ExtensionSql, usize)>`: the token stream replaces `lex_sql`; `scan_tokens`, `scan_run_time_sql` and `unread_calls` keep their signatures.
