# `arc test` Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** `arc test [name]` runs a Protocol's real steps in a temporary copy, with checked-in fixture files standing in for its fetches, and asserts each test in `tests.yaml` either succeeds with its checks passing or fails with a given message.

**Architecture:** A new module `src/protocol_test/` reads `tests.yaml`, works out for each test which steps a fixture replaces and refuses a test that would reach the network, makes a copy of the Protocol beside it, rewrites the copy's `arcform.yaml` (fixtured and publishing steps removed, the test's inline checks appended as `check:` steps), places and breaks the fixtures, and runs `arc run` on the copy as a child process from arc's own executable, as `protocol_run` in `src/mcp/hero.rs` already does. The outcome comes from the child's exit status, its `error:` line and the copy's run record. Nothing in the runner changes except one variable that lets a test hand it `measure_history`.

**Tech Stack:** Rust 2024, clap, serde_yaml, the `zip` crate already in `Cargo.toml` (reading an xlsx's sheet list and dimension), DuckDB's command line for fixture breaks, the linked DuckDB library for reading a `measure_history` CSV.

**Spec:** `docs/superpowers/specs/2026-11-15-protocol-checks-and-tests-design.md`, section "Protocol tests". `docs/ARCHITECTURE.md`'s "Checks and measures" section is the authority for the check steps this plan reuses.

## Global Constraints

- `risk:` is required on every test, and leads its failure output.
- A test never fetches data: an ingress step with no fixture refuses the test, naming the step; a step that reads a remote address refuses it the same way. Publishing steps never run in a test. Every other step runs as written, `uv` and `command:` steps included.
- `break:` is SQL over the fixture read as a table named `fixture`; for xlsx every cell as text, no header, a `row` column and one column per sheet letter; for CSV and JSON DuckDB's reader; written back in the same format by DuckDB's writer. No edit vocabulary in YAML.
- arc runs a control for every break: the same round trip with no statements, which must not fail with the expected message.
- With no `expect:`, a test asserts the run succeeds and every `checks:` query returns no rows.
- `arc test --junit <file>` writes JUnit XML, each failure's message led by its risk line. Exit code 1 when any test fails.
- Failure output shape, verbatim from the spec:

```
FAIL a moved definitions header is refused
  risk: BLS moves the header row and titles load into the wrong columns
  expected the run to fail with "header row has moved"; it succeeded
```

- Public repo: no Kata refs, private repo names or local paths in commits, PR text or tracked files.
- One cargo build at a time on this machine. Before each commit: `cargo fmt --check`, `cargo clippy --all-targets -- -D warnings`, and the tests the change touches. CI is the full gate.

## Rulings made while planning (Hugh away; each can be undone)

1. **The copy sits beside the Protocol**, as a hidden sibling folder `.<protocol-folder>.arc-test-<random>` in the Protocol's parent, not in the system's temporary directory. A Protocol reaches files outside its folder by `..` (the SOC 2018 Protocol runs `../../scripts/check_code_list.py` and `../../contracts/check_titles.sql`), and a sibling at the same depth resolves every such path to the same file without arc having to find them. It is removed after each test, pass or fail. The copy takes everything in the Protocol's folder except `build/` and the file `db:` names (and its `.wal`), so a test starts with no state and no earlier run records.
2. **The child is `arc run`, not the runner in-process.** It keeps `arc test`'s output to one line per test, gives each test a fresh process, and reads the run's outcome from the same record and exit status a user sees.
3. **Fixtured and publishing steps are removed from the copy's `arcform.yaml`**, edited as a `serde_yaml::Value` so every other key is kept. `depends_on:` names assets, not steps, so a removed step leaves the files it would have written as plain source files, which the fixtures are. With no `db:`, the copy's manifest gets `db: build/arc-test.duckdb`, so a test leaves no database in arc's data folder.
4. **A test's inline `checks:` become `check:` steps appended to the copy's manifest**, named `arc-test-check-<n>` (1-based), `severity: error`, with the test's `risk:`. The runner then refuses a query that is not exactly one query, gives it `measures` and `measure_history`, and records it, as for any check. `checks:` together with `expect:` is refused when `tests.yaml` loads.
5. **A fixture key is either a step name or an output path.** A step-name key needs a step whose outputs are exactly one file; an output-path key needs a step that produces that file, and every file output of that step must then be keyed. A fixtured step that produces a table is refused: a fixture stands in for a file.
6. **A fixture path is relative to the Protocol's folder** and must exist when `tests.yaml` loads.
7. **The failure message `fails_with:` matches** is the text arc printed after `error: ` on standard error, ANSI codes stripped. It is what the person running the Protocol reads.
8. **The control runs only for a break test that expects a failure.** A break test that expects success has nothing for a control to rule out.
9. **xlsx round trip.** arc reads the workbook's sheet names (`xl/workbook.xml`) and the sheet's used range (`<dimension ref>` in its worksheet XML, or the furthest `<c r=…>` when there is none) with the `zip` crate, then has DuckDB read `range = 'A1:<end>'`, `header = false`, `all_varchar = true`, `stop_at_empty = false`, `sheet = '<name>'`, numbered by `row_number() OVER ()` under `SET threads = 1`, and writes back `ORDER BY row` with `HEADER false, SHEET '<name>'`. A workbook with more than one sheet is refused for `break:`: DuckDB's writer writes one sheet, and dropping the others silently would test a different file. `row` orders the rows; it is not a cell address, so a row inserted with `row = 5` after `UPDATE fixture SET row = row + 1 WHERE row >= 5` lands fifth. Formatting and cell types are not kept: every cell comes back as text, which a loader reading `all_varchar = true` cannot tell apart.
10. **CSV round trip** keeps the delimiter, quote and header DuckDB's `sniff_csv` finds, reading every column as text; **JSON** writes an array when the file's first non-blank byte is `[`, newline-delimited otherwise. Extensions: `.xlsx`, `.csv`, `.tsv`, `.json`, `.jsonl`, `.ndjson`, in any case. Anything else is refused for `break:`, saying to check in a second fixture.
11. **A break runs on the Protocol's DuckDB command line**, against a scratch database in the copy, after the same extension refusals a step's file goes through. It is Protocol SQL.
12. **`measure_history:` in a test** is a CSV (`run_id, run_at, name, value`) relative to the Protocol's folder, handed to the child as `ARC_TEST_MEASURE_HISTORY=<path>`; the runner then reads its rows in place of the run records, taken as given, with no window or parameter filter. The variable is arc test's own, documented as such.
13. **Lifecycle hooks run as written** in a test, like every other step that is not a publish.
14. **A test that is refused** (an ingress step with no fixture, a remote read, a bad fixture key, a break arc cannot round-trip) **is a failing test**, reported with its risk line and the refusal, and the rest still run. A `tests.yaml` that does not parse, or a missing one, stops `arc test` with exit 1 before any test.

## Review Focus

1. **A run that fails before any step** (a refused manifest, a missing parameter) leaves no run record. The outcome must still come from the exit status and the `error:` line, not panic on a missing record. Pinned in Task 4.
2. **An expected message that appears in the SQL arc prints**, not in the failure. Matching only the text after `error: ` and the control run cover it; the control test in Task 4 pins that a message which also appears without the break fails the test.
3. **A sheet whose last rows or columns are empty** must round-trip to the same shape, or every refusal test of a workbook loader tests a different file. Task 3 pins a round trip of a workbook with blank rows inside and a title block above, comparing every cell before and after.
4. **A test name that is not unique, or a `tests.yaml` naming a step that does not exist**, must be refused naming it, not ignored. Task 1 pins duplicates; Task 2 pins an unknown step or path.
5. **An interrupted `arc test`** must not leave a copy that a later run, or `git status`, trips over. The copy's name starts with `.` and holds `arc-test`; Task 4 pins that the copy is gone after a passing and after a failing test.
