# Changelog

All notable changes to arcform will be documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/),
and this project adheres to [Semantic Versioning](https://semver.org/).

Rationale for each change is recorded in the project's design notes and commit history.

## [Unreleased]

### Added

- **`arc operator record` and the `arc mcp` tool `operator_record` record an operator as a new step of a Protocol, and do not run it.** An operator step used to be written by hand into `arcform.yaml`. The step's `with:` is checked against the operator's schema first, and a block that does not fit is refused naming the field, with the Protocol untouched.
- **`arc mcp` gains `protocol_edit`, `history_list` and `history_restore`, matching `arc edit-protocol`, `arc history list` and `arc history restore`; `arc history list --json` prints the versions as JSON.** An agent could record steps but not change or undo one. `protocol_edit` and `history_restore` replace content, as do `protocol_write_file` and `report_write`, so all four are marked destructive, and what they replace stays in history. A `--file` path for history must stay inside the Protocol.
- **`arc protocol write-file` and the `arc mcp` tool `protocol_write_file` write `schemas/<name>.json`, `panels/<name>.yaml` or `README.md` in a Protocol.** These files used to be written outside arc and so left no history. The content is checked to read as its kind, a path outside the Protocol or any other file is refused with nothing written, `report.md` is left to `report_write`, and what the write replaces is kept in history.
- **`arc table profile` and the `arc mcp` tool `table_profile` profile a table in a Protocol's database with FineType.** The table's rows are copied, up to `--sample-size`, to a temporary CSV outside the Protocol, and `--format json` gives each column's type while `--format json-schema` gives a JSON Schema its rows pass. The profile of a table with no rows is said so, and a schema of one is refused.
- **`arc table validate` and the `arc mcp` tool `table_validate` check a table against a JSON Schema file in the Protocol, in DuckDB with FineType's extension.** The answer is `valid` and each column's rejects as JSON, and the command exits 1 when a row is rejected. It needs `FINETYPE_DUCKDB_EXT` to name the extension.
- **`arc panel check` and the `arc mcp` tool `panel_check` report each panel whose marks read a table or a column the Protocol does not make.** A misspelt column used to show only as an empty chart. One line per finding, and the command exits 1 when there is any.
- **`arc report write` and the `arc mcp` tool `report_write` write `report.md` beside a Protocol.** The prose is the author's, on standard input or in the tool's arguments; arc adds how the answer was derived, the charts and the run, from the newest run's record or the one `--run` names. A Protocol that has not run is refused, and a report already there is replaced, both versions kept in history.
- **The `arc mcp` instructions are rewritten as one guide: discover, record, run, check, present, and what each step may change.** They named each tool in a clause of its own; they now give the order of work and say that recording runs nothing, a run runs, and history undoes.
- **Five agent skills under `skills/` teach an agent the analyst workflow through arc: `using-arcform`, `scoping-an-analysis`, `profiling-and-typing-data`, `building-and-checking-a-protocol` and `presenting-findings`.** An agent had the tools but no method: when to stop and ask, how to type data before trusting it, how to read a run record rather than its exit status. Each skill scales its stage to the size of the task, shows every step as an `arc` command beside the matching `arc mcp` tool, records each analysis step into the Protocol, and ends with when to switch and a table of known traps.
- **`cargo test --features mcp --test skills` holds the skills to the binary.** Prose drifts from the tools arc has. The test checks every tool, argument, verb and flag a skill names against `arc mcp` and `arc --help`, checks each skill's frontmatter, and runs each skill's examples against small fixture Protocols; the notation is in the module doc of `tests/skills.rs`.
- **The `arc mcp` instructions outline the five stages of the analyst workflow, Scope, Profile, Build, Check and Present, each with the skill that covers it.** An agent connected without the skills now still learns the order of the work, and one that has them learns which to load.
- **`arc skills install` installs the five analyst skills into each agent found on the machine (Claude Code, Codex, Cursor, Gemini CLI and the shared `~/.agents/skills`), or into the agents and folder named with `--agent` and `--target`; `arc skills list` prints them.** The skills ship inside the binary, so the ones installed are always those of the arc that installs them. Each folder written holds a `.arc-skill` marker recording the arc version; only such a folder is replaced, whole, and a same-named skill the user wrote is refused, with nothing written into that agent's skills folder while the other agents still install. With no agent found, the command prints where it would install and exits 1. Codex, Cursor and Gemini CLI all get the shared `~/.agents/skills`, which each of them reads, so a machine with several of them holds one copy of each skill rather than two.
- **This repository is a plugin for Claude Code, Codex and Cursor, and an extension for Gemini CLI, bringing the five analyst skills and connecting `arc mcp` in one install.** An analyst had to install the skills and add the server by hand in each agent. A plugin installs the skills of a released arc: the marketplace names the plugin at the release tag `v<version>`, not the default branch. Each agent's manifest is generated from `plugin/plugin.meta.json` by `scripts/generate-plugins.py`, with the version from `Cargo.toml`, and `tests/plugin_manifests.rs` fails CI when a committed manifest differs from what it generates. `skills/using-arcform/references/agents/` gives each agent's notes, and one for a desktop chat app: how it loads the skills, how to connect `arc mcp`, and what it calls the arc tools.
- **`eval/analyst-workflow/` is the release eval for the analyst skills: ten analyst tasks on public datasets, a preflight, a runbook and a scoring sheet.** The structural test proves a skill names only what arc has, not that an agent picks arc up and follows the method. Before each release, a maintainer runs every task in Claude Code, Codex and a desktop chat client with only `arc mcp`, with prompts that never name arc, and scores whether the agent chose arc unprompted and ended with the seven outcomes the skills promise; failures are clustered by cause and fixed with the smallest skill edit, and the scored sheet goes in the release pull request.
- **The catalogue holds `hide-column`, which leaves one column out of a table.** `arc operation record hide-column --on orders --name no_note --arg column=note` writes a model whose query is `SELECT * EXCLUDE (note) FROM orders`, a line to each clause. The column is a name, not SQL: arc writes it bare where DuckDB reads it bare as that column and in double quotes otherwise, so `order` or `my col` is hidden as named, and an empty or blank name is refused.
- **The catalogue holds `rename-column`, which gives one column of a table a new name.** `arc operation record rename-column --on orders --name relabelled --arg column=note --arg to=label` writes a model that copies `orders` and then runs `ALTER TABLE relabelled RENAME COLUMN note TO label`, so the column keeps its place and every row, and a `column` the table lacks or a `to` it already has fails the run instead of renaming nothing or suffixing the name. Both names are names, not SQL, written as `hide-column` writes its column, and an empty or blank one is refused.

### Changed

- **The `profiling-and-typing-data` skill now names all five FineType tools `arc mcp` serves, `generate` among them, and the README gives the command that builds `arc` with `arc mcp` from a checkout and says where FineType's tools are taught.** The skill's FineType reference listed `finetype generate` as a maintainer's command although `arc mcp` serves it as a tool, and did not say that the `profile` tool cannot give a Data Package. The README built `arc` only from crates.io.
- **The `brewtrend` example fetches its six files with the `http_fetch` operator instead of `curl` command steps, and every step carries a description.** The fetches keep their URLs, output paths and 24-hour preconditions, and the example no longer needs `curl`.
- **The library example in the README loads `examples/almanac` instead of `examples/brewtrend`.** brewtrend's `http_fetch` steps need the `http-fetch` feature, which `default-features = false` turns off, so the example could no longer load it.
- **The `using-arcform` skill says a quick look still starts with `scoping-an-analysis` and ends with `presenting-findings`, loaded before the answer, and `scoping-an-analysis`'s quick-look example now offers the size for override.** An agent given a quick look loaded only `using-arcform` and skipped the plan playback, the offer to override the size, the next steps and the findings panel. Only profiling and building are cut short.
- **The `presenting-findings` skill asks for at least one next step offered outright, and says opening, re-running or sharing the Protocol is not one; `scoping-an-analysis`'s rule for a quick look now says the message giving the size ends with the offer to override it.** In the eval runs recorded in `eval/analyst-workflow/dry-run.md`, half of the ten unattended runs answered without offering anything to do next beyond opening, re-running or sharing the work, and no quick look offered its size for override. After the edits every run that loaded `presenting-findings` offered a next step; no quick look offered the override yet.
- **The `presenting-findings` skill teaches what to do when a chart would colour more than eight series: highlight the one to three the answer is about and grey the rest, fold the tail into `Other` in a step, or split the series across panels.** Brightfield's palette has eight colours and repeats them past eight. `references/panels.md` gives a runnable example of the highlight, with an explicit `colorDomain` and `colorRange`, and says which two-layer and facet forms Brightfield does not draw.
- **The tests that need the finetype CLI, `tests/table_profile.rs`'s CLI tests and the skills' `needs=finetype` examples, now run in CI, and fail when it is missing.** CI installs finetype 0.6.62 and sets `ARCFORM_REQUIRE_FINETYPE_CLI`; they used to skip there.

## [0.2.2] - 2026-10-24

arc 0.2.2 moves arc onto DuckDB 2.0. arc is a single binary that runs a data pipeline, a Protocol, from a YAML manifest of SQL and shell steps, and reads each SQL step to work out which tables it reads and makes. From this release it links DuckDB 2.0, runs SQL steps on DuckDB 2.0's own `duckdb` command line, and works out each step's inputs and outputs from DuckDB's own parse of the SQL rather than a copy of DuckDB's grammar. The install script now installs DuckDB 2.0.0's release build for you when no suitable `duckdb` is found, and `arc run` warns when a Protocol last ran on a different DuckDB, since DuckDB 2.0 changes some results without an error.

**arc now needs DuckDB 2.0.** It links DuckDB 2.0 and runs SQL steps only on a 2.x `duckdb` command, and a 1.x one is refused. If you use DuckDB 1.5, stay on arc 0.2.1: `cargo install arcform --version 0.2.1`. `cargo install` and the install script treat this release as a compatible upgrade of 0.2.1, so they will move a DuckDB 1.5 user onto it unless the version is pinned.

### Added

- **`arc run` says when a Protocol runs on a different DuckDB from its last run.** When the newest readable run record names a DuckDB whose major or minor version differs from the one about to run, one notice on standard error before the first step says `this Protocol last ran on DuckDB <previous>, and this run uses DuckDB <current>; results can differ between them`, and for a move from 1.x to 2.x it names the four result changes listed under Changed. The run goes on. A Protocol with no run record draws no notice.
- **Homebrew's DuckDB 2.0.0 passes arc's version check as 2.0.0.** It prints `v2.0.0-dev88614 (Development Version) d54cbbe3df`, a development version built from the commit of the v2.0.0 release, which arc's range would otherwise refuse. arc treats a development build of a release's commit as that release everywhere it compares versions: its own range, a Protocol's `engine_version:` and the extension pins. Such a build cannot download community extensions, so a run of a Protocol that installs one warns before the first step, naming DuckDB's installer for the release build, which can. A run with a SQL step on it is still refused, because that build lacks DuckDB's autocomplete extension: see the next entry.
- **`arc run` names a DuckDB built without its autocomplete extension, and the install script installs DuckDB's release build.** arc reads each SQL step's tokens from DuckDB's `sql_tokenize`, which lives in that extension, and a `duckdb` built without it, such as Homebrew's 2.0.0 at the time of writing, gave no tokens for any file, so every SQL step was refused as one whose tokens arc could not read. A run on such a DuckDB is now refused before any step with exit 2 and one message: which DuckDB, with its path and printed version, cannot read SQL into tokens and why, and the fix, `curl https://install.duckdb.org | DUCKDB_VERSION=2.0.0 sh`, then `~/.duckdb/cli/2.0.0` first on `PATH` or `ARC_DUCKDB_BIN=~/.duckdb/cli/2.0.0/duckdb`. arc probes for the tokenizer, so a build that gains the extension runs. A command that reads the graph without running it, such as `arc sql record`, still reads it with arc's own parser, and its warning names the same cause and fix. After installing arc, the install script installs DuckDB's v2.0.0 release build with DuckDB's own installer when no `duckdb` is on `PATH` or the one there cannot read SQL into tokens, and says what to put on `PATH` when another `duckdb` comes first; `ARC_SKIP_DUCKDB=1` leaves DuckDB alone.
- **Each statement in the run record says which reader read it,** in `read_by`: `duckdb`, `sqlparser` or `nothing`. A record written before this change has no `read_by`.

### Changed

- **arc runs SQL steps on DuckDB `>=2.0, <3` and refuses a 1.x `duckdb` even with `ARC_ALLOW_UNTESTED_ENGINE=1`.** arc opens a Protocol's database through the DuckDB 2.0 library it links, and a database file DuckDB 2.0 creates cannot be opened by DuckDB 1.x, so a Protocol could not move between a 1.x command line and arc. The refusal names arc 0.2.1 as the release for DuckDB 1.5. The variable still lets a run go ahead on a 2.x pre-release or a 3.x, with a warning, and arc reads a 3.x's SQL tokens under it as it reads a 2.x's. The install script, CI and every pinned DuckDB version in the repository name v2.0.0, and use DuckDB 2.0's renamed release downloads (`duckdb-cli-<os>-<arch>.tar.gz` and `duckdb-shared-libs-<os>-<arch>.tar.gz`).
- **DuckDB 2.0 changes four results without an error, so a Protocol written for DuckDB 1.5 can give different answers on 2.0.** `~` and `!~` match part of a string, where 1.5 matched the whole string; integer `//` and `%` by zero raise an error, where 1.5 gave `NULL`; `x -> …` lambdas are rejected, and `lambda x: …` is the form 2.0 takes; and `ORDER BY` a non-integer literal is rejected. arc sets none of DuckDB's settings that bring the 1.5 behaviour back. The two example Protocols now say `engine_version: ">=2.0"` and write their lambdas as `lambda x: …`, and the Python operators depend on `duckdb>=2,<3`, since an operator that opens a Protocol's database or loads an extension must run the same major version.
- **The asset graph is read from DuckDB 2.0's own parse of each SQL step.** What each statement reads and produces comes from the DuckDB command line the step runs on, from the same tokens the extension refusals read. A statement DuckDB's reading cannot take, such as a `DROP` or a `PIVOT` DuckDB gives no tree for, is read by arc's own parser, sqlparser-rs; one neither can read draws `could not read statement <n> of <step> (<file>:<line>) — treating it as reading nothing`, and the other statements of the step are still read, where before the whole step was opaque. `ARC_SQL_READER=sqlparser` reads every statement with arc's own parser, as a way round a mistake in DuckDB's reading while it is fixed; `ARC_SQL_READER=duckdb` is the default, and any other value is refused. `arc run` refuses before any step runs when no DuckDB 2 answers, and refuses naming the step when DuckDB gives an answer arc cannot read for its file. A command that reads the graph without running it, such as `arc sql record`, reads it with arc's own parser when no DuckDB 2 answers, and says so once. A statement of a bare name, `tbl;`, which DuckDB 2.0's command line runs as `SELECT * FROM tbl`, reads `tbl`.
- **The extension refusals read each SQL file through DuckDB 2.0's own tokens**, which `sql_tokenize` gives without running anything, asked of the DuckDB that runs the step, in place of a lexer arc copied from DuckDB 1.5.5's source. What the command line does to a file before its parser sees it, such as skipping dot commands and `#` lines, is still arc's own reading, now taken from DuckDB v2.0.0's shell. A file DuckDB gives no tokens for, or tokens arc cannot read, is refused with exit 2, naming the step or hook; an empty file, or one holding only dot commands and `#` lines, has nothing to refuse. Two inputs are newly refused: an `INSTALL` of a name in backticks, which DuckDB 2.0 reads as a quoted name, and `INSTALL E'…\…'`, which DuckDB installs as a file of that name. A statement or string naming `current_dialect` is now refused too, as one naming `allow_parser_override_extension` already was, since a dialect an extension registers brings its own tokenizer and grammar; `enable_peg_parser`, which DuckDB 2.0 removed, is no longer looked for.
- **arc runs every DuckDB process it starts with `DUCKDB_AGENT_MODE=0`.** DuckDB 2.0's command line switches to markdown output, a row cap and a banner on standard error when it finds a variable an AI agent's harness sets, such as `AI_AGENT` or `CLAUDECODE`; arc then misread its answers and reported the banner as a step's error. SQL steps, hooks and arc's own questions of DuckDB now print DuckDB's normal output under an agent too.
- **`arc sql record` makes a table of a `DESCRIBE`, a `SHOW` or a `SUMMARIZE`, as it does of a `SELECT`.** DuckDB 2.0 parses and runs `CREATE TABLE … AS DESCRIBE …`, so the recorded step opens with the `CREATE OR REPLACE TABLE` line and makes a table of the step's name; on DuckDB 1.5 the statement was written as typed.
- **The run record's statement byte ranges split where DuckDB splits the step.** They used to be dropped when arc's own split and its parser counted the statements differently, such as for a `;` inside a `$$…$$` string.

### Fixed

- **The bundled build links on aarch64 Linux.** With `--features bundled-duckdb`, the DuckDB 2.0 crate links its extension-registration code after DuckDB itself, and GNU ld, the default linker there, failed with `undefined reference to duckdb_register_static_extensions`, so `cargo install arcform --features mcp,bundled-duckdb` failed on aarch64 Linux. arc's build now tells the linker to keep that function. A crate that links arcform's library with `bundled-duckdb` on Linux needs `-C link-arg=-Wl,-u,duckdb_register_static_extensions` until the DuckDB crate orders its archives itself.
- **arc depends on opendal 0.58.2, in place of 0.58.0, which was yanked from crates.io.** A build with the `opendal` feature no longer warns about a yanked dependency.

### Removed

- **Nine extensions leave the vetted list, which is re-vetted on DuckDB v2.0.0.** `dta`, `mlpack`, `onager` and `stats_duck` have no v2.0.0 build in the community registry. `http_client`, `minijinja`, `rapidfuzz`, `stochastic` and `textplot` have one, but it refuses to load: from DuckDB 2.0 those five are distributed from the Query.Farm repository, which arc does not allow a Protocol to install from. A Protocol that installs any of the nine `FROM community` is refused. The seven that stay are `finetype`, `h3`, `splink_udfs`, `subtoken`, `us_address_standardizer`, `webbed` and `zipfs`, each re-run on v2.0.0, and their entries now name v2.0.0.

## [0.2.1] - 2026-10-17

### Fixed

- **The `arc mcp` tools `taxonomy` and `generate` no longer offer a `priority` argument.** finetype 0.6.62 removed the `--priority` flag both passed it to, so a call that set it failed; finetype has no replacement for it. CI now installs finetype 0.6.62 and calls the five finetype tools through `arc mcp` with every argument their schemas advertise, so an argument finetype stops accepting fails arc's CI.
- **With `ARC_SQL_READER=duckdb`, a step holding a statement DuckDB warns about when parsing it, such as `PRAGMA threads = 4`, is read again.** Recent DuckDB 2.0 previews print the warning into the parse arc asks for, and the step was refused as unreadable; arc now asks with DuckDB's logging off.

## [0.2.0] - 2026-10-15

arc is local-first data analysis in one binary, for people and their agents. The work is kept as a Protocol, a folder holding `arcform.yaml` and its SQL, which `arc run` runs again from the top; arc reads each SQL step for the tables it reads and makes, so it knows how the steps connect and which ones a change makes stale. This is the first published release.

In the box: fetching and unpacking data, SQL modelling on DuckDB, operators for text embeddings, UMAP maps, entity resolution, Parquet export and DuckLake publishing, FineType semantic types and Frictionless Data Package descriptors, a vetted and pinned list of DuckDB community extensions, and a local history of every change to a Protocol, with a log that travels with the folder through git.

Install a release build for macOS or Linux (x86_64 and aarch64) with `curl -fsSL https://install.meridian.online/arc | bash`, or build from source with `cargo install arcform --locked --features mcp,bundled-duckdb`. arc runs SQL steps with the `duckdb` command, so put one on `PATH` (v1.5.6 recommended).

Then `arc mcp` serves arc to an AI agent over the Model Context Protocol. An agent can create a Protocol, record steps into it, describe a table, run a read-only query and run the Protocol, and what it leaves behind is a versioned Protocol anyone can re-run rather than a scratchpad.

### Added

- **arc has release binaries and an install script: a version tag builds it for macOS and Linux, on x86_64 and aarch64, and `curl -fsSL https://install.meridian.online/arc | bash` installs it.** Using arc used to mean building it from source against a system DuckDB. Each `vX.Y.Z` tag now builds `arc` with MCP and DuckDB compiled in, checks that each binary starts, and publishes checksummed archives, both crates on crates.io and the install script; the Linux binaries need glibc 2.35 or later. A first job refuses a tag that differs from `Cargo.toml`'s version or has no changelog section, and `docs/RELEASE.md` describes the process.
- **`arc sql query '<sql>'` and the `arc mcp` tool `sql_query` run SELECT statements against a Protocol's database and return what they give, without changing it.** An analyst or agent no longer has to open the database in another tool to look at a run's tables. The answer is JSON, one result per statement, with columns, types, up to `--limit` rows (100 by default) and how many rows were held back; text holding anything but SELECTs is refused before anything runs, and the database is opened read-only. A HUGEINT, such as the `sum()` of integers, is a number while a double holds it exactly and a string of its digits beyond that, and `keep` names both `arc sql record` and the `sql_record` tool for keeping a query as a step. A SELECT can still read the files and URLs it names, so the tool is marked open-world.
- **`arc table describe <table>` and the `arc mcp` tool `table_describe` say what a table in a Protocol's database holds, without changing it.** The JSON answer gives the row count, each column's name, type and null count, and five sample rows. A value JSON cannot hold exactly, such as `NaN`, a 38-digit decimal or a HUGEINT beyond ±2^53, comes back as a string rather than failing or being rounded, and a missing database or table is refused with a pointer to what is there. The database is opened read-only, but a view over a file reads that file, so the tool is marked open-world.
- **`arc mcp` gains `protocol_create`, which makes a new Protocol as `arc create-protocol` does.** An agent no longer has to ask for the Protocol to be made by hand before it records steps into it. The tool writes the same files the verb writes and refuses a folder that already holds an `arcform.yaml`.
- **`arc mcp` negotiates the protocol version from a fixed set, marks each tool read-only or not, and opens its instructions with when to use arc.** The server used to echo whatever version a client asked for, claiming revisions it was never written against; it now answers `2025-06-18` or `2025-11-25`, and the newest for anything else. Each tool carries `readOnlyHint`, `openWorldHint` and `destructiveHint`, so a client can tell a look from a write: `protocol_run` is marked destructive and open-world, since a Protocol can reach the network.
- **Local history records a save with the merge off, through `LocalHistory::record_save_unmerged` and `record_save_unmerged_for_file`.** A library caller that wants two saves seconds apart to list as two entries no longer has to record the second as a checkpoint. Everything else about a save, its log line included, is as before.
- **A Protocol folder renamed, moved or copied on the same machine keeps the versions local history recorded for it, found again through the log the folder carries.** `arc history list` in a renamed folder used to say there was no history yet, because snapshots are keyed to the folder's path. arc now reads the folder's `arcform-log.txt` and carries each version it names over to the new path; a copy and its original share their history up to the copy and diverge after it.
- **A plain save of `arcform.yaml` writes a line to `arcform-log.txt` that names each step the save added, removed or changed.** A colleague reading the log used to see the steps an agent recorded and nothing of what the analyst changed by hand. arc now compares the save with the state before it, step by name.
- **`arc create-protocol`, `arc init` and `arc init --from-descriptor` write a `.gitignore` and a `.gitattributes` beside `arcform.yaml`, so a Protocol shared through git stages the right files and merges its log cleanly.** The `.gitignore` names `build/.arcform/` (the run records), a database inside the folder and its write-ahead log, and any database `--from-descriptor` copies in, so `git add --all` no longer stages machine state. The `.gitattributes` sets `/arcform-log.txt merge=union`, so two clones that each record a version keep both sides' log lines instead of stopping on a merge conflict. An existing file of either name keeps its lines, and a Protocol made before this change needs the line added by hand.
- **Each version local history records appends one line to `arcform-log.txt` in the Protocol's folder, naming the file, the time, the kind, the interface and the step, with no contents, so the record travels with the folder.** The record of which steps an agent wrote and which the analyst did used to sit in one machine's home directory, and a colleague who received the Protocol through git or a drive got none of it. Each line is one JSON object (the README names the keys), `git add` stages the log, and when the folder is read-only the version is still recorded, without a log line. `arcform::spec::LOG_FILENAME` names the log.
- **`arc run` warns about a file beside `arcform.yaml` that may be a copy a synced drive set aside, and does not read or merge it.** When two people save a Protocol in a synced folder, Dropbox, OneDrive or Google Drive keeps one save and renames the other, and a colleague's steps went missing from the run without a word. Each file whose name starts with `arcform`, ends in `.yaml` and is not `arcform.yaml` now draws a warning, which the run record also carries in `run.protocol.possible_copies`, so `protocol_run` returns it too.
- **Local history records a text that was never written to its file as a third kind of entry, `unsaved`, beside a save and a checkpoint.** An editor's buffer closed without saving had nowhere to be kept. `LocalHistory::record_unsaved_for_file` records it without touching the file, `arc history list --file` shows it and `arc history restore` writes it. `HistoryKind` gains a variant, so a `match` over it needs a third arm.
- **`arc sql record` and the `arc mcp` tool `sql_record` record a SQL statement as a step of a Protocol, and do not run it.** A statement in hand used to become a step only by writing the model and the step by hand. A statement arc reads as a filter is recorded as the same `filter-rows` step `arc operation record` writes; any other statement DuckDB parses becomes a SQL step, a `SELECT` wrapped so the step makes a table of the step's name. Each recording is a version in `arc history`, and unparseable text, several statements, an unknown table or a duplicate name is refused with the Protocol untouched.
- **A run record names each extension the run's SQL installed or DuckDB loaded, with its repository, version and file hash, and the version and platform of the DuckDB the steps ran on.** Two runs of one Protocol that gave different results could not be told apart by their records when an extension's build had changed between them. `run.engine` gains `duckdb_cli`, `platform` and `extensions`; arc asks each SQL step's own DuckDB process which extensions it loaded, ones DuckDB loaded by itself included, and recording never refuses or changes a run. `docs/VETTED_EXTENSIONS.md` says this under "What a run records".
- **`arc sql recognise` and the `arc mcp` tool `sql_recognise` answer what a SQL statement is read as.** A tool no longer needs a SQL parser of its own to tell a filter typed as SQL from the same filter recorded by name. A `SELECT *` from one table with a `WHERE` and nothing else is answered `filter-rows` with its table and condition, and any other statement DuckDB parses is answered with `operation: null`. It writes nothing and runs nothing.
- **`SpecEdit::Nest` moves entries of a YAML mapping under a new key, as the one mapping of a new sequence, and `SpecEdit::Lift` puts them back, each keeping the comments among the lines it moves.** A tool editing a chart file could not wrap existing lines, such as a chart's `plot:` and `height:` under a `vconcat:`, without handing back the whole block and losing the author's comments. A lift undoes a nest exactly, and either is refused with a reason when it cannot apply cleanly. Neither has an `arc edit-protocol` verb yet.
- **A step in `arcform.yaml` may carry `description:`, one line saying what the step does and why, and `arc operation record --description` and `arc mcp`'s `operation_record` write the one they are given.** A Protocol handed to someone else, or written by an agent, could explain a step only in a YAML comment. A description is never run; `arc edit-protocol add steps[N] description "<TEXT>"` gives an existing step one, and an older arc ignores the key.
- **Each version local history records names the way arc was reached when it was written, and `arc history list` prints it beside the version.** An analyst could not tell a step an agent recorded from one they recorded themselves. A version now names `terminal`, `mcp`, or a word a library caller gives for itself through `LocalHistory::reached_by(HistoryWay::new("app")?)`; a version written before this change prints `not recorded`.
- **`arc operation describe` describes each of arc's operators in the shape it describes an operation, and a description names what a step reads and writes by role: `reads` and `writes` replace `applied_to`.** An agent at the terminal could not ask what an operator such as `umap_project` reads, writes or takes. `arc operation describe <name>` and `operation_describe` now answer for an operation or an operator with `long_name`, `summary`, `reads`, `writes` and `parameters`, each role saying its kind: a table, a file, a directory, a pattern or a column.
- **An operator's description states, as `default` in its `parameters`, each value its step takes when the key is left out, and a test fails when a stated default is not the value taken.** Six of the eight such defaults were stated only in prose; each is now in the schema, such as `parquet_export`'s `compression: "zstd"` and `umap_project`'s `neighbors: 15`.
- **`arc run` checks each SQL step's and hook's file again just before it runs, and refuses it on what the check before the run refuses.** A step that wrote over a later step's file used to run whatever that file installed, unchecked. A step refused there fails the run with exit 2, as a failed step does. It is not a sandbox: a `command:` step can still start a DuckDB of its own.
- **`arc upgrade <name>` writes or replaces the pin of a community extension on the vetted list, from the build the community registry serves, for the machine's DuckDB version and platform.** An author used to copy a hash by hand into `arcform.yaml`, where a mistyped digit refused the next analyst's run. The command installs and loads the extension, writes its SHA-256 under `extensions:` with every other byte kept, and checkpoints the old file in `arc history`; a name off the vetted list is refused. Run it on each platform a Protocol runs on. `SpecEdit::Add` with an empty value now writes a bare `key:`.
- **`arc run` checks each community extension a Protocol installs against the SHA-256 its `arcform.yaml` pins, and refuses a run on which it differs.** The vetted list said which extensions a Protocol may install but not which build, so two runs could run different code under one name. A new top-level `extensions:` key holds the pins, by extension, DuckDB version and platform:

  ```yaml
  extensions:
    mlpack:
      v1.5.5:
        linux_amd64: <sha256>
  ```

  An extension with no pin draws a warning and runs, and a pinned file a step replaces during the run fails the run at its end. `arc run` also refuses a step that sets `extension_directory`, `extension_directories` or `home_directory`, which would install where the check does not look. An older arc ignores the key.
- **arc can read what each SQL step reads and produces from DuckDB 2.0's own parse of it, chosen with `ARC_SQL_READER=duckdb`.** A step arc's own parser cannot read, such as one using `ASOF LEFT JOIN … USING`, used to become an opaque node in the asset graph. With the variable set, `arc run` asks a DuckDB 2.0 build for each statement's tokens and parse tree and takes what it reads and produces from them; this needs the 2.0 preview, and so `ARC_ALLOW_UNTESTED_ENGINE=1` as well. With the variable unset every step is read as before.
- **Local history keeps a chart file's versions under that file, and `arc history list`, `show` and `restore` take `--file <FILE>` to work with them.** A file beside a Protocol, such as a chart under `panels/`, had no history of its own. Each `arcform::spec::LocalHistory` call that takes a Protocol folder has a `_for_file` twin, each file's history is bounded on its own, and a restore checkpoints the text it replaces so it can be undone.
- **arc's SQL introspection parses DuckDB's `INSTALL … FROM <repository>`, `FORCE INSTALL`, an empty-string `COPY` option, a `PRAGMA` with several arguments, and `SET VARIABLE`.** A step opening with any of these used to become an opaque node, so its tables never reached the asset graph and a downstream step could run against a stale table. Three of the bundled examples opened with `SET VARIABLE`, and all three now parse.
- **`arcform::spec::apply_yaml_edits` splices YAML text of any shape, not only a Protocol.** A chart file with no `name:` can now be edited with the same byte-preserving splice, comments kept; its one gate is that the result still loads as YAML. It is reachable with `default-features = false`.
- **`op: ducklake_publish@1` ends a Protocol by publishing its build into a DuckLake catalog, as one snapshot.** The step registers a copy of the built Parquet file, so the next build cannot break time travel to a published version, and publishing bytes the table already holds reports the existing snapshot rather than committing another. Credentials come from named environment variables, and a catalog on object storage is refused in this version.
- **`arc operation list`, `arc operation describe <long name>` and the `arc mcp` tool `operation_describe` say which SQL operations arc holds and what each takes.** An agent or a second application could not ask what operations exist or what one takes. `list` prints each long name with a one-line summary (`--json` as well), and `describe` prints what the step reads and writes and a JSON Schema of its parameters. The terminal and the tool read one catalogue, so they cannot disagree.
- **`arc operation record` and the `arc mcp` tool `operation_record` record an operation as a new step of a Protocol, from its long name, the table it applies to and its arguments.** `arc operation record filter-rows --on orders --name big_orders --arg where='amount > 100'` writes a generated model under `models/` and appends a step to `arcform.yaml`, leaving every other byte alone and running nothing. A condition is recorded only when DuckDB parses it as exactly one statement, so `amount > 100; DROP TABLE orders` is refused, and each recording is a version in `arc history`.
- **The catalogue holds a second operation, `sort-rows`, beside `filter-rows`, so a table can be ordered by name.** `arc operation record sort-rows --on orders --name by_amount --arg order_by='amount desc'` writes a model ending `ORDER BY amount desc;`, under the same one-statement check `filter-rows` applies.
- **`arc run` warns on a step whose SQL runs SQL it builds or writes while it runs, and runs the step.** The extension check reads SQL files before the run and cannot see SQL assembled for `query()`, run by `IMPORT DATABASE` or written to `~/.duckdbrc`; each of these now draws one warning naming the file and line. `docs/VETTED_EXTENSIONS.md` names what is still not checked.
- **`datapackage_describe@1.1.0` passes declared column types to finetype through a new `nominations:` key.** A declared type now reaches finetype and comes back marked `x-finetype-nominated`, instead of being hand-copied into `descriptor.overrides.json`. A step with the key needs finetype 0.6.60 or later and is refused before it runs on an older one. Editing the sidecar or the nominations file now re-runs `describe`, where a warm run used to keep a stale `datapackage.json`.
- **`embed_project` is split into `umap_project` and `text_embed`, because one name over two jobs made each reachable only through the other.** An analyst who wanted vectors had to compute a map they had not asked for, and one whose columns were already numbers, such as a longitude and a latitude, could not make a map at all. `umap_project@1` maps numeric and vector columns, with a new `metric:` (`euclidean` or `cosine`), and `text_embed@1` writes vectors and nothing else. `embed_project` is removed, not aliased, and a manifest naming it fails validation.
- **`umap_project` can place appended rows into a persisted fit instead of refitting the map, and writes `projection_fit_id` to say when two maps may be compared row for row.** Appending rows used to refit the whole map: measured at 3,000 real rows, a 5% append left a point sharing only 42% of its 20 nearest map-neighbours with the old layout, 39% at 20% and 36% at 50%, the same order as swapping the embedding model (a sibling figure from a different repository, which the checker does not pin). With `fit:` in a manifest, the first run saves the fit and later runs place new rows into it with `UMAP.transform`, leaving existing rows exactly where they were (scored against the 256-d embeddings, where a row's own fit recovers 30.3%, the ceiling, a full refit places a new row at 89-97% of the ceiling, 29.6-27.0%, and `.transform()` at 27.2-26.4%: 3 to 4 points under the ceiling and -0.2-2.6 points under the full refit, for a 3.6 MB pickled model); the fit is an asset the step reads and produces, and a fit that does not match the input or its settings, or is not a usable fit at all, is refused naming what differs. The measurements live under `eval/map-refit-stability/`, whose checker now checks every statement of a figure and runs its bounds in CI; `operators/umap_project/README.md` explains when to keep a fit.
- **`datapackage_describe` stamps `x-finetype-version` into every descriptor it writes, and `expect_finetype_version` pins a run to one finetype release.** A descriptor now names the finetype that produced it, and a sidecar cannot overwrite the stamp. Unlike the minimum-version floor, a pin also refuses a newer binary.
- **A `tool:` precondition declares the external binary or artifact a step depends on.** A step whose output depends on a binary on the machine used to stay clean for ever while the binary changed. The tool is found by `name:`, `path:` or `env:` and identified by `version:`, a command or `contents: true`; a change re-runs the step, and a tool that cannot be identified halts the run rather than counting as fresh.
- **`parquet_export` can stamp key-value metadata into the Parquet footer through a new `metadata:` mapping.** A dataset can carry its description inside the file rather than only in a sidecar. Keys are written in sorted order so the output is reproducible, and an export with no `metadata:` is byte-identical to before.
- **Local history and machine-edit checkpoints: `arc history list`, `show` and `restore` give every Protocol an undoable record of its versions, with no git repository needed.** Saves keep bounded snapshots of `arcform.yaml` under `~/.arcform/history` (or `$ARCFORM_HISTORY_DIR`), outside the Protocol, up to 50 per spec, with saves within 10 seconds merged. Every machine edit checkpoints the state it replaces before writing, and a restore does too, so a rollback can itself be undone.
- **The record path: `arcform::spec` can promote an exploration into a step.** `record_step` writes the SQL as a new numbered model marked `-- generated:` and appends a step to the manifest, refusing up front when it cannot apply. `amend_step_sql` regenerates only a model carrying that marker, so hand-written SQL is never overwritten, and recording never runs anything.
- **CLI authoring verbs: `arc create-protocol` writes a fresh `arcform.yaml` and `arc edit-protocol` amends one (`replace`, `rewrite`, `add`, `append`, `delete`, `reorder`, addressed by paths such as `steps[2].command`).** An agent can author and amend a runnable Protocol with nothing but the binary. An edit whose result would not load is refused before the file is touched, and every byte it does not target is kept.
- **The spec write path: `arcform::spec` edits specs as well as loading them.** `SpecEdit` describes a change as a value, `apply_edits` applies it and checks the result loads, and `edit_spec` writes it atomically. Edits splice the original bytes, so comments, blank lines, key order and quoting survive, and `create_spec` writes a new spec through the same gate. A new example, `examples/almanac`, exercises `command: |` block scalars.
- **Execution resilience** — step `retry` with exponential backoff, plus step- and pipeline-level `timeout_sec`. Transient API failures retry; stuck processes are killed.
- **Pipeline parameterisation** — runtime `arc run --param KEY=VALUE` with manifest defaults, `dotenv` loading, and command-step output capture. Values reach shell steps as `ARC_PARAM_*` env vars and SQL via DuckDB `getenv()`; SQL passthrough is preserved.
- **Lifecycle hooks** — `on_init`, `on_success`, `on_failure`, and `on_exit` handlers for pipeline setup, teardown, and notification. Hook failures are non-fatal to the exit code.
- **Step preconditions** — typed freshness checks (`modified_after`, `command`) that skip a step when all pass.
- **Asset registry & SQL introspection** — SQL steps auto-discover their inputs/outputs via sqlparser-rs; command steps declare assets manually. Unparseable SQL degrades to an opaque step with a warning.
- **Run state tracking** — step hashes and run metadata persisted in the DuckDB database for staleness detection across runs.
- **Registry CLI scaffolding** — `arc registry list/show/fetch/run` command tree, index/resolver/cache/transport modules, and sandboxed tarball extraction. Production transport is not yet wired to a live index.
- **brewtrend reference pipeline** — the first complete runnable example under `examples/brewtrend/`, exercising command + SQL steps, preconditions, retries, and a runtime parameter; ships a Frictionless Data Package describing its output.

### Changed

- **The README opens with what arc is for, how to install it, what is in the box, a first Protocol made from your own CSV, and how to connect an agent through `arc mcp`.** The material below it stays, with the library snippet at `=0.2.0`, the status brought up to date, and links that pointed at another GitHub organisation fixed.
- **The crate is packaged for crates.io as `arcform`, so a library user writes `use arcform::spec`, and the command it installs is still `arc`.** crates.io already holds a crate named `arc`, so arcform could not be published or installed with `cargo install`. arcform's sqlparser fork is published as its own crate, `arcform-sqlparser` 0.55.0, so a crate that links arcform no longer needs a `[patch.crates-io]` entry. A crate that links arcform by git as `arc = { … }` adds `package = "arcform"`, or renames its imports to `arcform::`.
- **arc is built against DuckDB v1.5.6, and the new `bundled-duckdb` feature compiles DuckDB into the binary, as release binaries do.** A bundled `arc` starts on a machine with no DuckDB library installed. The crate, CI and the vetted extension list used to name three different DuckDB versions; all now name v1.5.6, and every vetted extension was checked again on it. The ICU extension is not compiled in, so a time-zone query needs `INSTALL icu` once, and the `duckdb` command is still needed to run SQL steps.
- **`arc run` can be told which DuckDB to run with `ARC_DUCKDB_BIN`, and refuses a DuckDB outside `>=1.3, <2`.** A manifest stating `">=1.2"` used to run on any 2.x, and DuckDB 1.2.x exits 0 when a SQL step fails, so a failed step was recorded as passed. arc now enforces its own tested range on every run with a SQL step, a manifest's `engine_version:` narrows it without widening it, and `ARC_ALLOW_UNTESTED_ENGINE=1` lifts arc's range with a warning saying what that costs. A set `ARC_DUCKDB_BIN` that is missing or not executable refuses the run rather than falling back to `PATH`.
- **A Protocol that names no `db:` keeps its database in arc's data folder, not beside its manifest, and a Protocol arc makes no longer writes a `db:` line.** A copy, a zip or a synced folder of a Protocol used to carry a live database the receiver rebuilds anyway. The database now lives under `$ARCFORM_DB_DIR` or `~/.arcform/db`, keyed by the Protocol folder's path; `arc run` prints where, and every `command:` step and hook reads it from `ARC_DB_PATH`. `arc create-protocol` writes `db:` only when `--db` names a path, `arc init` writes none, and an explicit `db:` is unchanged.
- **`arc run` refuses a `umap_project` `neighbors:` above one below the input's row count.** The script quietly clamped such a value, so on 48 rows `neighbors:` of 47, 100 and 200 drew the same map and the run reported success. The refusal names the value, the bound and the input, and an unset `neighbors` still takes 15 or the bound.
- **`SpecEdit::Add` into a sequence item puts the new key at the item's keys' column.** When the item's first key opened a nested block, the new key used to land inside that block and the result did not load.
- **A SQL step's table function is recorded by what it reads, not by its own name.** File readers such as `read_xlsx` and `ST_Read`, and `glob`, record the file they read; row generators such as `range()` record nothing; and a function called on a subquery records the tables the subquery reads, so a change to them marks the step stale. A function whose string or quoted arguments arc cannot read, such as `mlpack_random_forest_train(...)` or `query(...)`, records nothing under its name and draws a warning asking for `depends_on:` and `produces:`.
- **`datapackage_describe` refuses a curated sidecar that forges or contradicts a finetype nomination, and warns on one that pre-empts it.** A field block in `descriptor.overrides.json` could set `x-finetype-nominated` and make a hand-typed field claim to be a declared one. Setting that mark, or overriding the type or label of a nominated column, is now refused; overriding a column nobody nominated, or replacing a nominated column's constraints, warns. A sidecar that sets the mark through a `resource.schema` override or a top-level `resources` array is not yet caught.
- **`text_embed` takes its vectors from the DuckDB embedding extension instead of computing its own, so SQL and a Protocol embed the same text to the same numbers.** The old Python path disagreed with the extension, and with the reference model, on text made only of unknown tokens and on long text, and it is deleted. `extension:` is a new required field naming the extension file, hashed for staleness; `model:` is now optional and, with `model_release:`, is checked against the model the extension carries. Vectors move for out-of-vocabulary and long text, which is truncated at 3,072 characters or 512 tokens, whichever comes first.
- **A `COPY (SELECT …) TO 'file'` records the file it writes.** A step reading that file used to be skipped as fresh after the step that wrote it changed it. The file now appears in the asset graph and the run contract, as a file or a directory according to the statement's options.
- **`arc run` refuses a Protocol whose SQL installs a DuckDB community extension off the vetted list.** The list is `src/vetted_extensions.json`, shown in `docs/VETTED_EXTENSIONS.md`. Before any step runs, arc reads every step's and hook's SQL as the DuckDB CLI reads it, and refuses an unlisted community extension, an install from an address or another repository, and the settings that change where extensions come from or switch DuckDB's parser; no variable lifts the refusal. A vetted extension on a DuckDB version its entry does not name draws a warning.
- **The vetted list holds `finetype`, `minijinja`, `onager` and `splink_udfs`, sixteen extensions in all.** Each has a build for `linux_amd64` and `osx_arm64` and a statement that was run on data and checked, and a licence written as `MIT OR Apache-2.0` counts as permissive when every name in it is.
- **`datapackage_describe` no longer runs Python.** The sidecar merge is now native Rust and the operator calls the `finetype` command directly, so it needs neither `uv` nor Python. Its output is byte-identical on all four published datasets; the Python removal did not change its version, and the `nominations:` key took it to `1.1.0`.
- **The minimum `finetype` is 0.6.54, in both the `datapackage_describe` operator and the `arc mcp` FineType tools.** 0.6.53 corrected three labels published datasets depend on, and 0.6.54 stopped eight-digit numbers typing as confident dates with a date transform attached, which corrupts a column a consumer converts. An older binary is refused naming both versions, and tests hold the floor above each superseded release.
- **The HTTP ingress path is behind a new `http-fetch` feature.** The `http_fetch` and `html_link_discover` operators and the `fresh` precondition's remote check compile only with it, which the `cli` feature pulls in, so a library user with `default-features = false` no longer compiles `ureq` and its TLS stack. The `arc` binary is unchanged.
- **Adopted Frictionless Data Package as the data-description standard.** A Data Package *describes* data (Table Schema, `foreignKeys`, provenance); it does not execute — the runnable artifact stays the arcform manifest. Pipelines may ship a `datapackage.json` describing their IO.
- **Engine version assertion** — manifests may pin an `engine_version` semver constraint, checked at preflight for local/remote parity.
- **Vocabulary: "assets" not "asset registry"** for within-pipeline data declarations, freeing "registry" for the user-facing pipeline catalogue.

### Fixed

- **`arc sql record` and `sql_record` give a Protocol `arc create-protocol` just made its first step, instead of refusing it.** A new Protocol's `steps: []` used to refuse recording with `steps: the sequence has no items`. `arc edit-protocol replace` with a value starting on a new line no longer leaves a space at the end of the key's line, and keeps the comments and blank lines after the old value where they were.
- **`arc mcp`'s `protocol_run` writes nothing to standard output but JSON-RPC, so a client no longer reads a run's own output as a broken message.** A run's step lines and printed rows used to reach the MCP stream and break strict clients. The tool now runs the Protocol as a child `arc run` and returns its run record or, when there is none, an error carrying the last 4,000 bytes the run printed.
- **A frozen operator script is written under another name and renamed into place, so a second `arc` using the same operator never reads an empty script.** The old write truncated the file before writing it, and two runs at once could meet it.
- **A filter or a sort recorded on a table named with a reserved word, such as `order`, quotes the name and runs.** It used to write `FROM order`, which `arc run` then failed on, and `arc sql recognise` now reads such a filter typed with quotes as `filter-rows`.
